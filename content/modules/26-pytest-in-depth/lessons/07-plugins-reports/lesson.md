# Плагіни і звіти

Сила pytest — у плагінах. Це звичайні pip-пакети: після `python -m pip install pytest-html` нові можливості з'являються самі, без змін у тестах. Тестовий фреймворк зазвичай складається з pytest і кількох плагінів, зафіксованих у `requirements.txt`.

## Популярні плагіни

| Плагін | Що дає | Приклад запуску |
|---|---|---|
| `pytest-html` | HTML-звіт для людей | `python -m pytest --html=report.html --self-contained-html` |
| `pytest-xdist` | паралельний запуск на кількох процесах | `python -m pytest -n auto` |
| `pytest-cov` | звіт про покриття коду | `python -m pytest --cov=shop --cov-report=term-missing` |
| `pytest-rerunfailures` | повтор упалих тестів | `python -m pytest --reruns 2` |
| `pytest-timeout` | обмеження часу на тест | `python -m pytest --timeout=30` |
| `pytest-playwright` | фікстури `page`, `browser` для Playwright | `python -m pytest --headed --browser firefox` |

Без плагінів: `--junitxml=report.xml` — звіт у форматі JUnit XML, який розуміють CI-системи (GitLab, Jenkins, Azure).

## Налаштування в pyproject.toml

Щоб не повторювати опції в кожній команді, їх виносять у конфігурацію:

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
addopts = "-ra --strict-markers"
markers = [
    "smoke: fast critical checks for every pull request",
    "slow: long tests for the nightly run",
]
```

## Розбір: що означає кожен рядок

| Рядок | Що робить |
|---|---|
| `testpaths = ["tests"]` | шукати тести лише в папці `tests` |
| `addopts = "-ra ..."` | опції, які додаються до кожного запуску; `-ra` — короткий підсумок про всі пропущені й упалі тести |
| `--strict-markers` | незареєстрований маркер — помилка |
| `markers = [...]` | реєстрація власних маркерів з описом (видно в `python -m pytest --markers`) |

Тепер `python -m pytest` без жодних прапорців працює однаково у всіх членів команди і в CI.

## Паралельний запуск

`pytest-xdist` з `-n auto` запускає тести на кількох процесах — прогін на 20 хвилин може стати 5-хвилинним. Але є ціна:

- тести мають бути **незалежними**: порядок і сусідство непередбачувані;
- спільні ресурси (той самий файл, той самий тестовий користувач, глобальний лічильник) стають джерелом конфліктів;
- фікстура з `scope="session"` створюється **в кожному процесі** окремо.

## Повтори: обережно

`--reruns 2` перезапускає упалий тест. Це рятує від справжніх збоїв середовища, але легко **ховає** нестабільні тести й навіть баги, що проявляються не щоразу. Якщо повтори увімкнені, тести, що пройшли лише з повтору, треба бачити у звіті й розбирати.

> [!QA]
> Звіт — обличчя автотестів для команди. HTML-звіт або JUnit XML публікують як артефакт CI, щоб розробник побачив упалий тест без локального запуску. У модулі про CI ти налаштуєш це в GitHub Actions.

## Типові помилки

- Плагіни встановлені локально, але не записані в `requirements.txt` — у CI вони відсутні.
- `-n auto` для тестів зі спільним станом — випадкові падіння, які не відтворюються по одному.
- `--reruns` як «лікування» нестабільних тестів без розбору причин.
- `addopts` з десятком опцій, які ніхто не пам'ятає, — коментуй і тримай мінімум.

## Підсумок

- Плагіни — pip-пакети, що додають можливості без змін у тестах.
- `pytest-html`, `pytest-xdist`, `pytest-cov`, `pytest-rerunfailures`, `pytest-timeout`, `pytest-playwright`; `--junitxml` — вбудовано.
- Налаштування — у `[tool.pytest.ini_options]`: `testpaths`, `addopts`, `markers`.
- Паралельність вимагає незалежних тестів і унікальних даних.
- Повтори — лише з прозорістю у звіті й розбором причин.
