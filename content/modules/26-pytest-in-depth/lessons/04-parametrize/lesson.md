# Параметризація

Таблиця класів еквівалентності чи таблиця рішень з модуля тест-дизайну — це, по суті, список «вхідні дані → очікуваний результат». Писати для кожного рядка окрему функцію довго й нудно. `@pytest.mark.parametrize` перетворює таблицю на тести напряму.

## Одна функція — багато випадків

```python
import pytest

@pytest.mark.parametrize("weight, expected", [
    (0.5, 50),
    (1.0, 50),
    (1.1, 80),
    (5.0, 80),
])
def test_delivery_fee_by_weight(weight, expected):
    assert delivery_fee(weight) == expected
```

- Перший аргумент — назви параметрів одним рядком через кому.
- Другий — список рядків таблиці; кожен рядок — кортеж значень у тому самому порядку.
- pytest створює **окремий тест** для кожного рядка: `test_delivery_fee_by_weight[0.5-50]`, `[1.0-50]`… Якщо один випадок упаде, інші все одно виконаються.

## Розбір: таблиця рішень → параметри

Вимога: «Видати знижку: член клубу — 10 %, сума від 5000 — ще 5 %».

| Член клубу | Сума | Очікування | Рядок параметрів |
|---|---|---|---|
| ні | 4999 | 0 | `(False, 4999, 0)` |
| ні | 5000 | 5 | `(False, 5000, 5)` |
| так | 100 | 10 | `(True, 100, 10)` |
| так | 5000 | 15 | `(True, 5000, 15)` |

```python
@pytest.mark.parametrize("is_member, total, expected", [
    (False, 4999, 0),
    (False, 5000, 5),
    (True, 100, 10),
    (True, 5000, 15),
])
def test_discount(is_member, total, expected):
    assert discount(is_member, total) == expected
```

Таблиця з вимог і код тесту виглядають однаково — рев'юверу легко звірити, що нічого не пропущено.

## Зрозумілі назви: ids і pytest.param

Автоматичні назви на кшталт `[True-5000-15]` важко читати. Є два способи дати свої:

```python
@pytest.mark.parametrize("email", ["", "   ", "qa.example.test"], ids=["empty", "spaces", "no-at"])
def test_invalid_email(email):
    assert is_valid_email(email) is False

@pytest.mark.parametrize("total, expected", [
    pytest.param(4999, 0, id="just-below-threshold"),
    pytest.param(5000, 5, id="threshold"),
])
def test_threshold(total, expected):
    ...
```

У звіті: `test_invalid_email[no-at]` — одразу ясно, що зламалося.

## Декілька декораторів — усі комбінації

```python
@pytest.mark.parametrize("browser", ["chromium", "firefox"])
@pytest.mark.parametrize("page", ["/login", "/cart", "/checkout"])
def test_page_loads(browser, page):
    ...                     # 2 × 3 = 6 тестів
```

Складені декоратори дають декартів добуток — зручно для матриць «браузер × сторінка», але кількість тестів швидко росте.

## Параметризація і фікстури

Параметри й фікстури поєднуються в одному тесті: `def test_x(make_user, role, expected):` — фікстура приходить від pytest, а `role` і `expected` — з таблиці параметрів.

> [!QA]
> Параметризація — найкоротший шлях від тест-дизайну до автотестів: граничні значення, класи еквівалентності й таблиці рішень стають списками параметрів. На співбесіді її часто просять продемонструвати на live coding — «протестуй функцію валідації пароля».

## Коли краще окремі тести

Параметризуй, коли **перевірка однакова**, а різняться лише дані. Якщо для різних випадків потрібна різна логіка (`if` усередині тесту залежно від параметра) — це ознака, що випадки варто розділити на окремі тести.

## Типові помилки

- Назви в рядку не збігаються з параметрами функції: `"value, expected"`, а функція `def test(val, expected)` — pytest повідомить про помилку.
- Один параметр, але значення-кортежі: `parametrize("pair", [(1, 2)])` передасть кортеж цілком — це нормально, але легко переплутати з двома параметрами.
- Очікуване значення обчислюється в тесті тією самою формулою, що й у коді, — тест повторює помилку.
- Логіка `if` у параметризованому тесті — краще окремі тести.

## Підсумок

- `@pytest.mark.parametrize("a, b, expected", [(…), (…)])` — окремий тест для кожного рядка.
- Таблиця з тест-дизайну = список параметрів.
- `ids=[…]` або `pytest.param(…, id="…")` — зрозумілі назви випадків.
- Складені декоратори — усі комбінації; фікстури й параметри поєднуються.
- Однакова перевірка — параметризуй; різна логіка — окремі тести.
