# Області дії фікстур і прибирання через yield

Фікстура з минулого уроку створювалась для **кожного** тесту. Це найбезпечніше, але не завжди можливо: запуск браузера чи підключення до бази займає секунди, і робити це сто разів поспіль — дорого. А ще тести, що **створюють** дані (замовлення, користувачів), мають за собою прибирати.

## Області дії (scope)

```python
@pytest.fixture(scope="session")
def api_token():
    return login_and_get_token()       # один раз на весь прогін
```

| scope | Скільки разів створюється |
|---|---|
| `function` (за замовчуванням) | для кожного тесту |
| `class` | один раз на клас тестів |
| `module` | один раз на файл тестів |
| `session` | один раз на весь прогін |

Більший scope — швидше, але **спільний** об'єкт: якщо тест його змінить, інші побачать зміни. Тому великий scope — для дорогого й **незмінного**: токен, конфігурація, підключення, браузер. Дані, які тести змінюють, — лише `function`.

## Прибирання через yield

```python
@pytest.fixture
def temp_user(api):
    user_id = api.create_user("temp@example.test")   # підготовка
    yield user_id                                    # тест отримує user_id
    api.delete_user(user_id)                         # прибирання — після тесту
```

Код **до** `yield` — підготовка, значення після `yield` отримує тест, код **після** — прибирання. Воно виконується **навіть якщо тест упав** — так тестові дані не накопичуються в середовищі.

## Розбір: порядок підготовки й прибирання

```python
@pytest.fixture(scope="module")
def database():
    print("connect")
    yield
    print("disconnect")

@pytest.fixture
def report(database):
    print("create report")
    yield
    print("delete report")

def test_export(report): print("test_export")
def test_print(report): print("test_print")
```

| Крок | Вивід | Чому |
|---|---|---|
| 1 | `connect` | `database` (module) — перед першим тестом файлу |
| 2 | `create report` | `report` (function) — для першого тесту |
| 3 | `test_export` | сам тест |
| 4 | `delete report` | прибирання function-фікстури — одразу після тесту |
| 5 | `create report` | знову — для другого тесту |
| 6 | `test_print` | тест |
| 7 | `delete report` | прибирання |
| 8 | `disconnect` | прибирання module-фікстури — після **останнього** тесту файлу |

Прибирання йде у **зворотному** порядку до підготовки: спершу те, що створено останнім.

## autouse

Фікстуру з `autouse=True` не треба просити — вона працює для кожного тесту (у своїй області видимості):

```python
@pytest.fixture(autouse=True)
def reset_settings():
    yield
    SETTINGS.clear()        # після кожного тесту
```

Зручно для «прибиральників» і перевірок, але зловживати не варто: тест, що залежить від невидимої фікстури, важче зрозуміти.

> [!QA]
> Тести, що створюють дані через API чи UI і не прибирають їх, поступово «засмічують» тестове середовище: списки ростуть, пошук знаходить сміття, ліміти вичерпуються. Правило: **хто створив — той і видаляє**, у прибиранні фікстури після `yield`.

## Типові помилки

- `scope="session"` для об'єкта, який тести змінюють, — тести впливають один на одного.
- `return` замість `yield` — прибирання не відбудеться.
- Прибирання в кінці тесту замість фікстури — якщо тест упаде раніше, рядок прибирання не виконається.
- Фікстура з великим scope просить фікстуру з меншим (`session` → `function`) — pytest не дозволить: `ScopeMismatch`.

## Підсумок

- scope: `function` (за замовчуванням), `class`, `module`, `session`.
- Великий scope — для дорогого й незмінного; дані, що змінюються, — `function`.
- `yield` ділить фікстуру на підготовку і прибирання; прибирання виконується навіть після падіння.
- Прибирання — у зворотному порядку; module/session — після останнього тесту.
- `autouse=True` — фікстура для кожного тесту без запиту.
