# Автоочікування і нестабільні тести

**Flaky test** — тест, який то проходить, то падає, хоча ні код застосунку, ні код тесту не змінювалися. Один такий тест у наборі — і команда перестає довіряти червоному: «а, це знову той нестабільний». Через це пропускають справжні баги. Найчастіша причина в UI-тестах — **час**: тест робить крок раніше, ніж сторінка до нього готова.

## Автоочікування дій

Перед кожною дією Playwright перевіряє, що елемент готовий, і чекає (до timeout дії), поки всі умови виконаються:

| Перевірка | Що означає | Для яких дій |
|---|---|---|
| Visible | елемент видно (не `display: none`, має розмір) | click, fill, check, hover, select_option |
| Stable | елемент не рухається (анімація закінчилась) | click, check, hover |
| Receives events | елемент не перекритий іншим (модальним вікном, банером) | click, check, hover |
| Enabled | елемент не `disabled` | click, fill, check, select_option |
| Editable | поле не `readonly` | fill |

Тому `click()` по кнопці, яка з'являється через пів секунди, просто дочекається її. А якщо кнопку перекриває банер cookies, `click()` чекатиме й упаде з повідомленням, *що саме* заважає.

## Повторення перевірок

`expect(...)` повторює перевірку, доки вона не справдиться (урок 5). Разом з автоочікуванням дій це покриває майже всі випадки: **писати власні очікування зазвичай не потрібно**.

## Чому не sleep

```python
page.get_by_role("button", name="Save").click()
time.sleep(2)                                    # погано
assert page.get_by_role("status").inner_text() == "Saved"
```

| Пауза | Що станеться |
|---|---|
| менша, ніж потрібно сторінці (на CI сервер повільніший) | тест падає «випадково» |
| більша, ніж потрібно | тест завжди чекає повні 2 с; 200 таких тестів — плюс 6–7 хвилин на кожен прогін |

`page.wait_for_timeout(2000)` — та сама пауза, лише від Playwright. Виправлення — перевірка, яка чекає саме **стану**:

```python
page.get_by_role("button", name="Save").click()
expect(page.get_by_role("status")).to_have_text("Saved")
```

## Розбір: дві версії одного тесту

Сервер відповідає через 1,5 с. Порівняй, що відбувається в часі:

| Час | З `time.sleep(0.5)` + `inner_text()` | З `expect(...).to_have_text(...)` |
|---|---|---|
| 0 с | клік — запит пішов | клік — запит пішов |
| 0,5 с | пауза скінчилась, читає текст — на сторінці ще **старий** результат → тест падає | перевіряє — не збіглося, пробує знову |
| 1,0 с | — | ще не збіглося, пробує знову |
| 1,5 с | — | відповідь прийшла, текст збігся → тест пройшов |

На швидкому ноутбуці відповідь могла прийти за 0,4 с — тому тест «у мене проходив».

## Коли потрібне явне очікування

```python
expect(page).to_have_url(re.compile(r".*/orders/\d+"))     # чекати переходу на іншу сторінку

with page.expect_response("**/api/orders") as response_info:  # чекати конкретну відповідь сервера
    page.get_by_role("button", name="Place order").click()
response = response_info.value
assert response.status == 201
```

`expect_response` — менеджер контексту: спершу «підписуємося» на відповідь, потім робимо дію, що її викликає. Так не пропустимо відповідь, яка прийде дуже швидко.

## Методи, які не чекають

`inner_text()`, `text_content()`, `is_visible()`, `is_checked()`, `count()`, `input_value()` повертають стан **зараз**. Їх використовують для логів або коли стан уже встановився (після web-first перевірки) — але не як головну перевірку.

## Інші причини нестабільності

| Причина | Приклад | Що робити |
|---|---|---|
| спільні дані між тестами | два тести змінюють одне замовлення | кожен тест створює свої дані |
| залежність від порядку | тест B проходить лише після тесту A | тест сам готує свою передумову |
| випадкові дані | `random.choice` без seed | фіксовані дані або seed |
| дата й час | «сьогодні» після опівночі — інший день | фіксувати дату в тестових даних |
| зовнішні сервіси | платіжний sandbox іноді відповідає 10 с | підміна мережі (наступний модуль) |

pytest-playwright ізолює **браузер** (новий контекст для кожного тесту), але не дані на сервері — про них дбає сам тест.

## Як довести, що виправлення допомогло

Нестабільний тест падає не завжди, тож один зелений прогін нічого не доводить. Запусти його багато разів:

```python
@pytest.mark.parametrize("attempt", range(20))
def test_save_shows_status(page: Page, attempt):
    ...
```

20 зелених прогонів поспіль (і на CI теж) — уже аргумент. Перед комітом цей параметр прибирають.

> [!QA]
> Нестабільний тест — теж дефект, тільки в тестах. Його не «перезапускають, поки не позеленіє»: знаходять причину, виправляють або тимчасово позначають і заводять задачу. Інакше червоні тести перестають щось означати.

## Типові помилки

- «Виправити» flaky тест, збільшивши `sleep` з 1 до 3 секунд: тест став повільнішим і все одно впаде на повільнішому CI.
- `assert locator.is_visible()` замість `expect(locator).to_be_visible()`.
- Тест залежить від даних, які лишив попередній тест.
- Вважати тест виправленим після одного зеленого прогону.

## Підсумок

- Дії самі чекають, поки елемент готовий (visible, stable, enabled…), перевірки `expect` повторюються.
- `time.sleep` і `wait_for_timeout` роблять тести або нестабільними, або повільними — замінюй їх перевіркою стану.
- Явні очікування: `to_have_url`, `expect_response` — для переходів і відповідей сервера.
- Інші джерела нестабільності: спільні дані, порядок тестів, випадковість, дата, зовнішні сервіси.
- Виправлення доводять багатьма прогонами поспіль.
