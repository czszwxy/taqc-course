# Тестові дані й параметризовані тести

Техніки з модуля 03 дають **набір випадків**: межі (0, 1, 10, 11), класи еквівалентності, комбінації з таблиці рішень. Писати окремий тест на кожен рядок довго. Параметризація перетворює таблицю на тести.

## Таблиця + цикл

```ts
const QUANTITIES = [
  { qty: '0', valid: false },
  { qty: '1', valid: true },
  { qty: '10', valid: true },
  { qty: '11', valid: false },
];

for (const { qty, valid } of QUANTITIES) {
  test(`quantity ${qty} is ${valid ? 'accepted' : 'rejected'}`, async ({ page }) => {
    await page.goto('/playground/cart');
    await page.getByLabel('Quantity of Wireless mouse M2').fill(qty);
    // …перевірки
  });
}
```

- Цикл виконується під час **завантаження файлу** і створює окремі тести. У звіті 4 тести, кожен зі своєю назвою.
- Назви мають бути **унікальними**, тому вставляй дані в шаблонний рядок. Playwright зупиниться з помилкою, якщо дві назви збігаються.
- Кожен згенерований тест незалежний: падіння `quantity 0` не зупиняє `quantity 11`.

## Дані з файлу

```ts
import promoCases from './data/promo-codes.json';

for (const c of promoCases) {
  test(`promo ${c.code} → discount ${c.discount}`, async ({ page }) => { /* … */ });
}
```

Таблицю в JSON або CSV може доповнювати і не-програміст (аналітик, мануальний QA).

## Унікальні дані

Тести йдуть паралельно (у воркерах) і повторюються щодня. Якщо два тести реєструють `test@example.com`, другий упаде з «email already exists». Генеруй унікальні значення:

```ts
const email = `qa+${Date.now()}-${test.info().workerIndex}@gadgetly.test`;
```

`test.info()` дає інформацію про поточний тест: назву, воркер, номер повтору.

## Звідки беруться дані

| Спосіб | Коли |
|---|---|
| створити через **API** перед тестом | швидко й надійно (найчастіше) |
| створити через UI | лише коли саме UI створення і тестується |
| підготовлені дані (seed) у тестовій БД | довідники, стабільні сутності |
| мок відповіді (`page.route`, урок 8) | рідкісні стани: помилки, порожні списки |

> [!WARNING]
> Тест, що змінює спільні дані (наприклад, «видалити замовлення 1002»), ламає інші тести й колег. Кожен тест **створює своє** і **прибирає за собою**: в `afterEach` або в teardown фікстури.

## Параметризація проєктів

Інколи параметр — це не дані, а середовище: браузер, мова, роль користувача. Для цього є `projects` у конфігу (модуль 15) і власні опції:

```ts
// той самий набір тестів для двох мов інтерфейсу
projects: [
  { name: 'uk', use: { locale: 'uk-UA' } },
  { name: 'en', use: { locale: 'en-US' } },
],
```

> [!QA]
> Параметризація не замінює тест-дизайн, а підсилює його. 20 випадкових рядків нічого не дадуть. 6 рядків «межа − 1, межа, межа + 1» з обох боків ловлять більшість off-by-one багів. Таблиця даних у тесті — це твоя таблиця з модуля 03, тільки виконувана.

## Підсумок

- Data-driven тести — це таблиця випадків + `for (const … of …)` + `` test(`назва з ${даними}`) ``.
- Назви мають бути унікальні й інформативні. Кожен випадок — окремий тест.
- Дані можна тримати в JSON/CSV. Унікальні значення генеруються з `Date.now()` і `test.info()`.
- Дані краще створювати через API і прибирати за собою. Спільні дані не змінюють.
- Середовище (браузер, мова, роль) параметризують через `projects`.
