# Навіщо автоматизувати: вигоди, витрати, flaky-тести

Автотест — це програма, яка робить те саме, що й тестувальник: відкриває сторінку, заповнює форму, натискає кнопку і **перевіряє** результат. Різниця в тому, що програма не втомлюється, не пропускає кроків і проганяє сотні перевірок за хвилини, хоч щоночі, хоч на кожен коміт.

## Що дає автоматизація

- **Швидкий регрес**: 300 перевірок, які вручну займають 2 дні, автотести проходять за 10–20 хвилин.
- **Швидкий фідбек**: тести запускаються на кожен pull request (CI). Розробник дізнається про поломку за хвилини, а не через тиждень.
- **Однаковість**: автотест щоразу виконує ті самі кроки з тими самими даними.
- **Звільнений час**: замість рутинного регресу тестувальник займається дослідницьким тестуванням, новими фічами, ризиками.

## Скільки це коштує

Автоматизація — не безкоштовна:

- тест треба **написати** (зазвичай у 3–10 разів довше, ніж пройти кейс вручну);
- тест треба **підтримувати**: змінився інтерфейс — тест треба оновити;
- потрібна **інфраструктура**: CI, середовища, тестові дані;
- поганий тест **шкодить**: хибна тривога забирає час, а тест, що нічого не перевіряє, дає хибне відчуття безпеки.

> [!NOTE]
> Автотест окуповується, коли його запускають **багато разів**. Тест, який виконається двічі за весь проєкт, дешевше пройти руками.

## Що автоматизувати першим

| Хороші кандидати | Погані кандидати |
|---|---|
| smoke-перевірки критичних шляхів (логін, оформлення замовлення) | функції, що ще активно змінюються щодня |
| регресійні кейси, які проходять кожен реліз | перевірки «чи гарно виглядає», юзабіліті |
| розрахунки з багатьма комбінаціями (знижки, податки) | одноразові перевірки |
| перевірки API та бізнес-правил | дослідницьке тестування |
| дані, які вручну перевіряти довго (100 рядків таблиці) | сценарії з капчею, реальними платежами, SMS |

> [!QA]
> Автоматизація не замінює тестувальника. Вона перевіряє те, що ми **вже знаємо** (регрес). Нові баги в нових місцях частіше знаходить людина під час дослідницького тестування.

## Піраміда тестів

```text
          /\        E2E / UI      — мало: повільні, дорогі, крихкі
         /  \
        /----\      API / integration — більше
       /      \
      /--------\    Unit          — найбільше: швидкі, дешеві
```

UI-тести (саме їх ми пишемо на Playwright) найближчі до користувача, але найповільніші й найчутливіші до змін. Тому на рівні UI перевіряють **ключові сценарії**, а детальні комбінації даних краще перенести на рівень API чи unit, де тести швидші.

## Flaky-тести

**Flaky-тест** (нестабільний) — тест, який на тому самому коді то проходить, то падає. Типові причини:

- **фіксовані паузи** (`sleep 2 s`), а сервер іноді відповідає за 3 с;
- **гонки** (race conditions): тест перевіряє результат раніше, ніж сторінка його показала;
- **залежність між тестами**: тест B працює, лише якщо тест A створив дані;
- **спільні тестові дані**: два тести одночасно змінюють одного користувача;
- **нестабільні локатори**: «третя кнопка в другому div».

> [!WARNING]
> Flaky-тести вбивають довіру. Коли команда звикає до «та він завжди іноді падає», вона пропускає і справжні падіння. Нестабільний тест треба **виправити** або тимчасово вимкнути з тікетом на виправлення, а не «перезапускати, поки не позеленіє».

Як відрізнити flaky-тест від справжнього бага: прогнати тест багато разів на тому самому коді (`--repeat-each=10`). Падає завжди — швидше за все баг або неправильна перевірка. Падає іноді — flaky.

## Як це працює в цьому модулі

Практичні завдання з уроку 4 — це **справжні Playwright-тести**. Застосунок запускає їх у Chromium на сторінках Bug Playground: спершу на правильній версії сторінки (тест має бути зеленим), потім на версіях, де ввімкнено по одному багу (тест має впасти). Так ти бачиш головне: хороший автотест **ловить баг**.

## Підсумок

- Автоматизація пришвидшує регрес і фідбек, але коштує часу на написання, підтримку й інфраструктуру.
- Автоматизують те, що запускається часто й стабільне: smoke, регрес, розрахунки, API.
- Піраміда тестів: багато unit, менше API, найменше UI.
- Flaky-тест то проходить, то падає на тому самому коді. Його причини — паузи, гонки, залежності, спільні дані, крихкі локатори.
- Flaky-тести треба виправляти, бо вони руйнують довіру до всього набору.
