# Автоочікування, таймаути і flaky-тести

## Playwright чекає сам

Ти вже бачив два механізми:

1. **Дії** (`click`, `fill`, `check`…) чекають, поки елемент стане видимим, стабільним, активним і не перекритим (урок 7).
2. **Web-first перевірки** (`await expect(locator).toHaveText(…)`) повторюються, доки умова не виконається (урок 8).

Тому в хорошому Playwright-тесті **немає пауз**. Тест іде з тією швидкістю, з якою працює сторінка.

## Таймаути

| Таймаут | За замовчуванням | Де змінити |
|---|---|---|
| тест цілком | 30 с | `timeout` у конфігу, `test.setTimeout(…)` |
| web-first перевірка | 5 с | `expect: { timeout }`, `toHaveText('…', { timeout: 10_000 })` |
| дія (click, fill) | без окремого ліміту (обмежена таймаутом тесту) | `use: { actionTimeout }` |
| навігація (`goto`) | без окремого ліміту | `use: { navigationTimeout }` |

> [!TIP]
> Якщо конкретна дія справді довга (звіт генерується 20 с), збільш таймаут **лише для цієї перевірки**: `await expect(report).toBeVisible({ timeout: 30_000 })`. Не роздувай глобальні таймаути: тоді кожне падіння чекатиме хвилину.

## waitForTimeout — антипатерн

```ts
await page.getByRole('button', { name: 'Send' }).click();
await page.waitForTimeout(2000);  // ❌
```

Фіксована пауза завжди помиляється:

- **занадто коротка** на повільному CI: тест падає (flaky);
- **занадто довга** на швидкому комп'ютері: тест марно чекає. 100 тестів × 2 с = понад 3 хвилини простою.

Замість паузи чекай **подію**, яка тобі потрібна:

```ts
await expect(page.getByTestId('api-status')).toHaveText('200 OK');            // з'явився результат
await expect(page.getByRole('button', { name: 'Send' })).toBeEnabled();       // кнопка знову активна
await expect(page).toHaveURL(/\/orders\/\d+/);                                // перейшли на сторінку
const response = await page.waitForResponse((r) => r.url().includes('/api/orders')); // дочекались відповіді сервера
```

## Причини flaky-тестів

| Причина | Як виглядає | Як виправити |
|---|---|---|
| Гонка з UI | перевірка виконується раніше, ніж з'явився результат | web-first перевірка замість `textContent()` |
| Фіксовані паузи | `waitForTimeout(…)` | чекати подію |
| Залежність між тестами | тест B працює лише після тесту A | кожен тест готує свої дані сам |
| Спільні дані | два паралельні тести змінюють одного користувача | унікальні дані на тест |
| Крихкі локатори | `nth(3)`, довгі CSS-шляхи | ролі, підписи, test id |
| Анімації, сповіщення | клік у момент, коли елемент рухається або його перекриває toast | автоочікування; не `force: true` |
| Зовнішні сервіси | тест залежить від стороннього API | мок або стабільне тестове середовище |

## Як знайти і розібрати

```bash
npx playwright test cart.spec.ts --repeat-each=20   # багато прогонів одного тесту
npx playwright test --retries=2                     # у звіті з'являться "flaky" тести
```

Увімкни `trace: 'on-first-retry'` і відкрий trace впалого тесту (`npx playwright show-trace trace.zip` або з HTML-звіту). Там видно кожен крок, знімок DOM до й після, мережеві запити й консоль. Зазвичай одразу видно, що перевірка виконалася до того, як прийшла відповідь.

> [!WARNING]
> Повтори (`retries`) — це діагностика, а не ліки. Тест, що проходить «з другого разу», усе одно треба виправити, бо він ховає або гонку в тесті, або справжню нестабільність продукту.

> [!QA]
> Іноді flaky-тест знаходить **справжній баг**: подвійний клік створює два замовлення, повільний сервер повертає старі дані. Перш ніж «лагодити» тест, переконайся, що проблема саме в тесті, а не в продукті.

## Підсумок

- Дії й web-first перевірки чекають самі, тому паузи не потрібні.
- Таймаути: тест 30 с, перевірка 5 с. Збільшуй точково, а не глобально.
- `waitForTimeout` або занадто коротка (flaky), або занадто довга (повільно). Чекай подію: текст, стан кнопки, URL, відповідь сервера.
- Причини flaky-тестів: гонки, паузи, залежність тестів, спільні дані, крихкі локатори, анімації, зовнішні сервіси.
- Діагностика: `--repeat-each`, `--retries`, trace. Виправляй причину, не ховай її повторами.
