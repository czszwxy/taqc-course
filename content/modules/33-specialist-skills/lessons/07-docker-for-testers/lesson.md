# Docker для тестувальника

«У мене працює» — найвідоміша фраза в розробці. Причина майже завжди в середовищі: інша версія Node.js, іншої бібліотеки, інша база даних. **Docker** пакує програму разом з усім, що їй потрібно, в **контейнер**, який однаково запускається на твоєму ноутбуці, у колеги і в CI. Для QA це означає: підняти застосунок потрібної версії однією командою, отримати чисту базу для тестів і запускати автотести в тому самому оточенні, що й CI.

> [!QA]
> У вакансіях Docker стоїть у розділі «буде плюсом» майже завжди. Від тестувальника не чекають написання складних образів — чекають уміння **запустити** готове, подивитися логи і прочитати `docker-compose.yml`.

## Основні поняття

| Поняття | Що це | Аналогія |
|---|---|---|
| **Image** (образ) | шаблон: файли програми та її оточення; не змінюється | інсталятор |
| **Container** (контейнер) | запущений екземпляр образу; ізольований процес | запущена програма |
| **Dockerfile** | текстовий рецепт, як зібрати образ | інструкція збирання |
| **Registry** | сховище образів (Docker Hub та інші) | магазин застосунків |
| **Volume** / bind mount | папка, що живе поза контейнером або спільна з комп'ютером | зовнішній диск |
| **Port mapping** | зв'язок порту комп'ютера з портом контейнера | переадресація дзвінка |
| **Tag** | версія образу: `postgres:17` | номер версії |

Контейнер **одноразовий**: видалив — усе, що було всередині, зникло. Дані, які треба зберегти, кладуть у том.

## Основні команди

| Команда | Що робить |
|---|---|
| `docker pull postgres:17` | завантажити образ |
| `docker run -d --name db -p 5432:5432 -e POSTGRES_PASSWORD=test postgres:17` | запустити контейнер у фоні |
| `docker ps` / `docker ps -a` | запущені / всі контейнери |
| `docker logs -f db` | логи контейнера (`-f` — стежити) |
| `docker exec -it db bash` | відкрити термінал усередині контейнера |
| `docker stop db` / `docker rm db` | зупинити / видалити |
| `docker images` | список завантажених образів |
| `docker build -t my-app:1.4 .` | зібрати образ з Dockerfile у поточній папці |

Найчастіші прапорці `docker run`:

| Прапорець | Значення |
|---|---|
| `-d` | у фоні |
| `-it` | інтерактивно, з терміналом |
| `--rm` | видалити контейнер після завершення |
| `-p 8080:80` | порт `8080` комп'ютера → порт `80` контейнера |
| `-v ${PWD}:/work` | поточна папка видна в контейнері як `/work` |
| `-w /work` | робоча папка всередині |
| `-e NAME=value` | змінна оточення |

## Розбір: Playwright-тести в контейнері

У Playwright є офіційний образ із браузерами й системними бібліотеками:

```bash
docker run --rm --init --ipc=host -v ${PWD}:/work -w /work mcr.microsoft.com/playwright:v1.65.0-noble /bin/bash -c "npm ci && npx playwright test"
```

| Частина | Навіщо |
|---|---|
| `mcr.microsoft.com/playwright:v1.65.0-noble` | образ; версія **має збігатися** з `@playwright/test` у `package.json` |
| `--rm` | контейнер зникне після прогону |
| `--init` | коректне завершення процесів усередині |
| `--ipc=host` | рекомендовано для Chromium — інакше йому може забракнути пам'яті |
| `-v ${PWD}:/work -w /work` | тести беруться з твоєї папки; звіт після прогону лишиться в ній |
| `npm ci` | в образі є браузери, але **немає** пакетів твого проєкту |
| `npx playwright test` | сам прогін |

Якщо версії образу й пакета різні, Playwright не знайде браузерів. Головна користь для тестів — однакове середовище: скріншоти для візуальних порівнянь на Windows і в Linux-контейнері CI відрізняються шрифтами, а в одному й тому самому образі — ні.

## docker compose: кілька контейнерів разом

Застосунок рідко живе сам: йому потрібна база, а тестам — застосунок. `docker-compose.yml` описує всі контейнери одним файлом:

```yaml
services:
  db:
    image: postgres:17
    environment:
      POSTGRES_PASSWORD: test
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://postgres:test@db:5432/postgres
    depends_on:
      - db
  tests:
    image: mcr.microsoft.com/playwright:v1.65.0-noble
    working_dir: /work
    volumes:
      - ./:/work
    ipc: host
    environment:
      BASE_URL: http://app:3000
    depends_on:
      - app
    command: bash -c "npm ci && npx playwright test"
```

| Команда | Що робить |
|---|---|
| `docker compose up -d db app` | підняти базу й застосунок у фоні |
| `docker compose run --rm tests` | запустити тести й прибрати контейнер |
| `docker compose logs -f app` | логи застосунку |
| `docker compose down -v` | зупинити все й видалити томи — чисте середовище |

> [!WARNING]
> Усередині контейнера `localhost` — це **сам контейнер**, а не твій комп'ютер. Контейнери одного compose-файлу звертаються один до одного за **назвами сервісів**: тести йдуть на `http://app:3000`, застосунок — на `db:5432`. Найчастіша помилка новачка — `BASE_URL=http://localhost:3000` у контейнері з тестами.

## Навіщо це QA щодня

- Відтворити баг на конкретній версії: `docker run -p 3000:3000 my-app:1.4.2`.
- Чиста база для кожного прогону: `docker compose down -v`, потім `up`.
- Запустити залежність, якої немає на машині: базу, чергу, поштовий сервер-заглушку.
- Локально отримати те саме, що в CI, і не гадати, чому «в пайплайні падає».

## Типові помилки

- `localhost` у контейнері замість назви сервісу.
- Версія образу Playwright не збігається з версією пакета.
- Тег `latest`: сьогодні одна версія, завтра інша — прогін перестає бути відтворюваним.
- Дані в контейнері без тому — зникають після `rm`; або навпаки, старий том з минулого прогону псує «чисте» середовище.
- Десятки зупинених контейнерів і старих образів займають диск — `--rm` і `docker system prune` рятують.

## Підсумок

- Образ — шаблон, контейнер — запущений екземпляр; контейнер одноразовий.
- `run`, `ps`, `logs`, `exec`, `stop` — щоденний набір; `-p`, `-v`, `-e`, `--rm` — головні прапорці.
- Офіційний образ Playwright: та сама версія, що й пакет; `--ipc=host`; пакети проєкту ставляться через `npm ci`.
- Compose описує базу, застосунок і тести разом; між собою вони спілкуються за назвами сервісів.
- Docker дає однакове середовище локально і в CI.
