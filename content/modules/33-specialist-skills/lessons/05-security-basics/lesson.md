# Основи security-тестування для QA

Повноцінний пентест роблять спеціалісти з безпеки. Але найпоширеніші вразливості — це звичайні **функціональні дефекти у правилах доступу й валідації**, і їх може знайти тестувальник з браузером і Postman: чужі дані за зміненим `id`, сторінка адміністратора без перевірки ролі, скрипт у полі «Ім'я». Знайдений вчасно такий баг коштує годину роботи; знайдений зловмисником — репутацію компанії.

> [!IMPORTANT]
> Перевіряй безпеку **лише** там, де маєш дозвіл: у власному проєкті, на тестових середовищах своєї компанії, на навчальних стендах. «Перевірка» чужого сайту без дозволу — правопорушення, навіть з добрими намірами.

## OWASP Top 10

**OWASP Top 10** — список найкритичніших ризиків вебзастосунків, який оновлюють раз на кілька років. Чинна редакція — 2025:

| Код | Ризик | Простими словами |
|---|---|---|
| A01 | Broken Access Control | користувач бачить або змінює те, що йому не належить |
| A02 | Security Misconfiguration | небезпечні налаштування: відкриті службові сторінки, докладні помилки |
| A03 | Software Supply Chain Failures | вразливі або підроблені залежності й інструменти збирання |
| A04 | Cryptographic Failures | дані не зашифровані там, де мусять бути (паролі, HTTPS) |
| A05 | Injection | введений текст виконується як код (SQL, XSS) |
| A06 | Insecure Design | небезпечна сама логіка, а не її реалізація |
| A07 | Authentication Failures | слабкий вхід: підбір пароля, вічні сесії |
| A08 | Software or Data Integrity Failures | неперевірені оновлення й дані |
| A09 | Security Logging and Alerting Failures | атаку ніхто не помітить: немає журналів і сповіщень |
| A10 | Mishandling of Exceptional Conditions | система небезпечно поводиться при помилках |

У статтях і на співбесідах досі часто згадують редакцію 2021 — категорії майже ті самі, змінились порядок і кілька назв. Для QA найважливіші A01, A05 і A07.

## Контроль доступу (A01)

Найчастіша знахідка тестувальника — **IDOR** (Insecure Direct Object Reference): сервер віддає об'єкт за `id`, не перевіривши, чи він твій.

## Розбір: матриця доступу для одного ендпоінта

`GET /api/invoices/118` — рахунок користувача Олени.

| Хто питає | Очікувано | Якщо інакше |
|---|---|---|
| без токена | `401` | будь-хто читає рахунки |
| зіпсований або прострочений токен | `401` | перевірка токена не працює |
| Олена (власниця) | `200` | зламана основна функція |
| Тарас (інший користувач) | `403` або `404` | **IDOR**: чужі дані |
| адміністратор | `200` | роль не працює |

Таку матрицю складають для кожного чутливого ресурсу і для кожної дії: читання, зміна, видалення. Перевіряй саме **API**: сховати кнопку в інтерфейсі — не захист.

## Автентифікація й сесії (A07)

| Перевірка | Безпечна поведінка |
|---|---|
| 20 неправильних паролів поспіль | тимчасове блокування або `429` |
| вихід із системи | старий токен більше не працює |
| скидання пароля для невідомого email | те саме нейтральне повідомлення, що й для відомого |
| посилання для скидання | одноразове і з терміном дії |
| довга бездіяльність | сесія завершується |

## Ін'єкції (A05)

Ін'єкція — коли введений текст стає частиною команди.

| Проба | Куди | Безпечна поведінка |
|---|---|---|
| `' OR '1'='1` | пошук, логін | звичайна відповідь «нічого не знайдено» / «невірні дані»; не `500` і не всі записи |
| `<script>alert(1)</script>` | ім'я, коментар | показано **як текст**; нічого не виконується |
| `"><img src=x onerror=alert(1)>` | будь-яке поле, що потім показується | показано як текст |

**XSS** (Cross-Site Scripting) небезпечний тим, що чужий скрипт виконується в браузері іншого користувача й може, наприклад, викрасти його сесію. Достатньо показати, що `alert(1)` спрацював, — далі не «експлуатуй».

## Чутливі дані й конфігурація (A04, A02)

- Пароль або повний номер картки у відповіді API, у логах, в URL.
- Форма входу працює через `http://` без переходу на `https://`.
- Сторінка помилки показує stack trace, шляхи до файлів, версії фреймворку.
- Відкриті службові адреси: `/debug`, `/admin`, список файлів у `/uploads/`.

## Як оформляти security-баг

- Severity зазвичай висока: витік чужих даних — Critical.
- Мінімальний доказ: запит, відповідь, яких даних не мало бути. Не копіюй у репорт справжні персональні дані.
- Не обговорюй деталі в публічних каналах, доки баг не виправлено.

Глибші перевірки роблять сканерами (OWASP ZAP, Burp Suite) — це вже наступний рівень; безкоштовні навчальні стенди є у PortSwigger Web Security Academy.

## Типові помилки

- «Кнопки немає — отже, не можна»: перевіряють лише інтерфейс, а не запит напряму.
- Перевірка доступу лише на читання; зміну й видалення чужого ресурсу забули.
- Очікування `200` з порожнім тілом як «захисту»: має бути `401` / `403` / `404`.
- Проби на продакшні чи чужих сайтах.
- Справжні паролі й персональні дані в тестових даних і баг-репортах.

## Підсумок

- OWASP Top 10 — мапа головних ризиків; для QA найближчі A01, A05, A07.
- Доступ: матриця «хто питає → що очікуємо» для кожного ресурсу й дії, на рівні API.
- Автентифікація: блокування підбору, вихід, скидання пароля, тривалість сесії.
- Ін'єкції: проби мають показуватись як текст або давати звичайну помилку.
- Чутливі дані не з'являються у відповідях, логах, URL і повідомленнях про помилки.
- Лише дозволені середовища, мінімальний доказ, обережність з даними.
