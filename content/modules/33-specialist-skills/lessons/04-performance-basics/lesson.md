# Основи performance-тестування

Функціональний тест відповідає на питання «чи працює?». Performance-тест — «чи працює **достатньо швидко** і **під навантаженням**?». Сайт, який у «чорну п'ятницю» відповідає 20 секунд або падає, для бізнесу зламаний, хоч усі функціональні тести зелені. Окремого performance-інженера є не в кожній команді, тож базові речі часто лягають на QA.

> [!QA]
> Від автоматизатора не чекають тюнінгу серверів. Чекають трьох речей: розуміти терміни (p95, throughput, LCP), вміти прочитати звіт навантажувального тесту і помітити деградацію раніше за користувачів.

## Види тестів

| Тест | Навантаження | Питання |
|---|---|---|
| **Load** | очікуване: «звичайний робочий день» | чи вкладаємось у вимоги за нормальних умов? |
| **Stress** | вище за очікуване, росте, доки не зламається | де межа і **як** система ламається й відновлюється? |
| **Spike** | різкий стрибок за секунди | чи переживемо розсилку або рекламу на ТБ? |
| **Soak** (endurance) | звичайне, але **годинами** | чи немає витоків пам'яті, чи не росте час відповіді? |

## Метрики

| Метрика | Що означає |
|---|---|
| Response time | час від запиту до відповіді |
| Throughput | запитів за секунду (RPS), які система обробляє |
| Error rate | частка невдалих запитів |
| Virtual users (VUs) | скільки «користувачів» одночасно імітує тест |

## Розбір: чому середнє бреше

Десять запитів: дев'ять по 100 мс і один — 2000 мс.

| Показник | Значення | Що «каже» |
|---|---|---|
| Середнє (avg) | (9 × 100 + 2000) / 10 = **290 мс** | «усе добре» |
| Медіана (p50) | **100 мс** | половина запитів не повільніша за 100 мс |
| p90 | **100 мс** | 90 % запитів не повільніші за 100 мс |
| p95 | **2000 мс** | 95 % запитів не повільніші за 2000 мс — тобто хтось чекає 2 секунди |
| Максимум | 2000 мс | найгірший випадок |

**Перцентиль pN** — значення, не повільнішими за яке є N % запитів. Простий спосіб порахувати (метод найближчого рангу): відсортувати за зростанням і взяти елемент з номером `ceil(N / 100 × кількість)`. Для p95 з 10 значень: `ceil(9.5) = 10` — десяте, найбільше.

Середнє ховає повільні запити, а саме їх помічають користувачі. Тому вимоги пишуть у перцентилях: «**p95 < 500 мс**, помилок **< 1 %**».

## k6: тест як код

```js
import http from 'k6/http';

export const options = {
  vus: 20,
  duration: '1m',
  thresholds: {
    http_req_failed: ['rate<0.01'],
    http_req_duration: ['p(95)<500'],
  },
};

export default function () {
  http.get('https://staging.example.test/api/products');
}
```

| Рядок | Значення |
|---|---|
| `vus: 20`, `duration: '1m'` | 20 віртуальних користувачів протягом хвилини |
| `http_req_failed: ['rate<0.01']` | помилок менше 1 % |
| `http_req_duration: ['p(95)<500']` | 95 % запитів швидші за 500 мс |
| поріг не виконано | k6 завершується з ненульовим кодом — крок CI червоний |

Пороги (**thresholds**) перетворюють «подивимось на графік» на автоматичну перевірку «пройшов / не пройшов».

## Швидкість у браузері: Core Web Vitals

| Метрика | Що вимірює | «Добре» |
|---|---|---|
| **LCP** — Largest Contentful Paint | коли з'явився головний вміст | ≤ 2.5 с |
| **INP** — Interaction to Next Paint | як швидко сторінка реагує на дії | ≤ 200 мс |
| **CLS** — Cumulative Layout Shift | наскільки «стрибає» верстка | ≤ 0.1 |

Оцінюють за 75-м перцентилем відвідувань. **Lighthouse** (вкладка в Chrome DevTools) вимірює сторінку в лабораторних умовах; INP він не міряє — дій користувача там немає. **Лабораторні** дані зручні для порівняння «до / після», **польові** (від справжніх користувачів) показують реальність.

## Що може зробити QA вже зараз

- Додати в чекліст релізу: Lighthouse для ключових сторінок, порівняння з минулим релізом.
- Дивитися час відповідей у вкладці Network і в логах API-тестів; різке зростання — привід для бага.
- Запускати короткий k6-сценарій (smoke) у CI для головних ендпоінтів.
- Писати вимоги до швидкості вимірювано: «p95 < 500 мс при 50 RPS», а не «швидко».

> [!WARNING]
> Навантажувальні тести запускають **лише** на середовищах, де це дозволено: власний staging або спеціальний стенд. Навантаження на продакшн чи чужий сайт без дозволу — це фактично атака, навіть якщо ти «просто тестував».

## Типові помилки

- Вимога «сайт має працювати швидко» — її неможливо перевірити.
- Висновок за середнім часом: 5 % користувачів чекають по 5 секунд, а «середнє 300 мс».
- Тест на ноутбуці через Wi-Fi: вимірюється мережа тестувальника, а не сервер.
- Жорсткі перевірки часу у функціональних UI-тестах (`expect(duration).toBeLessThan(200)`) — нестабільність без користі.
- Тестові дані «з трьох товарів»: реальна база з мільйоном записів поводиться інакше.

## Підсумок

- Load, stress, spike, soak — різне навантаження, різні питання.
- Метрики: час відповіді в перцентилях (p95, p99), throughput, error rate.
- Середнє ховає повільні запити; вимоги формулюй як пороги.
- k6: `vus`, `duration`, `thresholds` — тест проходить або падає автоматично.
- Фронтенд: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1; Lighthouse — лабораторні дані.
- Навантажуй лише дозволені середовища.
