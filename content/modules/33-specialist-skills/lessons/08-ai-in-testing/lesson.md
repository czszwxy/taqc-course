# AI-асистенти в роботі тестувальника

AI-асистенти (чат-моделі, помічники в IDE, агенти, що самі керують браузером) стали звичайним робочим інструментом. Вони пишуть чернетку тесту за хвилину — і так само за хвилину можуть написати тест, який **виглядає** правильно, але нічого не перевіряє. Цінність тестувальника зміщується: менше набирати код, більше **ставити задачу** і **перевіряти результат**.

> [!QA]
> AI — це дуже швидкий стажер, який ніколи не бачив твого застосунку. Він знає синтаксис Playwright краще за тебе, але не знає, що кнопка називається «Sign in», а не «Login», і що за вимогою товарів має бути 10, а не 12. Відповідальність за тест — твоя.

## Де AI допомагає

| Задача | Приклад |
|---|---|
| Ідеї для тестів | «які негативні сценарії для форми скидання пароля я пропустив(ла)?» |
| Тестові дані | 20 варіантів невалідних email, імена різними алфавітами |
| Чернетка коду | page object за фрагментом розмітки, фікстура, параметризація |
| Пояснення помилок | stack trace, незрозуміле повідомлення TypeScript |
| Рев'ю | «що слабкого в цьому тесті?» |
| Рутина | перетворити чекліст на заготовки тестів, скласти README |

## Де AI помиляється

| Помилка | Як виглядає | Чому |
|---|---|---|
| Вигадані локатори | `page.locator('#login-button')`, якого немає | він не бачив сторінку |
| Вигадані очікування | `toHaveText('12 products found')` | він не знає вимог і даних |
| Слабкі перевірки | `expect(count).toBeGreaterThan(0)`, `toBeTruthy()` | «безпечно» проходить завжди |
| Паузи | `waitForTimeout(3000)` | у навчальних даних багато старого коду |
| Застарілий або неіснуючий API | методи з інших бібліотек чи версій | впевнене «доповнення» прогалин |
| Тест, підігнаний під баг | перевіряє те, що система робить зараз | він бачить поведінку, а не вимогу |

Останнє — найпідступніше: якщо попросити «напиши тести для цієї сторінки» і дати лише сторінку, AI зафіксує **поточну** поведінку — разом з її дефектами.

## Контекст вирішує все

Якість відповіді майже повністю залежить від того, що ти дав(ла) на вході:

| Що дати | Навіщо |
|---|---|
| вимоги (правила, межі, тексти повідомлень) | звідки брати очікувані результати |
| справжню структуру сторінки (aria-снапшот, фрагмент HTML) | щоб локатори існували |
| приклад твого тесту або page object | щоб стиль збігся з фреймворком |
| правила проєкту | «лише getByRole / getByLabel, без waitForTimeout, один тест — одна поведінка» |
| формат відповіді | «один файл spec, без пояснень» |

## Розбір: слабкий і сильний запит

| | Запит | Результат |
|---|---|---|
| Слабкий | «Напиши тести Playwright для сторінки реєстрації» | вигадані поля, загальні перевірки |
| Сильний | роль + вимоги + aria-снапшот форми + правила + формат | тести з реальними локаторами й очікуваннями з вимог |

Каркас сильного запиту:

```text
Ти — QA automation engineer. Напиши тести Playwright (TypeScript) для форми реєстрації.

Вимоги:
- Ім'я: 2–50 символів …
- Вік: 18–120 включно …
- Повідомлення про помилки: "…"

Структура сторінки (aria snapshot):
- textbox "Full name"
- spinbutton "Age"
- button "Create account"

Правила: лише getByRole / getByLabel; web-first перевірки expect; без waitForTimeout;
один тест — одна поведінка; назви тестів описують поведінку.
Формат: один файл signup.spec.ts, без пояснень.
```

## Чекліст рев'ю згенерованого тесту

1. **Запусти.** Тест, який не запускався, — це текст, а не тест.
2. **Локатори існують** і стійкі (роль, підпис, test id — не довгий CSS).
3. **Очікування взяті з вимог**, а не з голови AI чи з поточної поведінки.
4. **Перевірки точні**: конкретний текст, кількість, статус — не `toBeTruthy()`.
5. **Немає пауз** і разових перевірок без очікування.
6. **Тест може впасти**: зламай очікування або умову — він має почервоніти.
7. **Незалежність і дані**: тест сам готує й прибирає своє.
8. **Немає секретів** і зайвих залежностей.

## Приватність і безпека

- Ніколи не вставляй у зовнішній сервіс **секрети**: паролі, токени, ключі, файл `.env`.
- Персональні дані клієнтів, логи й дампи з продакшну — лише після **знеособлення** або взагалі ні.
- Код і документи компанії — за її правилами: з'ясуй, які AI-інструменти дозволені.
- Не запускай наосліп команди, які пропонує AI: спершу прочитай, що вони роблять.

## Інструменти Playwright

| Інструмент | Що це |
|---|---|
| **Codegen** | не AI: записує твої дії і пропонує справжні локатори сторінки |
| **Playwright MCP** | сервер, через який AI-агент керує справжнім браузером і бачить сторінку як дерево доступності — тому не вигадує локатори |
| **Test Agents** | три агенти: **planner** складає план тестів у Markdown, **generator** перетворює його на тести, перевіряючи локатори на живій сторінці, **healer** запускає тести й лагодить ті, що впали |

Агентів додають у проєкт командою `npx playwright init-agents --loop=…` (для свого AI-інструмента). Обережно з автоматичним «лікуванням»: якщо тест упав через справжній баг, «полагоджений» тест цей баг сховає. Зміни, які пропонує агент, читають так само уважно, як код колеги.

## Типові помилки

- Прийняти згенерований тест без запуску й рев'ю, бо «виглядає правильно».
- Просити тести без вимог — отримати фіксацію поточних багів.
- Вставити в чат лог з токеном або даними клієнтів.
- Дозволити «самовідновлення» тестів без перегляду змін.
- Перестати вчитися: без власного розуміння неможливо оцінити відповідь AI.

## Підсумок

- AI швидко робить чернетки, ідеї й дані; не знає твого застосунку й вимог.
- Типові вади: вигадані локатори й очікування, слабкі перевірки, паузи.
- Сильний запит = роль + вимоги + реальна структура сторінки + правила + формат.
- Кожен згенерований тест: запустити, перевірити локатори й очікування, переконатися, що він здатен упасти.
- Секрети й персональні дані — ніколи в запит; правила компанії — понад усе.
