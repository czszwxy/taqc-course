# Структура фреймворку і найкращі практики

Ти вже вмієш усе окремо: локатори, дії, перевірки, Page Objects, фікстури, API-тести, конфіг, звіти. **Фреймворк** — це домовленість, як усе це скласти, щоб набір з 500 тестів був зрозумілим, стабільним і дешевим у підтримці.

## Шари

```text
tests            — сценарії і перевірки (що перевіряємо)
  ↓ використовують
fixtures         — збирають усе разом: користувачі, дані, Page Objects, клієнти; прибирання
  ↓
pages / clients  — як працювати зі сторінками (Page Objects) і з API (OrdersApi, AuthApi)
  ↓
config / data    — середовища, тестові дані, константи
```

Правило: кожен шар знає лише про нижчі. Тест не знає локаторів, Page Object не знає про тестові дані конкретного сценарію.

## Структура папок

```text
gadgetly-e2e/
├─ tests/
│  ├─ ui/cart.spec.ts
│  ├─ ui/account.spec.ts
│  ├─ api/orders.api.spec.ts
│  └─ auth.setup.ts
├─ pages/          AccountPage.ts, CartPage.ts, components/ProductCard.ts
├─ clients/        OrdersApi.ts, AuthApi.ts
├─ fixtures/       index.ts   ← export const test = base.extend<…>(…)
├─ data/           promo-codes.json, users.ts (без паролів!)
├─ playwright.config.ts
├─ .env.example    BASE_URL=…, QA_PASSWORD=…
├─ .github/workflows/playwright.yml
└─ README.md       як встановити, запустити, де звіти
```

Тести імпортують `test` з `fixtures/index.ts`, а не з `@playwright/test`. Так кожен тест отримує всі фікстури проєкту.

## Домовленості

- **Назви тестів** описують поведінку: `locked account cannot sign in`, а не `test login 3`.
- **Один тест — одна поведінка**. Кроки з `test.step`, теги рівнів (`@smoke`, `@regression`).
- **Локатори**: ролі й підписи, `data-testid` за домовленістю з розробниками.
- **Без пауз**, без `force: true`, без `test.only` у коміті.
- **Дані**: створюються тестом або фікстурою, прибираються. Унікальні значення для паралельного запуску.
- **Секрети** лише у змінних оточення і секретах CI.
- **Код тестів рев'юють** так само, як код продукту (модуль 09).

## Антипатерни

| ❌ | Чому погано |
|---|---|
| один «мега-тест» на 200 кроків | впаде на 15-му кроці, і решта не перевірена |
| копіпаста логіну в кожному тесті | 100 місць правити при зміні форми |
| `expect` всередині Page Object на кожному кроці | методи не підходять для негативних сценаріїв |
| тести залежать від порядку | падають при паралельному запуску |
| «зелений будь-що»: `retries: 5`, таймаути по хвилині | ховають і flaky, і справжні баги |
| хардкод адрес і паролів | неможливо змінити середовище, секрети витікають |

## Проєкт для портфоліо

Для співбесіди на Trainee/Junior QA Automation добре мати публічний репозиторій, у якому:

1. README з описом, командами запуску і скріншотом звіту;
2. 15–30 осмислених тестів UI і API: позитивні, негативні, межові;
3. Page Objects, фікстури, конфіг з projects і змінними оточення;
4. GitHub Actions, що запускає тести на кожен push (модуль 18);
5. чиста історія комітів з нормальними повідомленнями (модуль 09).

> [!QA]
> Інтерв'юер дивиться не на кількість тестів, а на **рішення**: чому такі локатори, як ти прибираєш дані, що робиш з flaky-тестами, як тест-дизайн (межі, класи еквівалентності) відображений у тестах. Будь готовий пояснити кожну папку свого проєкту.

## Підсумок

- Шари: тести → фікстури → Page Objects і API-клієнти → конфіг і дані. Кожен шар знає лише про нижчі.
- Тести імпортують `test` з власних фікстур. Структура папок відображає шари.
- Домовленості: назви про поведінку, одна поведінка на тест, без пауз і `only`, дані з прибиранням, секрети в оточенні.
- Антипатерни: мега-тести, копіпаста, залежні тести, «зелений будь-що», хардкод.
- Портфоліо-проєкт: README, осмислені тести, POM + фікстури, CI, чиста історія.
