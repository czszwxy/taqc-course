# Репортери: HTML-звіт і читання результатів

Прогін без звіту нічого не дає команді. **Репортер** визначає, як Playwright показує результати: у терміналі, як HTML-сторінку, як файл для CI або для інших систем.

## Вбудовані репортери

| Репортер | Де і навіщо |
|---|---|
| `list` | термінал: рядок на кожен тест (за замовчуванням локально) |
| `line` | термінал: компактно, одна оновлювана лінія |
| `dot` | термінал: крапка на тест (за замовчуванням на CI) |
| `html` | інтерактивна сторінка з кроками, помилками, trace, скріншотами |
| `json` | машинне читання: власні дашборди, метрики |
| `junit` | XML, який розуміють Jenkins, GitLab, Azure DevOps |
| `github` | анотації помилок прямо в pull request на GitHub |
| `blob` | проміжний формат для об'єднання звітів шардів |

```ts
reporter: [
  ['list'],
  ['html', { open: 'never' }],
  ['junit', { outputFile: 'results/junit.xml' }],
],
```

```bash
npx playwright test --reporter=dot
npx playwright show-report                       # відкрити HTML
npx playwright merge-reports --reporter html ./blob-reports   # об'єднати шарди
```

## HTML-звіт

- фільтри: **Passed / Failed / Flaky / Skipped**, пошук за назвою і тегом (`@smoke`);
- для кожного тесту — кроки з часом, помилка з Expected/Received, вкладення (скріншот, відео, **trace**);
- групування за файлами і `describe`.

## Кроки і вкладення

```ts
test('checkout', async ({ page }) => {
  await test.step('add a product to the cart', async () => { /* … */ });
  await test.step('apply SAVE10', async () => { /* … */ });
  await test.step('check the total', async () => { /* … */ });
});

await test.info().attach('api response', { body: JSON.stringify(body, null, 2), contentType: 'application/json' });
```

`test.step` робить звіт читабельним, як тест-кейс з модуля 04. Вкладення додають докази (відповідь API, лог).

## Як читати результати прогону

| Статус | Що означає | Що робити |
|---|---|---|
| **passed** | зелений | — |
| **failed** | впав і в повторах | розібрати: баг продукту, тесту чи середовища (модуль 16) |
| **flaky** | впав, але пройшов з повтору | завести задачу, розібрати trace — не ігнорувати |
| **skipped** | пропущений (`skip`, `fixme`, умова) | перевірити, що пропуск свідомий і має задачу |

> [!QA]
> Звіт — інструмент комунікації. На стендапі кажуть не «щось червоне», а «з 120 тестів 3 впали: 2 — один баг промокоду (QA-412), 1 — staging недоступний 5 хвилин; 2 flaky у кошику, розбираю trace». Так команда за хвилину розуміє стан релізу.

## Підсумок

- Репортери: `list` / `line` / `dot` для терміналу, `html` для людей, `json` / `junit` / `github` для систем, `blob` для шардів.
- Можна кілька одночасно. `show-report` відкриває HTML.
- `test.step` і `attach` роблять звіт читабельним і доказовим.
- Статуси: passed, failed, flaky, skipped. Кожен, крім passed, потребує дії.
- Результати прогону переказують мовою ризиків: що впало, чому, що з цим робимо.
