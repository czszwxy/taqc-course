# CRUD-ланцюжки і прибирання тестових даних

Окремий запит перевіряє окрему відповідь. Але баги часто ховаються **між** запитами: створене не читається, оновлення не змінило суму, видалене все ще знаходиться. CRUD-тест перевіряє ресурс протягом усього його життя.

## Ланцюжок

```ts
// Create
const created = await request.post('/api/orders', { headers, data: { productId: 1, quantity: 2 } });
expect(created.status()).toBe(201);
const order = await created.json();

// Read
const read = await request.get(`/api/orders/${order.id}`, { headers });
expect(await read.json()).toEqual(order);

// Update — і похідні поля!
const patched = await request.patch(`/api/orders/${order.id}`, { headers, data: { quantity: 3 } });
expect(await patched.json()).toMatchObject({ quantity: 3, total: 1497 });

// Delete — і що його справді немає
expect((await request.delete(`/api/orders/${order.id}`, { headers })).status()).toBe(204);
expect((await request.get(`/api/orders/${order.id}`, { headers })).status()).toBe(404);
```

> [!QA]
> Після Update перевіряй не лише поле, яке змінював, а й ті, що мали змінитися **разом** з ним: суму, дату оновлення, статус. «Кількість 3, а сума як за 2» — класичний баг.

## Повторні операції

| Операція | Повтор | Очікування |
|---|---|---|
| `GET` | скільки завгодно | той самий результат |
| `PUT` (повна заміна) | вдруге з тими самими даними | той самий стан (ідемпотентний) |
| `DELETE` | вдруге | ресурсу вже немає → **404** |
| `POST` | вдруге | **новий** ресурс (не ідемпотентний) |

Тест «видалити двічі» ловить баги, коли сервер каже «готово» (204) про те, чого вже немає.

## Прибирання

Тест, що створює дані, мусить їх **видалити**. Інакше спільне середовище засмічується, а тести починають заважати одне одному.

```ts
const created: number[] = [];

test.afterEach(async ({ request }) => {
  for (const id of created.splice(0)) {
    await request.delete(`/api/orders/${id}`, { headers });   // навіть якщо тест упав
  }
});
```

Варіанти:

| Спосіб | Плюси |
|---|---|
| `afterEach` + список створеного | простий, працює для групи тестів |
| `try { … } finally { delete }` в тесті | наочно, локально |
| фікстура з teardown після `await use()` | перевикористовується, найнадійніше (урок 7, модуль 16) |
| окреме тестове середовище, яке скидається | для великих наборів |

> [!WARNING]
> Ніколи не прибирай «все підряд» (`POST /reset`, `DELETE` усіх замовлень користувача) у тестах, що йдуть паралельно: так ти видалиш дані, з якими зараз працює інший тест. Прибирай **лише своє**.

## Ізоляція

- кожен тест створює свої ресурси й працює лише з ними (за id);
- не перевіряй глобальні лічильники («у користувача 3 замовлення»): паралельний тест може саме зараз створити четверте;
- різні ролі = різні тестові користувачі (наприклад, Olena і Taras для тесту прав доступу).

## Підсумок

- CRUD-тест: створив → прочитав → оновив (з похідними полями) → видалив → переконався, що 404.
- Повторний DELETE чесно відповідає 404. POST не ідемпотентний, PUT — ідемпотентний.
- Прибирай лише свої дані: в `afterEach`, `finally` або teardown фікстури.
- Паралельні тести не мають залежати від глобальних лічильників і спільних даних.
