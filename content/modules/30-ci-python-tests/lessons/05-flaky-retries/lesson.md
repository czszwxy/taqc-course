# Нестабільні тести і повтори

**Flaky-тест** на тому самому коді то проходить, то падає. Він шкодить більше, ніж здається: після кількох «перезапусти — само пройде» команда перестає вірити червоним прогонам — і пропускає справжній баг, що теж виглядав як «просто flaky».

> [!QA]
> Нестабільний тест — це теж дефект, тільки в тестовому коді (або в продукті: гонка станів, яку тест чесно ловить через раз). Його розбирають, як баг: відтворити, знайти причину, виправити, перевірити.

## Типові причини в pytest + Playwright

| Причина | Як виглядає в коді | Виправлення |
|---|---|---|
| Фіксована пауза | `time.sleep(2)` перед перевіркою | `expect(...)` чекає сам |
| Разова перевірка | `assert page.get_by_text("Saved").is_visible()` | `expect(page.get_by_text("Saved")).to_be_visible()` |
| Спільні дані | два тести реєструють `qa@example.test` | унікальні дані: `f"qa-{uuid4().hex[:8]}@example.test"` |
| Залежність від порядку | тест B видаляє замовлення, створене тестом A | кожен тест готує свої дані у фікстурі |
| Спільний стан | тест змінює список із фікстури `scope="session"` | копія або фікстура `scope="function"` |
| Час | «сьогодні», північ, часові пояси | фіксована дата в даних або підміна часу |
| Зовнішні сервіси | реальний платіжний шлюз, пошта | мок (`page.route`, `monkeypatch`) |
| Повільна машина CI | таймаут на межі | менше роботи в тесті, розумні таймаути |

Паралельний запуск (`-n auto`) не створює ці проблеми — він їх **виявляє**: залежність від порядку й спільні дані миттєво стають видимими.

## Як впіймати

```bash
pip install pytest-repeat
python -m pytest tests/ui/test_cart.py --count=30 -x
```

`--count=30` запускає кожен тест 30 разів, `-x` зупиняє на першому падінні. Інші способи:

- **історія CI**: той самий тест на тому самому коміті і зелений, і червоний — точно flaky;
- **перемішаний порядок**: плагін `pytest-randomly` перемішує тести і друкує `--randomly-seed=...`, щоб повторити той самий порядок;
- **паралельно й послідовно**: падає лише з `-n 4` — шукай спільні дані.

## Повтори: pytest-rerunfailures

```bash
pip install pytest-rerunfailures
python -m pytest --reruns 2 --reruns-delay 1
```

Упалий тест перезапускається до двох разів з паузою в 1 секунду; фікстури тесту створюються заново. У підсумку видно, скільки було повторів: `… 41 passed, 2 rerun in 63.2s`.

| Варіант | Що робить |
|---|---|
| `--reruns 2` | повторити будь-який упалий тест до 2 разів |
| `--only-rerun ConnectionError` | повторювати лише при такій помилці |
| `@pytest.mark.flaky(reruns=3)` | повтори лише для одного тесту |

## Коли повтори доречні, а коли ховають проблему

| Доречно | Ховає проблему |
|---|---|
| лише в CI, 1–2 повтори | повтори локально — розробник не бачить нестабільності |
| збої інфраструктури: мережа раннера, холодний старт браузера | «лікування» власних `sleep` і разових перевірок |
| кількість повторів видно у звіті й її розбирають | ніхто не дивиться, що пройшло лише з повтору |
| тест сам прибирає за собою дані | повтор API-тесту, що щоразу створює нове замовлення без видалення |

## Карантин

Відомий flaky-тест, який не встигли виправити, не повинен блокувати всі pull request. Його позначають маркером і виносять в окремий job:

```python
@pytest.mark.quarantine  # TEST-512: cart badge updates late, owner: Olena
def test_add_two_items(cart_page):
    ...
```

```bash
python -m pytest -m "not quarantine"   # основний job — блокує merge
python -m pytest -m quarantine         # окремий job, continue-on-error: true
```

Правила карантину: у кожного тесту — задача і відповідальний, термін, і тест **повертається** в основний набір після виправлення. Карантин без терміну — це просто вимкнений тест.

## Розбір: від симптому до виправлення

| Крок | Що робимо | Що бачимо |
|---|---|---|
| 1 | CI: `test_add_two_items` червоний, повтор — зелений | історія: 3 падіння з 40 на тих самих комітах |
| 2 | локально `--count=30 -x` | падає на 7-му прогоні |
| 3 | трейс падіння | лічильник кошика показує `1`, а через мить — `2` |
| 4 | код тесту | `assert page.get_by_test_id("cart-count").inner_text() == "2"` — разова перевірка до оновлення |
| 5 | виправлення | `expect(page.get_by_test_id("cart-count")).to_have_text("2")` |
| 6 | перевірка | `--count=50` — усі зелені; тест виходить з карантину |

## Типові помилки

- `--reruns 5` в `addopts` «на всяк випадок» — нестабільність і рідкісні баги зникають зі звітів.
- `time.sleep(...)` як виправлення — тест став повільнішим, але не стабільним.
- Карантин без задачі й терміну — тест забули назавжди.
- «На моїй машині проходить» — без `--count` і перемішаного порядку проблему не відтворити.

## Підсумок

- Flaky = на тому самому коді то зелений, то червоний; це дефект, його розбирають.
- Головні причини: паузи й разові перевірки, спільні дані й стан, порядок, час, зовнішні сервіси.
- Ловимо: `--count`, перемішаний порядок, паралельний запуск, історія CI.
- `--reruns` — лише в CI, мало, з видимою кількістю повторів; не замість виправлення.
- Карантин — маркер, окремий job, задача з терміном.
