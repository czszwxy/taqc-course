# Tech check: Python test automation

На співбесіді на Python QA Automation технічна частина майже завжди йде за однією схемою: pytest («як працюють фікстури?», «skip чи xfail?»), Playwright («які локатори ти обираєш?», «чому тест нестабільний?»), API («що ти перевіряєш, крім статусу?») і фреймворк з CI («розкажи про свій фреймворк»). Цей tech check закриває блок автоматизації на Python. Блок вважається пройденим, коли ти його складеш.

## Як проходить сесія

1. 12 випадкових питань з банку — рівномірно з кожного модуля блоку, тема за темою.
2. На кожне — близько 2 хвилин. Відповідай **уголос**, ніби навпроти сидить інтерв'юер.
3. Відкриваєш еталонну відповідь і відмічаєш ключові пункти, які ти **справді сказав**.
4. Прохідний бал — 80%. Повторна спроба — новий набір питань.

## Як відповідати на питання про автоматизацію

- **Що це → приклад → навіщо → що зламається.** «Фікстура з `yield` створює замовлення через API, віддає його тесту, а після тесту видаляє — навіть якщо тест упав. Без цього дані накопичуються, і тести починають заважати один одному».
- **Пояснюй рішення.** Не лише «я використовую `expect`», а «бо `expect` чекає, а `assert is_visible()` перевіряє один раз і робить тест нестабільним».
- **Приклади зі свого коду.** Page object для входу, pydantic-модель замовлення, фікстура `settings`, workflow з артефактами — готові відповіді на «а де ти це робив?».
- **Не вигадуй назви.** Не пам'ятаєш точний метод — опиши поведінку й де шукати в документації.

> [!TIP]
> Найчастіші уточнення інтерв'юера: «а що буде з session-фікстурою при `-n 4`?», «чому не `time.sleep`?», «як не логінитися в кожному тесті?», «де лежать секрети?», «що ти робиш з flaky-тестом?». Підготуй на кожне відповідь з прикладом.

## Після сесії

- **Не склав** — таблиця «By topic» покаже, які модулі повторити. Відкрий свої розв'язки з цих модулів і поясни їх уголос, ніби на код-рев'ю.
- **Склав** — пройди tech check з Claude (**Practice with Claude**): він поставить уточнювальні питання й попросить розповісти про фреймворк. Далі — підготовка до співбесіди й фінальний проєкт.

> [!QA]
> Автоматизатора наймають не за знання синтаксису, а за вміння будувати **стабільні** тести, яким команда довіряє, і пояснювати, чому вони побудовані саме так.

## Що перевіряє цей tech check

| Тема | Про що питають |
|---|---|
| pytest: основи | чому pytest, як він знаходить тести, `pytest.raises`, `approx`, ознаки хорошого тесту |
| pytest: поглиблено | фікстури й `yield`, scopes, conftest.py, `parametrize`, skip / xfail / strict, monkeypatch і Mock |
| Playwright для Python | browser / context / page, локатори, авто-очікування і `expect`, налагодження й трейси |
| Playwright на практиці | page objects, storage state, моки мережі, діалоги й нові вкладки |
| API-тести | що перевіряти, правила requests, pydantic-контракти, тестові дані, API + UI |
| Фреймворк і CI | структура, налаштування й секрети, звіти, GitHub Actions, flaky-тести й повтори |

## Підсумок

- Технічна співбесіда на Python QA Automation: pytest, Playwright, API, фреймворк і CI.
- Відповідь: що це → приклад → навіщо → що зламається.
- Пояснюй рішення і наводь приклади зі свого коду.
- Не склав — повтори модулі з «revisit» і поясни свої розв'язки вголос.
