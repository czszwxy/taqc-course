# Менші та безпечніші образи

Перший Dockerfile працює — але образ можна зробити в рази меншим (швидше завантажується на сервер, менше вразливих пакетів) і безпечнішим (без root і без паролів усередині). У цьому уроці — чотири звички, які відрізняють навчальний Dockerfile від робочого.

## 1. Базовий образ

| Варіант | Що всередині | Коли |
|---|---|---|
| `python:3.13` | повний Debian з компіляторами й багатьма бібліотеками | збирати пакети, що компілюються з вихідного коду |
| `python:3.13-slim` | мінімальний Debian: лише те, що потрібно самому Python | **типовий вибір** для застосунку |
| `python:3.13-alpine` | Alpine Linux з бібліотекою **musl** замість glibc | обережно: частина пакетів з PyPI не має готових wheel для musl і компілюється, а деякі поводяться інакше |

У `slim` немає навіть `curl` — це варто пам'ятати, коли пишеш health-перевірку (урок про health). Якщо пакету потрібен компілятор чи системна бібліотека, на допомогу приходить наступна звичка.

## 2. Багатоетапне збирання (multi-stage)

Інструменти для збирання (компілятор, заголовки бібліотек) не потрібні під час роботи. Multi-stage build збирає в одному образі, а в фінальний переносить лише результат:

```text
FROM python:3.13-slim AS build
RUN python -m venv /opt/venv
ENV PATH="/opt/venv/bin:$PATH"
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

FROM python:3.13-slim
ENV PATH="/opt/venv/bin:$PATH" PYTHONUNBUFFERED=1
COPY --from=build /opt/venv /opt/venv
WORKDIR /app
COPY news_api ./news_api
CMD ["fastapi", "run", "news_api/main.py"]
```

Перший етап `build` ставить залежності у віртуальне середовище `/opt/venv`. Другий етап починається з чистого `slim` і копіює **лише папку venv** (`COPY --from=build`). Усе, що лишилось у першому етапі (кеші, компілятори, якщо їх ставили), у фінальний образ не потрапляє.

## 3. Не від root

За замовчуванням процес у контейнері працює від **root**. Якщо в застосунку знайдеться вразливість, зловмисник отримає повні права всередині контейнера. Інструкція `USER` перемикає на звичайного користувача:

```text
RUN useradd --no-log-init --system --uid 10001 app
USER app
```

Усе після `USER` (інші `RUN`, а головне — `CMD`) виконується від `app`. Користувач не може писати в папки root — тому файли, які застосунок має змінювати, створюй з правильним власником (`COPY --chown=app:app ...`) або тримай у томі. Явний `--uid` робить номер користувача однаковим у кожному збиранні.

## 4. Секрети не мають потрапляти в образ

Образ — це архів шарів, і будь-хто з доступом до образу може його розпакувати. Що «запікається» в образ:

| Як | Чому це витік |
|---|---|
| `ENV DATABASE_PASSWORD=...` | змінна зберігається в образі й видна в `docker inspect` |
| `ARG TOKEN` + використання в `RUN` | значення build-аргументів видно в `docker history` |
| `COPY .env .` | файл лежить у шарі |
| `COPY .env .` + пізніше `RUN rm .env` | **все одно** витік: `rm` створює новий шар, а старий з файлом лишається в образі |

Як правильно:

- секрети для **роботи** застосунку — змінні середовища під час **запуску** (`docker run -e`, `env_file` у compose, секрети платформи), не в Dockerfile;
- секрет, потрібний лише **під час збирання** (токен до приватного реєстру пакетів), — через build secret: `RUN --mount=type=secret,id=pip_token ...` монтує його тільки на час цієї команди, без запису в шар;
- `.env` — у `.dockerignore` і `.gitignore`.

## `.dockerignore` у деталях

Правила, які частіше за все дивують:

| Рядок | Що виключає |
|---|---|
| `*.pyc` | `.pyc` **лише в корені** контексту — шаблон порівнюється з шляхом від кореня |
| `**/*.pyc` | `.pyc` у будь-якій папці (`**` — будь-яка кількість папок, і нуль теж) |
| `.venv` | папку `.venv` з усім вмістом |
| `!README.md` | виняток: повертає файл, виключений рядком вище |

Коли кілька рядків підходять до одного файлу, вирішує **останній** з них. Тому `*.md`, потім `!README.md` — README потрапляє; а `!README.md`, потім `*.md` — ні.

## Теги й digest

Тег `python:3.13-slim` — рухомий покажчик: автори оновлюють його з кожним патч-релізом Python і безпековими виправленнями Debian. Це добре (отримуєш виправлення під час збирання), але два збирання в різні дні можуть дати різні образи. Повністю зафіксувати базу можна через **digest**: `python:3.13-slim@sha256:...` — він завжди вказує на той самий образ. Ціна — оновлювати його доведеться самому (або ботом на зразок Dependabot).

> [!WARNING]
> Видалити секрет з образу заднім числом неможливо: якщо пароль хоч раз потрапив у шар, вважай його скомпрометованим, **зміни пароль** і перезбери образ.

## Типові помилки

- `python:3.13` замість `slim` «бо так працювало» — образ у кілька разів більший.
- `RUN rm .env` після `COPY .env` — файл усе одно в попередньому шарі.
- Пароль у `ENV` чи `ARG` — видно в `docker inspect` / `docker history`.
- `*.pyc` у `.dockerignore` без `**/` — вкладені папки не фільтруються.
- `USER` додано, а застосунок пише в `/app` — `PermissionError` на старті.

## Підсумок

- `slim` — типова база; `alpine` — лише якщо всі пакети мають wheel для musl.
- Multi-stage: залежності збираються в одному етапі, у фінальний копіюється лише результат.
- `USER` з явним `--uid` — застосунок не працює від root.
- Секрети — лише під час запуску або через build secrets; `ENV`, `ARG`, `COPY .env` і навіть `RUN rm` лишають їх в образі.
- `.dockerignore`: шляхи від кореня, `**` для будь-якої глибини, `!` для винятків, вирішує останній рядок, що підійшов.
