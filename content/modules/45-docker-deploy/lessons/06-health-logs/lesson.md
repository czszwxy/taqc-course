# Health-перевірки та логи

У production за твоїм застосунком ніхто не стежить очима. Платформа (Docker, Kubernetes, хмарний сервіс) сама вирішує, чи слати йому трафік і чи не час його перезапустити, — і для цього питає спеціальні ендпоінти. А коли щось іде не так, єдине, що лишається, — **логи**. Цей урок про те, як зробити обидва канали корисними.

## Три питання платформи

| Перевірка | Питання | Що робить платформа, якщо «ні» |
|---|---|---|
| **liveness** | процес живий і не завис? | **перезапускає** контейнер |
| **readiness** | готовий приймати запити зараз? | тимчасово **не шле трафік**, але не перезапускає |
| **startup** | уже завершив старт? | поки ні — не перевіряє дві інші (повільний старт не вважається зависанням) |

Ці назви — з Kubernetes, але ідея однакова скрізь. У застосунку їм зазвичай відповідають два ендпоінти:

- **`/health`** (liveness) — відповідає `200`, якщо процес здатен обробити запит. **Не перевіряє зовнішніх залежностей**: якщо база впала, перезапуск API її не підніме, а одночасний перезапуск усіх копій лише погіршить аварію;
- **`/ready`** (readiness) — перевіряє, чи доступні залежності, без яких запити все одно впадуть (база, обов'язковий зовнішній сервіс). Не готовий — `503 Service Unavailable`: «спробуй інший екземпляр».

## Readiness у FastAPI

Приклад для API новин з однією залежністю:

```python
from fastapi import FastAPI
from fastapi.responses import JSONResponse

app = FastAPI()


@app.get("/health")
def health():
    return {"status": "ok"}


@app.get("/ready")
async def ready():
    try:
        await feeds.ping()                       # швидкий запит до сервісу стрічок
    except Exception:
        log.exception("Feeds service is not reachable")
        return JSONResponse(status_code=503, content={"status": "not ready"})
    return {"status": "ready"}
```

Що додати для реального застосунку:

- **тайм-аут** на кожну перевірку: залежність, що «зависла», не має тримати `/ready` довше, ніж платформа готова чекати; інакше зависне й перевірка, а платформа вирішить, що завис застосунок;
- **кілька залежностей одночасно** — `asyncio.gather` з модуля про async;
- **жодних деталей помилки у відповіді**: `/ready` відкритий, а текст винятку може містити ім'я користувача бази чи внутрішню адресу. Деталі — у лог.

## HEALTHCHECK у Docker

Docker теж уміє перевіряти контейнер — інструкція `HEALTHCHECK` у Dockerfile або ключ `healthcheck` у compose. Команда виконується **всередині** контейнера; код виходу `0` — здоровий, `1` — ні. За замовчуванням: кожні 30 секунд, тайм-аут 30 секунд, 3 невдачі поспіль — `unhealthy`.

У `python:3.13-slim` **немає `curl`**, але є Python:

```text
HEALTHCHECK --interval=10s --timeout=3s --retries=3 \
  CMD ["python", "-c", "import urllib.request; urllib.request.urlopen('http://localhost:8000/health', timeout=2)"]
```

`urlopen` кидає виняток на помилку з'єднання й на відповідь `4xx` / `5xx` — Python завершується з кодом `1`. Статус видно в `docker ps` (`healthy` / `unhealthy`), і саме його чекає `depends_on: condition: service_healthy` у compose.

## Логи: у stdout

Контейнер не має «свого» файлу логів, який хтось відкриє. Правило: застосунок пише логи в **stdout / stderr**, а збирає й зберігає їх платформа (`docker logs`, агрегатори на зразок Loki, Elasticsearch, CloudWatch). Звідси:

- жодних `FileHandler` у контейнері — лише `StreamHandler`;
- `PYTHONUNBUFFERED=1` — інакше рядки з'являються в `docker logs` пачками із запізненням;
- uvicorn уже пише access-логи в stdout.

## Структуровані логи

Рядок `Order 1001 paid by user 42` зручно читати очима, але важко шукати: «покажи все про замовлення 1001» перетворюється на регулярні вирази. **Структурований** лог — це один JSON-об'єкт на рядок:

```json
{"time": "2026-11-17T09:30:00.250+00:00", "level": "INFO", "logger": "news.feeds", "message": "Feed refreshed", "feed": "sport", "items": 42}
```

Агрегатор розбирає поля, і пошук стає запитом `feed = "sport" AND level = "ERROR"`. Додаткові поля передають через `extra`:

```python
log.info("Feed refreshed", extra={"feed": "sport", "items": 42})
```

Кожен ключ з `extra` стає атрибутом об'єкта `LogRecord`, а **форматер** (`logging.Formatter`) перетворює запис на рядок. Свій форматер — це підклас з методом `format(record)`:

```python
class PrefixFormatter(logging.Formatter):
    def format(self, record):
        return f"[news] {record.levelname} {record.getMessage()}"
```

## Що логувати і чого ні

- **так:** `request_id` (однаковий для всіх записів одного запиту — так збирають історію запиту), ідентифікатори сутностей, тривалість, результат;
- **ні:** паролі, токени, ключі, повні номери карток, увесь об'єкт налаштувань. Логи читає багато людей і систем, і зберігаються вони довго.

> [!QA]
> Під час інциденту логи — головне джерело правди. Пошук за `request_id` з відповіді, яку бачив користувач, за хвилину знаходить traceback — якщо логи структуровані й мають цей id.

## Підсумок

- Liveness — «процес живий» (без залежностей; «ні» → перезапуск), readiness — «готовий до трафіку» (з залежностями; «ні» → `503`, без перезапуску).
- Перевірки readiness — з тайм-аутами, разом і без деталей помилок у відповіді.
- `HEALTHCHECK` виконується в контейнері; у slim немає `curl` — перевіряй через `python -c`.
- Логи — у stdout; `PYTHONUNBUFFERED=1`; структуровані JSON-записи з полями з `extra`.
- Ніяких секретів у логах; `request_id` пов'язує записи одного запиту.
