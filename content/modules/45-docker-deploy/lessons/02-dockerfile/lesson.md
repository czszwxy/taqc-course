# Dockerfile для Python-застосунку

Образ не завантажують з неба — його **збирають** за рецептом. Рецепт — текстовий файл `Dockerfile` у корені проєкту: кожен рядок — інструкція, яка додає до образу щось нове. Розберемо Dockerfile для API служби підтримки на FastAPI, а потім — як зробити так, щоб він збирався за секунди, а не хвилини.

## Проєкт

```text
helpdesk/
├── Dockerfile
├── .dockerignore
├── requirements.txt
└── helpdesk_api/
    ├── __init__.py
    └── main.py        ← app = FastAPI()
```

## Dockerfile рядок за рядком

```text
FROM python:3.13-slim

ENV PYTHONDONTWRITEBYTECODE=1 \
    PYTHONUNBUFFERED=1

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY helpdesk_api ./helpdesk_api

EXPOSE 8000
CMD ["fastapi", "run", "helpdesk_api/main.py", "--port", "8000"]
```

| Рядок | Що робить |
|---|---|
| `FROM python:3.13-slim` | базовий образ: мінімальний Debian з Python 3.13. Версію Python бери ту, на якій розробляєш і тестуєш |
| `ENV PYTHONDONTWRITEBYTECODE=1` | Python не пише `.pyc`-файли — у контейнері вони не потрібні |
| `ENV PYTHONUNBUFFERED=1` | `print` і логи одразу йдуть у вивід, а не накопичуються в буфері — `docker logs` показує їх без затримки |
| `WORKDIR /app` | робоча папка в образі; наступні команди виконуються в ній |
| `COPY requirements.txt .` | спершу **лише** список залежностей |
| `RUN pip install --no-cache-dir -r requirements.txt` | встановити бібліотеки; `--no-cache-dir` — не зберігати завантажені пакети в образі (менший розмір) |
| `COPY helpdesk_api ./helpdesk_api` | тепер код |
| `EXPOSE 8000` | документація: застосунок слухає 8000 |
| `CMD [...]` | команда запуску контейнера |

`fastapi run` — production-режим FastAPI CLI: без автоперезавантаження і на адресі `0.0.0.0` (порт за замовчуванням `8000`). Під капотом — uvicorn.

## Збирання і запуск

```bash
docker build -t helpdesk-api:1.0 .
docker run --rm -p 8000:8000 helpdesk-api:1.0
```

`-t helpdesk-api:1.0` — ім'я і тег образу, `.` — **контекст збирання**: папка, файли якої Docker може копіювати в образ.

## Кеш шарів: чому спершу `requirements.txt`

Кожна інструкція створює шар, і Docker кешує шари. Під час нового збирання він іде згори вниз і бере шар з кешу, якщо ні інструкція, ні файли для неї не змінились. Щойно щось змінилось — цей шар **і всі нижчі** збираються заново.

| Що змінилось | Що перезбирається |
|---|---|
| нічого | нічого — збирання за секунду |
| код у `helpdesk_api/` | лише `COPY helpdesk_api` і нижче — секунди |
| `requirements.txt` | `pip install` і все нижче — хвилина |
| `FROM` (інша версія Python) | усе |

Код змінюється десятки разів на день, залежності — рідко. Тому спершу копіюють `requirements.txt` і ставлять пакети, а код — після. Якби першим стояв `COPY . .`, будь-яка правка в коді скидала б кеш `pip install`, і кожне збирання тривало б хвилини.

## `.dockerignore`

Контекст збирання — уся папка, і без фільтра в нього потрапить зайве: `.venv` на сотні мегабайт, `.git`, кеші й, що найгірше, `.env` з паролями. Файл `.dockerignore` поруч з Dockerfile виключає їх:

```text
.venv
.git
**/__pycache__
**/*.pyc
.pytest_cache
.env
```

Деталі правил (`**`, винятки з `!`) — у наступному уроці.

## Exec-форма `CMD` і сигнали

`CMD` можна записати двома способами:

| Форма | Приклад | Хто стає головним процесом |
|---|---|---|
| **exec** (JSON-масив) | `CMD ["fastapi", "run", "main.py"]` | сам застосунок |
| shell (рядок) | `CMD fastapi run main.py` | `/bin/sh -c`, а застосунок — його дочірній процес |

`docker stop` надсилає головному процесу сигнал **SIGTERM** — «будь ласка, завершуйся». У shell-формі сигнал отримує `sh`, який **не передає** його далі: застосунок не дізнається про зупинку, Docker чекає 10 секунд і вбиває все через SIGKILL. Незавершені запити обриваються, а код зупинки застосунку (закрити з'єднання, дописати чергу) не виконується. Тому — **завжди exec-форма**. Якщо у Dockerfile кілька `CMD`, діє лише останній.

> [!TIP]
> Системні пакети: якщо бібліотеці потрібен системний пакет, пиши `RUN apt-get update && apt-get install -y --no-install-recommends <пакет> && rm -rf /var/lib/apt/lists/*` **однією** інструкцією. Окремий шар з `apt-get update` закешується і з часом міститиме застарілий список пакетів.

## Розбір: що відбувається під час `docker build`

1. Docker пакує контекст (папку без того, що в `.dockerignore`).
2. `FROM` — бере базовий образ (з кешу або реєстру).
3. Кожна наступна інструкція — новий шар; якщо вхід не змінився, шар з кешу (`CACHED` у виводі).
4. Наприкінці образ отримує ім'я `helpdesk-api:1.0` і лежить у `docker images`.

## Типові помилки

- `COPY . .` до `pip install` — повільні збирання після кожної правки.
- Shell-форма `CMD` — контейнер зупиняється 10 секунд і не виконує код завершення.
- `fastapi dev` або `--reload` в образі — режим розробки зі стеженням за файлами і `127.0.0.1`.
- Немає `.dockerignore` — у контексті `.venv`, `.git` і `.env`.
- `FROM python` без тегу — збирання сьогодні й через місяць дають різні образи.

## Підсумок

- Dockerfile — рецепт образу: `FROM`, `ENV`, `WORKDIR`, `COPY`, `RUN`, `EXPOSE`, `CMD`.
- Порядок для кешу: спершу `requirements.txt` і `pip install --no-cache-dir`, потім код.
- `PYTHONUNBUFFERED=1` — логи без затримки, `fastapi run` — production-сервер на `0.0.0.0`.
- `.dockerignore` тримає `.venv`, `.git` і `.env` поза контекстом.
- `CMD` — лише в exec-формі, щоб застосунок отримав SIGTERM.
