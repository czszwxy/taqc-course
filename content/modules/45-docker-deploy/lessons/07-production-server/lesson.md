# Застосунок у production

`fastapi dev` і `manage.py runserver` створені для розробки: перезапускаються при змінах файлів, показують детальні помилки, обслуговують один запит за іншим. У production потрібен сервер, що тримає навантаження, працює за HTTPS-проксі, правильно зупиняється й не розкриває внутрішніх деталей. Розберемо це для FastAPI і Django.

## FastAPI: `fastapi run` і uvicorn

`fastapi run` — це uvicorn з production-налаштуваннями: адреса `0.0.0.0`, порт `8000` (або зі змінної `PORT`), без автоперезавантаження. Те саме напряму:

```bash
uvicorn weather_api.main:app --host 0.0.0.0 --port 8000
```

**Скільки процесів?** Python-процес використовує одне ядро для Python-коду. Варіанти:

| Де працює | Як масштабувати |
|---|---|
| один сервер з Docker Compose | кілька воркерів в одному контейнері: `--workers 4` (або змінна `WEB_CONCURRENCY`) |
| Kubernetes, хмарні платформи з репліками | **один процес на контейнер**, а кількість контейнерів (реплік) задає платформа |

Документація FastAPI радить саме так: на кластері реплікацією займається платформа, а менеджер процесів усередині контейнера лише ускладнює.

## HTTPS і reverse proxy

Застосунок зазвичай не працює з HTTPS сам. Перед ним стоїть **reverse proxy** (nginx, Caddy, Traefik або балансувальник хмари): приймає HTTPS на порту 443, розшифровує й передає запит застосунку звичайним HTTP. Застосунок бачить адресу проксі замість адреси клієнта й `http` замість `https` — справжні значення проксі кладе в заголовки `X-Forwarded-For` і `X-Forwarded-Proto`.

`fastapi run` читає ці заголовки (`--proxy-headers` увімкнено за замовчуванням), але **довіряє** їм лише від адрес зі списку `--forwarded-allow-ips` (за замовчуванням тільки `127.0.0.1`). Якщо проксі — інший контейнер, його адресу треба додати, інакше `request.url` буде `http://…`, а редиректи й посилання — неправильними.

## Django у production

| Що | Як |
|---|---|
| сервер | WSGI: `gunicorn shop.wsgi`; ASGI: `uvicorn shop.asgi:application` (замість `runserver`) |
| `DEBUG` | `False`; інакше сторінка помилки показує налаштування й код |
| `ALLOWED_HOSTS` | домени сайту зі змінної середовища |
| `SECRET_KEY` | довгий випадковий, з секрету, не з репозиторію |
| статика | `STATIC_ROOT` + `manage.py collectstatic` під час збирання образу; віддає її проксі, CDN або пакет WhiteNoise |
| HTTPS за проксі | `SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")` — лише якщо проксі завжди встановлює цей заголовок |

Перевірку робить сам Django: `python manage.py check --deploy` перелічує небезпечні налаштування з кодами (`security.W018` — `DEBUG` увімкнено, `security.W020` — порожній `ALLOWED_HOSTS` тощо). Його варто запускати в CI з production-налаштуваннями.

## Міграції — окремий крок

Запускати міграції в `CMD` перед стартом сервера здається зручним, але коли стартує п'ять реплік, п'ять процесів одночасно мігрують одну базу. Надійніше — окремий **крок релізу**: одноразовий контейнер з тим самим образом виконує `alembic upgrade head` чи `manage.py migrate`, і лише після його успіху запускаються нові екземпляри застосунку (як сервіс `migrate` у compose з попереднього уроку).

## Коректна зупинка

Платформа зупиняє контейнер при кожному релізі, масштабуванні чи переїзді на інший сервер — тобто постійно. Що відбувається:

1. `docker stop` (чи платформа) надсилає головному процесу **SIGTERM**.
2. uvicorn **перестає приймати** нові з'єднання.
3. **Доробляє** запити, що вже виконуються (без ліміту, якщо не задано `--timeout-graceful-shutdown`).
4. Запускає **shutdown-частину lifespan** — твій код закриття ресурсів.
5. Процес завершується з кодом 0.
6. Якщо за 10 секунд (типовий ліміт `docker stop`; у compose — `stop_grace_period`) процес не завершився, Docker надсилає **SIGKILL** — і все, що не встигло, губиться.

Звідси вимоги: exec-форма `CMD` (інакше SIGTERM отримає `sh`), швидке завершення, ліміти часу на зовнішні виклики.

## Lifespan

Ресурси, що живуть увесь час роботи процесу, відкривають на старті й закривають на зупинці в одному місці — **lifespan**:

```python
from contextlib import asynccontextmanager

import httpx
from fastapi import FastAPI


@asynccontextmanager
async def lifespan(app: FastAPI):
    app.state.weather = httpx.AsyncClient(base_url="https://api.weather.example.com", timeout=5)
    yield                                    # тут застосунок працює
    await app.state.weather.aclose()         # SIGTERM → закрити з'єднання


app = FastAPI(lifespan=lifespan)
```

Код до `yield` виконується до першого запиту, після `yield` — на зупинці. Порядок закриття — **зворотний** до відкриття: спершу те, що користується ресурсом (фонові задачі, черги), і лише потім сам ресурс. Фонову задачу мало попросити зупинитися (`cancel()`) — на неї треба **дочекатися**, інакше вона може ще працювати, коли ресурс уже закрито.

> [!TIP]
> `TestClient(app)` у блоці `with` запускає lifespan: старт на вході в блок і зупинку на виході. Тож коректне завершення можна перевірити звичайним тестом — без Docker і сигналів.

## Підсумок

- Production: `fastapi run` / uvicorn (FastAPI), gunicorn чи uvicorn (Django) — не dev-сервери.
- Масштабування: воркери на одному сервері або один процес на контейнер і репліки на кластері.
- За HTTPS-проксі: `X-Forwarded-*` заголовки і список довірених адрес проксі.
- Django: `DEBUG=False`, `ALLOWED_HOSTS`, секретний `SECRET_KEY`, `collectstatic`, `check --deploy`.
- Міграції — окремий крок релізу; зупинка — SIGTERM → доробити запити → lifespan shutdown у зворотному порядку → вихід до SIGKILL.
