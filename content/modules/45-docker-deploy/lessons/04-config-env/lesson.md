# Конфігурація через змінні середовища

Той самий образ запускають локально, у CI, на staging і в production. Відрізняються лише **налаштування**: адреса бази, рівень логів, секретні ключі, режим налагодження. Якщо налаштування вписані в код чи в образ, для кожного середовища потрібен окремий образ — і production отримує не той образ, що пройшов тести. Тому налаштування передають ззовні, у **змінних середовища**.

> [!NOTE]
> Методологія **The Twelve-Factor App** формулює це так: конфіг — усе, що відрізняється між деплоями, — зберігається в середовищі, а не в коді. Перевірка проста: чи можна прямо зараз відкрити код публічно, не розкривши жодного пароля?

## Що таке змінна середовища

Кожен процес отримує від того, хто його запустив, набір пар `НАЗВА=значення`. У Python вони в `os.environ` — це відображення **рядок → рядок**:

```python
import os

os.environ["NEWS_API_URL"]                  # KeyError, якщо змінної немає
os.environ.get("NEWS_PAGE_SIZE", "20")      # значення або запасне
os.getenv("NEWS_PAGE_SIZE", "20")           # те саме коротше
```

Звідки змінні беруться:

| Де запускаєш | Як задати |
|---|---|
| PowerShell | `$env:LOG_LEVEL = "DEBUG"`, потім команда |
| Git Bash / Linux | `LOG_LEVEL=DEBUG fastapi run main.py` |
| Docker | `docker run -e LOG_LEVEL=DEBUG …` або `--env-file .env` |
| Compose | `environment:` або `env_file:` (наступний урок) |
| GitHub Actions | `env:` кроку, значення з `vars` і `secrets` |
| Хмарна платформа | налаштування сервісу в її консолі; секрети — у її сховищі секретів |

## Усе — рядки

Змінні середовища не мають типів. Порт `"8000"` — рядок, і `"8000" + 1` — помилка. Найпідступніше з логічними значеннями:

```python
os.environ["NEWS_DEBUG"] = "false"
bool(os.environ["NEWS_DEBUG"])     # True — бо рядок непорожній!
```

Тому значення **розбирають і перевіряють**: числа — з межами, логічні — з явного списку слів (`true / false`, `1 / 0`, `yes / no`, `on / off`), списки — через кому з обрізанням пробілів. Невідоме слово — помилка, а не мовчазне `False`.

## Fail fast: перевіряти на старті

Погана змінна має зупинити застосунок **на старті**, а не через годину, коли користувач уперше відкриє сторінку, що її читає. І краще повідомити **всі** проблеми разом: інакше людина виправляє одну змінну, перезапускає, бачить наступну — і так п'ять деплоїв поспіль. Контейнер, що не стартував, одразу видно в `docker ps -a` і в логах.

## pydantic-settings: те саме бібліотекою

У FastAPI-проєктах (модуль про FastAPI) розбором займається `pydantic-settings`: оголошуєш поля з типами, а він читає змінні, перетворює типи й збирає всі помилки валідації.

```python
from pydantic_settings import BaseSettings


class NewsSettings(BaseSettings):
    news_api_url: str              # обов'язкова: NEWS_API_URL
    page_size: int = 20            # PAGE_SIZE → int, "abc" — помилка
    debug: bool = False            # "false", "0", "no", "off" → False


settings = NewsSettings()          # ValidationError на старті, якщо щось не так
```

Розуміти, що відбувається всередині, все одно треба: для Django, скриптів і воркерів часто пишуть невеликий власний завантажувач — як у задачі цього уроку.

## DATABASE_URL

Платформи й інструменти передають базу однією змінною у форматі URL:

```text
postgresql://news:s3cret@db.internal:5432/newsroom?sslmode=require
└─схема─┘   └кор.┘└пароль┘└───хост────┘└порт┘└─база──┘└─параметри─┘
```

Спецсимволи в паролі (`@`, `/`, `:`, `#`) ламають розбір, тому їх **кодують** через `%`: `@` → `%40`, `/` → `%2F`. Пароль `p@ss/word` в адресі виглядає як `p%40ss%2Fword`. Розбирати таку адресу треба стандартним `urllib.parse.urlsplit`, а закодовані частини — повертати через `unquote`.

## Django: налаштування зі змінних

`settings.py` — звичайний Python-модуль, тож читати змінні можна прямо в ньому:

```python
import os

SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]         # без запасного значення: немає — не стартуємо
DEBUG = os.environ.get("DJANGO_DEBUG", "") == "1"
ALLOWED_HOSTS = [h.strip() for h in os.environ.get("DJANGO_ALLOWED_HOSTS", "").split(",") if h.strip()]
```

Для production важливо, щоб безпечне значення було **за замовчуванням**: забута змінна має дати `DEBUG = False`, а не відкритий режим налагодження з трасуваннями помилок для всіх відвідувачів.

## `.env` і `.env.example`

Для локальної розробки змінні тримають у файлі `.env` — його читають compose, `docker run --env-file` і бібліотеки на зразок `python-dotenv` / `pydantic-settings`. Правила:

- `.env` — у `.gitignore` і `.dockerignore`; він лише на твоєму комп'ютері;
- `.env.example` — у репозиторії: усі назви змінних з безпечними прикладами чи порожніми значеннями — документація для нових людей у команді;
- у production `.env`-файлів зазвичай немає: значення дає платформа.

> [!QA]
> Конфіг — частина поведінки, і її тестують: «без `DATABASE_URL` застосунок не стартує і пише, чого бракує», «`DEBUG=false` справді вимикає налагодження». Такі тести не потребують ні Docker, ні бази — функції завантаження налаштувань передають словник замість `os.environ`.

## Типові помилки

- `bool(os.environ["DEBUG"])` — `"false"` стає `True`.
- Небезпечне значення за замовчуванням: `DEBUG=True`, тестовий `SECRET_KEY`.
- Пароль зі `@` не закодовано в `DATABASE_URL` — хост розбирається неправильно.
- `.env` закомічено — пароль назавжди в історії git.
- Помилка конфігу з'являється не на старті, а в рідкісному запиті.

## Підсумок

- Конфіг, що відрізняється між середовищами, — у змінних середовища; образ один.
- `os.environ` — рядки: числа, логічні значення й списки треба розбирати й перевіряти.
- Перевіряй усе на старті й показуй усі проблеми разом (fail fast).
- `DATABASE_URL` — одна змінна для бази; спецсимволи в паролі кодуються через `%`.
- `.env` — лише локально й поза git; `.env.example` — документація в репозиторії.
