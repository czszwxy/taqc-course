# Тестування переходів станів

Багато об'єктів у системах мають **стани**: замовлення (нове → оплачене → відправлене), акаунт (активний → заблокований), підписка, тікет у Jira. Поведінка залежить від **поточного стану**: кнопка «Скасувати» працює для нового замовлення, але не для доставленого. **State transition testing** перевіряє саме це.

## Складові

| Поняття | Що це | Приклад |
|---|---|---|
| **Стан** (state) | у якому положенні об'єкт | `Paid` |
| **Подія** (event) | що відбувається | «натиснути Ship» |
| **Перехід** (transition) | зміна стану через подію | `Paid --Ship--> Shipped` |
| **Дія** (action) | що система робить при переході | надіслати лист з трек-номером |
| **Умова** (guard) | коли перехід дозволено | «Скасувати можна протягом 30 хвилин» |

## Діаграма станів

Замовлення в інтернет-магазині:

```text
            Pay              Ship             Deliver
   [New] ─────────▶ [Paid] ─────────▶ [Shipped] ─────────▶ [Delivered]
     │                │
     │ Cancel         │ Cancel (+ refund)
     ▼                ▼
          [Cancelled]
```

## Таблиця переходів

Діаграма показує **дозволені** переходи. Таблиця змушує подумати про **кожну** пару «стан × подія», зокрема про недозволені:

| Стан \ Подія | Pay | Ship | Deliver | Cancel |
|---|---|---|---|---|
| **New** | Paid | ❌ | ❌ | Cancelled |
| **Paid** | ❌ | Shipped | ❌ | Cancelled |
| **Shipped** | ❌ | ❌ | Delivered | ❌ |
| **Delivered** | ❌ | ❌ | ❌ | ❌ |
| **Cancelled** | ❌ | ❌ | ❌ | ❌ |

❌ — **невалідний перехід**: система має відхилити подію (кнопка недоступна, API повертає помилку) і **не змінити** стан.

> [!QA]
> Невалідні переходи — золота жила для багів: «скасувати вже відправлене замовлення», «оплатити двічі», «доставити неоплачене». У UI кнопки можуть бути сховані, але через API або подвійний клік перехід усе одно стається. Перевіряй невалідні переходи не лише через інтерфейс.

## Як отримати тести

**1. Покриття всіх станів** — пройти шлях, який відвідує кожен стан (найслабкіший рівень).

**2. Покриття всіх валідних переходів** (0-switch coverage) — кожен дозволений перехід хоча б раз:

| # | Тест |
|---|---|
| 1 | New → Pay → **Paid** |
| 2 | Paid → Ship → **Shipped** |
| 3 | Shipped → Deliver → **Delivered** |
| 4 | New → Cancel → **Cancelled** |
| 5 | Paid → Cancel → **Cancelled** (+ повернення коштів) |

Кілька переходів можна пройти **одним** наскрізним тестом (1 → 2 → 3).

**3. Невалідні переходи** — вибрані ❌ з таблиці, особливо ризикові: Cancel для Shipped, Pay для Paid (подвійна оплата), Ship для New.

> [!TIP]
> Не забувай перевіряти **дії** при переходах: чи надіслано лист, чи повернуто гроші, чи змінилась кількість товару на складі. Стан може змінитися правильно, а дія — не виконатися.

## Де шукати стани

- статуси сутностей у базі (`status`, `state`);
- кнопки, які з'являються чи зникають залежно від ситуації;
- workflow у Jira чи трекері;
- вимоги зі словами «після», «до того як», «лише якщо», «більше не може».

## Підсумок

- Стан + подія → перехід (+ дія, + умова).
- Діаграма показує дозволене, таблиця — **всі** пари «стан × подія».
- Тестуй усі валідні переходи і найризиковіші невалідні.
- Перевіряй не лише новий стан, а й дії: листи, гроші, склад.
