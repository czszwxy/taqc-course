# Тестування на основі use case і сценаріїв

EP, BVA і таблиці рішень перевіряють окремі поля та правила. Але користувач не «заповнює поле Quantity» — він **купує товар**. **Use case testing** перевіряє наскрізні сценарії: як користувач досягає мети від початку до кінця.

## Що таке use case

**Use case** (варіант використання) — опис взаємодії **актора** (користувача чи іншої системи) із системою для досягнення **мети**.

| Частина | Приклад: «Зняти готівку в банкоматі» |
|---|---|
| **Актор** | власник картки |
| **Мета** | отримати готівку |
| **Передумови** | банкомат працює, картка активна |
| **Основний потік** (main / happy path) | вставити картку → ввести PIN → обрати суму → отримати гроші → забрати картку |
| **Альтернативні потоки** | обрати іншу суму вручну; надрукувати чек |
| **Виняткові потоки** (exceptions) | неправильний PIN; недостатньо коштів; у банкоматі немає купюр; 3 неправильні PIN → картку заблоковано |
| **Постумови** | баланс зменшено на зняту суму, транзакцію записано |

## Як отримати тести

1. **Один тест на основний потік** — найважливіший, зазвичай входить у smoke.
2. **Тест на кожен альтернативний потік** — інший шлях до тієї ж мети.
3. **Тест на кожен винятковий потік** — шлях, де мети не досягнуто, але система має повестися коректно: зрозуміле повідомлення, жодних втрат даних чи грошей.
4. **Перевір постумови** — не лише «гроші видано», а й «баланс зменшено», «транзакція в історії».

> [!QA]
> Найцінніші баги ховаються у **виняткових** потоках: що станеться, якщо оплата впала посередині? Чи не списали гроші двічі? Чи повернувся товар на склад? Розробники часто ретельно роблять happy path і поспіхом — винятки.

## Сценарії з user stories

В Agile замість формальних use cases часто є user stories з acceptance criteria. Ті самі ідеї працюють і тут: кожна історія має «щасливий» сценарій і набір альтернатив та винятків. Корисно складати **сценарій-подорож** (user journey) з кількох історій: «зареєструватися → знайти товар → додати в кошик → застосувати промокод → оплатити → отримати лист».

## Use case і інші техніки

Use case показує **шлях**, а на кожному кроці шляху працюють інші техніки:

- «обрати суму» → EP і BVA для суми;
- «ввести PIN» → переходи станів (3 спроби → блокування);
- «знижка» → таблиця рішень.

> [!TIP]
> Пиши наскрізні сценарії з погляду **реальних цілей** користувачів, а не функцій системи. «Подарувати книгу другові з доставкою на його адресу» знайде більше проблем, ніж «перевірити поле адреси».

## Підсумок

- Use case: актор, мета, передумови, основний, альтернативні й виняткові потоки, постумови.
- Тести: основний потік + кожен альтернативний + кожен винятковий + перевірка постумов.
- Найбільше багів — у виняткових потоках.
- На окремих кроках сценарію застосовуй EP, BVA, таблиці рішень, переходи станів.
