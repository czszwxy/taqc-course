# Навіщо потрібен тест-дизайн

Пам'ятаєш принцип «вичерпне тестування неможливе»? Поле «вік» приймає тисячі значень, форма реєстрації — мільярди комбінацій. **Тест-дизайн** (test design) — це вміння вибрати з цього океану **невеликий набір тестів, який знайде більшість багів**.

## Без технік і з техніками

Уяви поле **Quantity**: цілі числа від 1 до 99.

**Без технік**: тестувальник вводить 5, 10, 50, 77… Усі проходять, бо всі з середини діапазону. Баг `quantity > 1` замість `>= 1` залишається непоміченим.

**З техніками**:

- **класи еквівалентності**: < 1 (невалідні), 1–99 (валідні), > 99 (невалідні) → 3 тести;
- **граничні значення**: 0, 1, 99, 100 → ще 4 тести, саме там, де ховаються помилки `>` / `>=`.

Сім продуманих тестів знаходять більше, ніж п'ятдесят випадкових.

> [!QA]
> Техніки тест-дизайну — це не бюрократія, а **аргумент**. Коли тебе питають «чому ти перевірив саме ці значення?», відповідь «за класами еквівалентності й граничними значеннями» звучить професійно, а покриття можна пояснити й перевірити.

## Огляд технік

| Група | Техніка | Коли використовувати |
|---|---|---|
| **Black box** | Equivalence partitioning (класи еквівалентності) | вхідні дані можна поділити на групи, які обробляються однаково |
| | Boundary value analysis (граничні значення) | є діапазони, мінімуми й максимуми, довжини |
| | Decision tables (таблиці рішень) | результат залежить від **комбінації** кількох умов |
| | State transition (переходи станів) | система має стани і події, що їх змінюють: замовлення, акаунт, підписка |
| | Pairwise (попарне тестування) | багато параметрів з кількома значеннями (браузер × ОС × мова) |
| | Use case / scenario testing | треба перевірити наскрізні сценарії користувача |
| **White box** | Statement / branch coverage | є доступ до коду (розробники, unit-тести) |
| **Experience-based** | Error guessing, exploratory, checklists | доповнюють формальні техніки досвідом |

Техніки **комбінують**: EP + BVA для полів, таблиця рішень для бізнес-правил, переходи станів для статусів, error guessing для «дивних» даних.

## Процес: від вимоги до тест-кейсу

1. **Проаналізувати вимогу**: які входи, правила, стани, ролі?
2. **Визначити умови тестування** (test conditions): що саме треба перевірити.
3. **Обрати техніку** під кожну умову.
4. **Отримати тест-кейси**: конкретні вхідні дані + очікуваний результат.
5. **Пріоритезувати** й доповнити досвідом (error guessing).

Приклад для вимоги *«Знижка 10% для замовлень від 1000 грн, якщо користувач зареєстрований»*:

| Крок | Результат |
|---|---|
| Умови | сума замовлення; чи зареєстрований користувач |
| Техніки | BVA для суми (999 / 1000), таблиця рішень для комбінації «сума × реєстрація» |
| Тести | 1000 грн + зареєстрований → знижка; 999 + зареєстрований → без знижки; 1000 + гість → без знижки; … |

> [!TIP]
> Записуй, **яку техніку** ти застосував і **чому**. Наприклад: «граничні значення 999/1000 за BVA». Це допомагає під час рев'ю тест-кейсів і на співбесідах.

## Покриття

Кожна техніка дає свою **міру покриття**: скільки класів, меж, правил таблиці чи переходів перевірено. Це чесніша метрика, ніж «написали 200 тест-кейсів»: 200 тестів з одного класу еквівалентності покривають менше, ніж 7 продуманих.

## Підсумок

- Тест-дизайн — вибір малого набору тестів, що знаходить максимум багів.
- Основні black-box техніки: EP, BVA, таблиці рішень, переходи станів, pairwise, use cases.
- Процес: вимога → умови тестування → техніка → тест-кейси → пріоритети.
- Техніки комбінують між собою й доповнюють досвідом.
