# Flaky-тести і підтримка набору

Автотести — не «написав і забув». Продукт змінюється щодня, і набір, який не доглядають, за кілька місяців стає червоним «за звичкою». Тоді його перестають слухати. У модулі 15 ти дізнався, що таке flaky-тест. Тепер про системну роботу з ним на CI.

## Як помітити flaky-тест

- **Статус flaky у звіті**: тест упав, але пройшов з повтору (`retries` на CI).
- **Історія**: той самий тест то зелений, то червоний на однаковому коді в різних прогонах.
- **Стрес-прогін**: `npx playwright test search.spec.ts --repeat-each=30 --workers=4`. Паралельність теж виявляє гонки й спільні дані.

## Як розібратися

1. Відкрий **trace** впалої спроби: що відбувалося на кроці падіння? Чи прийшла відповідь сервера? Чи був елемент перекритий?
2. Порівняй з успішною спробою: різниця зазвичай у **часі** або **даних**.
3. Знайди причину з таблиці модуля 15: пауза, гонка, `textContent()` замість web-first перевірки, залежність від порядку, спільні дані, нестабільний локатор, зовнішній сервіс.
4. Виправ причину і перевір: `--repeat-each=30` зелений.

> [!WARNING]
> Збільшити `retries`, `timeout` або додати `waitForTimeout` — не виправлення. Так нестабільність ховають, і через місяць вона повернеться разом зі справжнім багом, який теж «пройде з третьої спроби».

## Карантин

Якщо виправлення потребує часу, flaky-тест **тимчасово** виводять з воріт CI, щоб він не блокував усіх, але **не забувають**:

```ts
test('search counter matches the cards', { tag: '@quarantine', annotation: { type: 'issue', description: 'QA-512' } }, async ({ page }) => {
  // …
});
```

```bash
npx playwright test --grep-invert @quarantine     # основний прогін без карантину
npx playwright test --grep @quarantine            # окремий нічний прогін карантину
```

Правила карантину: кожен тест у ньому має задачу і власника, а сам карантин має ліміт (наприклад, 2 тижні). Порожній карантин — ціль.

## Метрики стабільності

| Метрика | Навіщо |
|---|---|
| частка зелених прогонів `main` | чи можна довіряти CI |
| кількість flaky за тиждень | чи росте нестабільність |
| час прогону PR-набору | чи не гальмує команду |
| час від падіння до розбору | чи хтось реагує |

## Підтримка набору

- **Власник падінь**: хтось щодня (часто по черзі) розбирає червоні прогони.
- **Видаляй застарілі тести**: функцію прибрали — тест теж. Тест, що нічого не ловить роками, — кандидат на перегляд.
- **Зміна UI** виправляється в Page Object, а не в 30 тестах (модуль 16).
- **Рев'ю тестів** і ті самі стандарти, що й для продукту: без пауз, без `force`, з web-first перевірками.
- **Оновлення Playwright** регулярно, разом з браузерами (`npm install -D @playwright/test@latest`, `npx playwright install`). Спершу в окремому PR з повним прогоном.
- **Дані**: прибирання, унікальні значення, жодних спільних змінюваних записів.

> [!QA]
> Хороший тест-набір — як хороший газон: його не «садять раз», а доглядають щотижня. На співбесіді питання «що ти робиш з flaky-тестами?» перевіряє саме це. Найкраща відповідь: виявити → розібрати trace → виправити причину або в карантин із задачею → стежити за метриками.

## Підсумок

- Flaky видно за статусом flaky (retries), історією прогонів і стрес-прогоном `--repeat-each`.
- Розбір: trace впалої і успішної спроби → причина → виправлення → повторний стрес-прогін.
- Більші retries, timeout і паузи ховають проблему, а не виправляють її.
- Карантин: тег `@quarantine`, задача, власник, ліміт часу. Основний прогін — `--grep-invert @quarantine`.
- Підтримка: власник падінь, видалення застарілого, Page Objects, рев'ю, оновлення Playwright, метрики.
