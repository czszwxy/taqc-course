# Концепції CI/CD

Автотести мало користі приносять, якщо їх запускають «коли згадаємо» на ноутбуці тестувальника. Справжня цінність з'являється, коли вони запускаються **автоматично на кожну зміну** і можуть **зупинити** погану зміну. Для цього існує CI/CD.

## Три терміни

| Термін | Що означає |
|---|---|
| **Continuous Integration (CI)** | кожна зміна (push, pull request) автоматично збирається і перевіряється тестами. Зміни часто вливаються в `main` маленькими порціями |
| **Continuous Delivery** | після CI зміна автоматично готова до релізу: задеплоєна на тестове середовище, перевірена. Реліз у продакшн — **кнопкою** людини |
| **Continuous Deployment** | те саме, але реліз у продакшн відбувається **автоматично**, якщо всі перевірки зелені |

## Конвеєр (pipeline)

```text
push / PR
   │
   ▼
[build] → [lint + unit] → [API + UI smoke] → (merge) → [deploy staging] → [e2e regression] → [release] → [prod smoke]
            хвилини          5–10 хв                                        30+ хв або вночі         1–2 хв
```

Кожен етап — **quality gate**: якщо він червоний, далі зміна не йде. Тому порядок такий: швидкі й дешеві перевірки спочатку, повільні й дорогі потім.

## Які тести де

| Коли | Що запускати | Чому |
|---|---|---|
| кожен pull request | lint, unit, API, **UI smoke** (`@smoke`) | фідбек за хвилини, поки розробник пам'ятає зміну |
| після злиття в main / деплою на staging | повніший набір UI і API | перевірка інтегрованої системи |
| щоночі (schedule) | повна регресія, кілька браузерів, візуальні тести | довго, але не блокує роботу вдень |
| після релізу в prod | короткий prod smoke (лише читання!) | переконатися, що реліз живий |

> [!QA]
> Швидкість фідбеку — головна метрика CI. Тест, що повідомляє про баг через 5 хвилин після push, вартий значно більше, ніж той самий тест, що знайде баг через тиждень. Тому набір ділять тегами (`@smoke`, `@regression`) і запускають різні частини в різні моменти.

## Правила здорового CI

- **Червоний CI — пріоритет №1**: поки `main` червоний, нові зміни не вливаються.
- **Тести мають право зупинити злиття**. Інакше це не quality gate, а прикраса.
- **Нестабільні тести — ворог CI**: якщо червоний статус буває «просто так», команда перестає йому вірити (урок 4).
- **Відтворюваність**: CI запускає тести в чистому середовищі з точними версіями (`npm ci`, lock-файл).

## Роль QA Automation у CI

- додати автотести в конвеєр і підтримувати їх зеленими;
- налаштувати, які набори де запускаються;
- розбирати падіння: баг продукту → баг-репорт; баг тесту → виправити; середовище → повідомити DevOps;
- стежити за швидкістю й стабільністю набору.

## Підсумок

- CI автоматично перевіряє кожну зміну. Continuous Delivery готує реліз, людина натискає кнопку. Continuous Deployment релізить автоматично.
- Pipeline — це етапи-ворота: швидкі перевірки спочатку, повільні потім.
- На PR запускають smoke, після деплою — ширший набір, щоночі — повну регресію, після релізу — prod smoke.
- Червоний `main` — пріоритет. Тести мають право блокувати. Flaky-тести руйнують довіру.
