# AI-асистенти в роботі тестувальника

AI-асистенти (чат-моделі, помічники в IDE, агенти, що самі керують браузером) стали звичайним робочим інструментом. Вони пишуть чернетку тесту за хвилину — і так само за хвилину можуть написати тест, який **виглядає** правильно, але нічого не перевіряє. Цінність тестувальника зміщується: менше набирати код, більше **ставити задачу** і **перевіряти результат**.

> [!QA]
> AI — це дуже швидкий стажер, який ніколи не бачив твого застосунку. Він знає синтаксис pytest і Playwright краще за тебе, але не знає, що кнопка називається «Sign in», а не «Login», і що за вимогою товарів має бути 10, а не 12. Відповідальність за тест — твоя.

## Де AI допомагає

| Задача | Приклад |
|---|---|
| Ідеї для тестів | «які негативні сценарії для форми скидання пароля я пропустив(ла)?» |
| Тестові дані | 20 варіантів невалідних email, імена різними алфавітами — готовий список для `parametrize` |
| Чернетка коду | page object за фрагментом розмітки, фікстура, параметризація |
| Пояснення помилок | traceback pytest, незрозуміле повідомлення pydantic |
| Рев'ю | «що слабкого в цьому тесті?» |
| Рутина | перетворити чекліст на заготовки тестів, скласти README |

## Де AI помиляється

| Помилка | Як виглядає | Чому |
|---|---|---|
| Вигадані локатори | `page.locator("#login-button")`, якого немає | він не бачив сторінку |
| Вигадані очікування | `to_have_text("12 products found")` | він не знає вимог і даних |
| Слабкі перевірки | `assert count > 0`, `assert first` | «безпечно» проходить завжди |
| Паузи | `time.sleep(3)`, `page.wait_for_timeout(3000)` | у навчальних даних багато старого коду |
| Застарілий або неіснуючий API | методи з інших бібліотек, версій чи з Playwright для JavaScript (`expect.poll` у Python немає) | впевнене «доповнення» прогалин |
| Тест, підігнаний під баг | перевіряє те, що система робить зараз | він бачить поведінку, а не вимогу |

Останнє — найпідступніше: якщо попросити «напиши тести для цієї сторінки» і дати лише сторінку, AI зафіксує **поточну** поведінку — разом з її дефектами.

## Контекст вирішує все

Якість відповіді майже повністю залежить від того, що ти дав(ла) на вході:

| Що дати | Навіщо |
|---|---|
| вимоги (правила, межі, тексти повідомлень) | звідки брати очікувані результати |
| справжню структуру сторінки (aria-снапшот, фрагмент HTML) | щоб локатори існували |
| приклад твого тесту, фікстури або page object | щоб стиль збігся з фреймворком |
| правила проєкту | «лише get_by_role / get_by_label, без time.sleep, один тест — одна поведінка» |
| версії й формат | «Python 3.13, pytest + pytest-playwright, sync API; один файл, без пояснень» |

## Розбір: слабкий і сильний запит

| | Запит | Результат |
|---|---|---|
| Слабкий | «Напиши тести Playwright для сторінки реєстрації» | вигадані поля, загальні перевірки, іноді взагалі JavaScript |
| Сильний | роль + вимоги + aria-снапшот форми + правила + версії й формат | тести з реальними локаторами й очікуваннями з вимог |

Каркас сильного запиту:

```text
Ти — QA automation engineer. Напиши тести Playwright для Python (pytest + pytest-playwright,
sync API) для форми реєстрації.

Вимоги:
- Ім'я: 2–50 символів …
- Вік: 18–120 включно …
- Повідомлення про помилки: "…"

Структура сторінки (aria snapshot):
- textbox "Full name"
- spinbutton "Age"
- button "Create account"

Правила: лише get_by_role / get_by_label; web-first перевірки expect; без time.sleep
і wait_for_timeout; межі — через pytest.mark.parametrize; один тест — одна поведінка.
Формат: один файл test_signup.py, без пояснень.
```

## Чекліст рев'ю згенерованого тесту

1. **Запусти.** Тест, який не запускався, — це текст, а не тест.
2. **Локатори існують** і стійкі (роль, підпис, test id — не довгий CSS).
3. **Очікування взяті з вимог**, а не з голови AI чи з поточної поведінки.
4. **Перевірки точні**: конкретний текст, кількість, статус — не `assert value`.
5. **Немає пауз** і разових перевірок без очікування.
6. **Тест може впасти**: зламай очікування або умову — він має почервоніти.
7. **Незалежність і дані**: тест сам готує й прибирає своє (фікстура з `yield`).
8. **Немає секретів** і зайвих залежностей у `requirements.txt`.

## Приватність і безпека

- Ніколи не вставляй у зовнішній сервіс **секрети**: паролі, токени, ключі, файл `.env`.
- Персональні дані клієнтів, логи й дампи з продакшну — лише після **знеособлення** або взагалі ні.
- Код і документи компанії — за її правилами: з'ясуй, які AI-інструменти дозволені.
- Не запускай наосліп команди, які пропонує AI (`pip install` невідомого пакета теж): спершу прочитай, що вони роблять.

## Інструменти Playwright

| Інструмент | Що це |
|---|---|
| **Codegen** | не AI: `playwright codegen <url>` записує твої дії і пропонує справжні локатори сторінки — зокрема у вигляді коду pytest |
| **Playwright MCP** | сервер, через який AI-агент керує справжнім браузером і бачить сторінку як дерево доступності — тому не вигадує локатори |
| **Test Agents** | агенти planner / generator / healer для Playwright Test (Node.js): план тестів, генерація з перевіркою локаторів, «лікування» тестів, що впали |

Обережно з автоматичним «лікуванням» будь-яким інструментом: якщо тест упав через справжній баг, «полагоджений» тест цей баг сховає. Зміни, які пропонує агент, читають так само уважно, як код колеги.

## Типові помилки

- Прийняти згенерований тест без запуску й рев'ю, бо «виглядає правильно».
- Просити тести без вимог — отримати фіксацію поточних багів.
- Не вказати мову й версії — отримати тест для JavaScript або для async API.
- Вставити в чат лог з токеном або даними клієнтів.
- Дозволити «самовідновлення» тестів без перегляду змін.
- Перестати вчитися: без власного розуміння неможливо оцінити відповідь AI.

## Підсумок

- AI швидко робить чернетки, ідеї й дані; не знає твого застосунку й вимог.
- Типові вади: вигадані локатори й очікування, слабкі перевірки, паузи, API з іншої мови.
- Сильний запит = роль + вимоги + реальна структура сторінки + правила + версії й формат.
- Кожен згенерований тест: запустити, перевірити локатори й очікування, переконатися, що він здатен упасти.
- Секрети й персональні дані — ніколи в запит; правила компанії — понад усе.
