# Основи performance-тестування

Функціональний тест відповідає на питання «чи працює?». Performance-тест — «чи працює **достатньо швидко** і **під навантаженням**?». Сайт, який у «чорну п'ятницю» відповідає 20 секунд або падає, для бізнесу зламаний, хоч усі функціональні тести зелені. Окремого performance-інженера є не в кожній команді, тож базові речі часто лягають на QA.

> [!QA]
> Від автоматизатора не чекають тюнінгу серверів. Чекають трьох речей: розуміти терміни (p95, throughput, LCP), вміти прочитати звіт навантажувального тесту і помітити деградацію раніше за користувачів.

## Види тестів

| Тест | Навантаження | Питання |
|---|---|---|
| **Load** | очікуване: «звичайний робочий день» | чи вкладаємось у вимоги за нормальних умов? |
| **Stress** | вище за очікуване, росте, доки не зламається | де межа і **як** система ламається й відновлюється? |
| **Spike** | різкий стрибок за секунди | чи переживемо розсилку або рекламу на ТБ? |
| **Soak** (endurance) | звичайне, але **годинами** | чи немає витоків пам'яті, чи не росте час відповіді? |

## Метрики

| Метрика | Що означає |
|---|---|
| Response time | час від запиту до відповіді |
| Throughput | запитів за секунду (RPS), які система обробляє |
| Error rate | частка невдалих запитів |
| Users (віртуальні користувачі) | скільки «користувачів» одночасно імітує тест |

## Розбір: чому середнє бреше

Десять запитів: дев'ять по 100 мс і один — 2000 мс.

| Показник | Значення | Що «каже» |
|---|---|---|
| Середнє (avg) | (9 × 100 + 2000) / 10 = **290 мс** | «усе добре» |
| Медіана (p50) | **100 мс** | половина запитів не повільніша за 100 мс |
| p90 | **100 мс** | 90 % запитів не повільніші за 100 мс |
| p95 | **2000 мс** | 95 % запитів не повільніші за 2000 мс — тобто хтось чекає 2 секунди |
| Максимум | 2000 мс | найгірший випадок |

**Перцентиль pN** — значення, не повільнішими за яке є N % запитів. Простий спосіб порахувати (метод найближчого рангу): відсортувати за зростанням і взяти елемент з номером «N % від кількості, округлене **вгору**». Для p95 з 10 значень: 9.5 → **10** — десяте, найбільше.

Середнє ховає повільні запити, а саме їх помічають користувачі. Тому вимоги пишуть у перцентилях: «**p95 < 500 мс**, помилок **< 1 %**».

## Locust: навантаження як код на Python

**Locust** — інструмент навантажувального тестування, де сценарій — це звичайний клас Python. Файл `locustfile.py`:

```python
from locust import HttpUser, between, task


class Shopper(HttpUser):
    wait_time = between(1, 3)

    @task(3)
    def browse_products(self):
        self.client.get("/api/products")

    @task(1)
    def open_product(self):
        self.client.get("/api/products/7", name="/api/products/[id]")
```

| Рядок | Значення |
|---|---|
| `class Shopper(HttpUser)` | один віртуальний користувач; Locust створює їх стільки, скільки скажеш |
| `wait_time = between(1, 3)` | «думає» 1–3 секунди між діями, як людина |
| `@task(3)` / `@task(1)` | вага: перегляд каталогу втричі частіший за відкриття товару |
| `self.client.get(...)` | HTTP-запит (клієнт схожий на `requests`); час і статус записуються в статистику |
| `name="/api/products/[id]"` | різні id в одному рядку статистики, а не сотня окремих |

Запуск `locust` відкриває вебінтерфейс (за замовчуванням http://localhost:8089) з графіками. Для CI — без інтерфейсу:

```bash
locust -f locustfile.py --headless -u 20 -r 5 --run-time 1m -H https://staging.example.test
```

| Опція | Значення |
|---|---|
| `--headless` | без вебінтерфейсу, статистика — у термінал |
| `-u 20` | 20 користувачів одночасно |
| `-r 5` | додавати по 5 користувачів за секунду |
| `--run-time 1m` | тривалість тесту |
| `-H` | адреса системи під тестом |

## Пороги: тест, що сам проходить або падає

Щоб CI ставав червоним, коли вимогу порушено, у `locustfile.py` додають обробник події завершення і задають код виходу процесу:

```python
from locust import events


@events.quitting.add_listener
def check_slo(environment, **kwargs):
    total = environment.stats.total
    too_many_errors = total.fail_ratio > 0.01
    too_slow = total.get_response_time_percentile(0.95) > 500
    environment.process_exit_code = 1 if too_many_errors or too_slow else 0
```

| Вираз | Значення |
|---|---|
| `environment.stats.total` | підсумок за всіма запитами |
| `fail_ratio > 0.01` | помилок більше 1 % |
| `get_response_time_percentile(0.95) > 500` | p95 повільніший за 500 мс (перцентиль задають часткою: 0.95) |
| `process_exit_code = 1` | Locust завершиться з кодом 1 — крок CI червоний |

Пороги перетворюють «подивимось на графік» на автоматичну перевірку «пройшов / не пройшов».

## Швидкість у браузері: Core Web Vitals

| Метрика | Що вимірює | «Добре» |
|---|---|---|
| **LCP** — Largest Contentful Paint | коли з'явився головний вміст | ≤ 2.5 с |
| **INP** — Interaction to Next Paint | як швидко сторінка реагує на дії | ≤ 200 мс |
| **CLS** — Cumulative Layout Shift | наскільки «стрибає» верстка | ≤ 0.1 |

Оцінюють за 75-м перцентилем відвідувань. **Lighthouse** (вкладка в Chrome DevTools) вимірює сторінку в лабораторних умовах; INP він не міряє — дій користувача там немає. **Лабораторні** дані зручні для порівняння «до / після», **польові** (від справжніх користувачів) показують реальність.

## Що може зробити QA вже зараз

- Додати в чекліст релізу: Lighthouse для ключових сторінок, порівняння з минулим релізом.
- Дивитися час відповідей у вкладці Network і в логах API-тестів; різке зростання — привід для бага.
- Запускати короткий сценарій Locust (smoke: кілька користувачів, хвилина) у CI для головних ендпоінтів.
- Писати вимоги до швидкості вимірювано: «p95 < 500 мс при 50 RPS», а не «швидко».

> [!WARNING]
> Навантажувальні тести запускають **лише** на середовищах, де це дозволено: власний staging або спеціальний стенд. Навантаження на продакшн чи чужий сайт без дозволу — це фактично атака, навіть якщо ти «просто тестував(ла)».

## Типові помилки

- Вимога «сайт має працювати швидко» — її неможливо перевірити.
- Висновок за середнім часом: 5 % користувачів чекають по 5 секунд, а «середнє 300 мс».
- Тест на ноутбуці через Wi-Fi: вимірюється мережа тестувальника, а не сервер.
- Жорсткі перевірки часу у функціональних UI-тестах (`assert duration < 0.2`) — нестабільність без користі.
- Тестові дані «з трьох товарів»: реальна база з мільйоном записів поводиться інакше.
- Сценарій Locust без `wait_time`: кожен «користувач» шле запити без пауз, і 20 користувачів дають навантаження, як сотні людей.

## Підсумок

- Load, stress, spike, soak — різне навантаження, різні питання.
- Метрики: час відповіді в перцентилях (p95, p99), throughput, error rate.
- Середнє ховає повільні запити; вимоги формулюй як пороги.
- Locust: клас `HttpUser`, `@task`, `wait_time`; у CI — `--headless -u -r --run-time`, пороги — через `process_exit_code`.
- Фронтенд: LCP ≤ 2.5 с, INP ≤ 200 мс, CLS ≤ 0.1; Lighthouse — лабораторні дані.
- Навантажуй лише дозволені середовища.
