# Віртуальні оточення, pip і структура проєкту

Досі Python працював прямо в браузері. З модуля pytest ти запускатимеш тести на своєму комп'ютері — і тут з'являються питання, які на співбесіді ставлять кожному автоматизатору: «Як ти налаштовуєш проєкт? Як колега запустить твої тести?»

## Встановити Python

1. Завантаж інсталятор з python.org (розділ Downloads).
2. На Windows **обов'язково** познач **Add python.exe to PATH** на першому екрані інсталятора.
3. Перевір у терміналі:

```bash
python --version      # Windows також: py --version
```

## Навіщо віртуальне оточення

Пакети (pytest, requests, Playwright) встановлюються в Python. Якщо ставити все «глобально», два проєкти з різними версіями pytest почнуть заважати один одному. **Віртуальне оточення** (venv) — окрема папка з власним Python і власними пакетами для **одного** проєкту.

```bash
python -m venv .venv
```

Команда створює папку `.venv` у проєкті. Далі її **активують** — тоді `python` і `pip` у цьому терміналі беруться з оточення:

| Система | Команда активації |
|---|---|
| Windows, PowerShell | `.venv\Scripts\Activate.ps1` |
| Windows, cmd | `.venv\Scripts\activate.bat` |
| macOS / Linux | `source .venv/bin/activate` |

Ознака успіху — `(.venv)` на початку рядка терміналу. Вимкнути — `deactivate`.

> [!NOTE]
> Якщо PowerShell відмовляється запускати скрипт активації, можна обійтися без активації і викликати Python оточення напряму: `.venv\Scripts\python -m pytest`. Про налаштування, яке дозволяє скрипти, розповідає документація модуля venv.

## pip — встановлення пакетів

```bash
python -m pip install pytest requests     # встановити
python -m pip list                        # що встановлено
python -m pip install -U pytest           # оновити
```

`python -m pip` гарантує, що пакет потрапить саме в той Python, який зараз активний, — а не в якийсь інший на комп'ютері.

## requirements.txt

Щоб колега чи CI встановили **ті самі** версії пакетів, їх записують у файл:

```bash
python -m pip freeze > requirements.txt
```

```text
pytest==8.3.4
requests==2.32.3
```

На іншому комп'ютері (після створення й активації свого `.venv`):

```bash
python -m pip install -r requirements.txt
```

Зафіксовані версії (`==`) роблять запуск відтворюваним. Сучасна альтернатива — файл `pyproject.toml`, де описують і залежності, і налаштування інструментів.

## Розбір: колега запускає твій проєкт

| Крок | Команда | Навіщо |
|---|---|---|
| 1 | `git clone <url>` | отримати код (без `.venv` — його немає в git) |
| 2 | `python -m venv .venv` | своє оточення |
| 3 | `.venv\Scripts\Activate.ps1` | увімкнути його |
| 4 | `python -m pip install -r requirements.txt` | ті самі версії пакетів |
| 5 | `python -m pytest` | запустити тести |

Якщо на будь-якому кроці потрібне щось ще (змінні оточення, браузери Playwright) — це має бути написано в README.

## Структура тестового проєкту

```text
gadgetly-tests/
├── .venv/              ← оточення, не в git
├── pages/              ← page objects
│   ├── __init__.py
│   └── login_page.py
├── api/
│   └── client.py       ← API-клієнт
├── data/
│   └── users.json      ← тестові дані (без реальних персональних даних)
├── tests/
│   ├── conftest.py     ← фікстури pytest
│   └── test_login.py
├── .gitignore
├── pytest.ini          ← налаштування pytest (або pyproject.toml)
├── requirements.txt
└── README.md
```

Тести запускай з **кореня** проєкту командою `python -m pytest`: так папка проєкту потрапляє в шлях імпорту, і в тестах працює `from pages.login_page import LoginPage`.

## .gitignore для Python

```text
.venv/
__pycache__/
.pytest_cache/
test-results/
playwright-report/
.env
```

`__pycache__` — скомпільований байткод, який Python створює сам; `.pytest_cache` — службові дані pytest; звіти й скріншоти генеруються при кожному прогоні.

## Секрети

Паролі, токени й ключі API **ніколи** не потрапляють у git — навіть у приватний репозиторій. Їх тримають у файлі `.env` (він у `.gitignore`) або в секретах CI і читають з коду через змінні оточення: `os.environ["API_TOKEN"]`.

> [!QA]
> README з розділом «Як запустити» — обличчя твого портфоліо. Рекрутер чи тімлід клонує репозиторій і пробує запустити тести; якщо за 5 хвилин нічого не вийшло — він закриє вкладку. Перевір інструкцію на «чистій» папці: склонуй репозиторій заново і пройди всі кроки буквально.

## Типові помилки

- `ModuleNotFoundError: No module named 'pytest'` одразу після встановлення — пакет потрапив в інший Python: оточення не активоване, або `pip` і `python` з різних місць. Використовуй `python -m pip`.
- `.venv` у git — тисячі файлів, які до того ж не працюють на іншому комп'ютері.
- `requirements.txt` без версій — через пів року нова версія пакета ламає тести.
- Запуск `pytest` з папки `tests/` — імпорти `from pages...` перестають працювати.
- Токен у коді чи в закоміченому `.env` — його доведеться відкликати, навіть якщо коміт потім видалити.

## Підсумок

- `python -m venv .venv` + активація — окреме оточення для кожного проєкту.
- `python -m pip install ...`; версії — у `requirements.txt` (`pip freeze`), встановлення — `pip install -r`.
- Структура: `pages/`, `api/`, `data/`, `tests/` з `conftest.py`, конфіг pytest, README.
- У `.gitignore`: `.venv/`, `__pycache__/`, `.pytest_cache/`, звіти, `.env`.
- Секрети — у змінних оточення, не в git; README «як запустити» перевір на чистому клоні.
