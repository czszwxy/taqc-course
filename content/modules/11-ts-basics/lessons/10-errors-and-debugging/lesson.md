# Читання помилок і налагодження

Помилки — нормальна частина програмування. Досвідчений інженер відрізняється не тим, що не помиляється, а тим, що **швидко розуміє**, що саме пішло не так. Для тестувальника це подвійно важливо: ти шукатимеш причини падіння автотестів щодня.

## Чотири види помилок

| Вид | Коли виникає | Хто ловить | Приклад |
|---|---|---|---|
| **Синтаксична** | код написано не за правилами мови | компілятор, до запуску | забута `)` або `}` |
| **Помилка типів** | значення не відповідає типу | TypeScript, до запуску | `const n: number = 'five'` |
| **Runtime** | код запустився і «впав» під час виконання | середовище виконання | `undefined.toUpperCase()` |
| **Логічна** | код працює, але результат неправильний | **тести** (і тестувальники!) | `>` замість `>=` |

> [!QA]
> Логічні помилки — це звичайні баги. Компілятор їх не бачить, бо з погляду мови все правильно. Знайти їх можна лише перевіркою **очікуваного** результату проти **фактичного**. Саме це роблять тести.

## Як читати помилку TypeScript

```text
Line 4:9 · TS2322
Type 'string' is not assignable to type 'number'.
```

1. **Де**: рядок 4, символ 9. Почни з цього місця, але дивись і на рядок вище: помилка часто «з'являється» трохи нижче за причину.
2. **Код** `TS2322` за потреби можна загуглити.
3. **Повідомлення** читай буквально: «тип string не можна присвоїти типу number». Отже, зліва очікують число, а справа рядок.

Якщо помилок кілька, виправляй **першу**: інші часто є її наслідками.

### Найчастіші помилки TypeScript

| Код | Повідомлення (скорочено) | Що зазвичай означає |
|---|---|---|
| TS2322 | Type 'X' is not assignable to type 'Y' | значення не того типу |
| TS2304 | Cannot find name 'x' | опечатка або змінну не оголошено |
| TS2552 | Cannot find name 'totl'. Did you mean 'total'? | опечатка, TS підказує правильну назву |
| TS2339 | Property 'x' does not exist on type 'Y' | опечатка у властивості або її немає в типі |
| TS2345 | Argument of type 'X' is not assignable to parameter of type 'Y' | у функцію передано не той тип |
| TS2554 | Expected 2 arguments, but got 1 | неправильна кількість аргументів |
| TS2355 | A function whose declared type is … must return a value | забули `return` |
| TS2588 | Cannot assign to 'x' because it is a constant | перезапис `const` |
| TS7006 | Parameter 'x' implicitly has an 'any' type | не вказано тип параметра |
| TS1005 | ';' expected / ')' expected | синтаксис: щось пропущено |

## Runtime-помилки та stack trace

```text
TypeError: Cannot read properties of undefined (reading 'toUpperCase')
    at getInitials (solution.ts:3:22)
    at test (tests.ts:5:12)
```

- **Тип помилки**: `TypeError` (операція з невідповідним значенням), `ReferenceError` (змінної не існує), `RangeError` (значення поза допустимим діапазоном).
- **Повідомлення**: «не можна прочитати властивість `toUpperCase` у `undefined`». Отже, у тебе `щось.toUpperCase()`, і це «щось» виявилося `undefined`.
- **Stack trace** (стек викликів): ланцюжок функцій від місця падіння догори. Верхній рядок показує, де саме впало.

Найчастіша причина `Cannot read properties of undefined` — звернення до неіснуючого елемента масиву або властивості: `parts[1]`, коли в масиві лише один елемент.

## Техніки налагодження

### 1. Відтвори проблему

Знайди **мінімальний** вхід, на якому помилка проявляється стабільно. Тести в задачах показують цей вхід: `Expected: 2, Received: 1`.

### 2. Подивись на проміжні значення

```ts
function countPassed(results: string): number {
  let count = 0;
  for (let i = 1; i <= results.length; i++) {
    console.log(i, results[i]); // ← тимчасовий вивід
    if (results[i] === 'P') count++;
  }
  return count;
}
countPassed('PPF');
// 1 'P'
// 2 'F'
// 3 undefined   ← ага! перший символ пропущено, а останній індекс за межами
```

Натисни **Run** у задачі, щоб побачити вивід `console.log`. Після виправлення прибери зайві логи.

### 3. Порівнюй очікуване й фактичне

Сформулюй як баг-репорт: «на вході `'PPF'` очікую `2`, отримую `1`». Часто вже на цьому кроці стає зрозуміло, де помилка.

### 4. Звужуй область пошуку

Закоментуй частину коду або перевір проміжний результат посередині функції. Якщо там уже неправильно, помилка вище. Якщо правильно — нижче.

### 5. Rubber duck debugging

Поясни код уголос рядок за рядком, хоч гумовій качечці. Звучить смішно, але дуже часто помилка знаходиться саме на рядку, де пояснення «не сходиться».

> [!TIP]
> У VS Code є повноцінний **debugger**: точки зупину (breakpoints), покрокове виконання і перегляд змінних. Ти будеш використовувати його разом з Playwright Inspector у треку автоматизації.

## Кидаємо помилки самі: throw

Іноді функція має явно повідомити, що отримала неприпустимі дані:

```ts
function getPercent(part: number, total: number): number {
  if (total === 0) {
    throw new Error('total must be greater than 0');
  }
  return (part / total) * 100;
}
```

Обробляти такі помилки через `try/catch` навчимося в модулі «OOP, Async & Modules».

## Підсумок

- Чотири види помилок: синтаксичні, типів, runtime, логічні. Останні ловлять тільки тести.
- Повідомлення TypeScript читай буквально: де, код, що не так. Виправляй першу помилку.
- `Cannot read properties of undefined` — ти звертаєшся до того, чого немає.
- Налагодження: відтвори → виведи проміжні значення → порівняй очікуване з фактичним → звузь область.
- Опиши проблему як баг-репорт, навіть у власному коді.
