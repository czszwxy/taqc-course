# TypeScript і live coding на співбесіді

Друга частина технічної співбесіди перевіряє, чи вмієш ти **програмувати** на рівні, потрібному для автотестів. Для Trainee/Junior QA Automation це не алгоритми зі змагань, а впевнена робота з масивами, об'єктами, функціями, типами й асинхронністю. Тобто модулі 11–13.

## Часті питання

| Питання | Коротка відповідь |
|---|---|
| `==` vs `===` | `===` порівнює без приведення типів. У тестах завжди `===` |
| `let` vs `const` vs `var` | `const` — не можна перевизначити, `let` — можна, обидва блочні; `var` — застарілий, функціональна область |
| `any` vs `unknown` | `any` вимикає перевірку типів; `unknown` вимагає перевірити тип перед використанням (безпечніше) |
| `interface` vs `type` | обидва описують форму об'єкта; `interface` можна розширювати й доповнювати, `type` вміє union (`'a' \| 'b'`) і складні типи |
| Що таке Promise? | об'єкт «результат буде пізніше»: pending → fulfilled / rejected |
| Навіщо `async/await`? | писати асинхронний код як послідовний; `await` чекає Promise |
| `Promise.all` | запустити кілька Promise паралельно і дочекатися всіх (падає, якщо хоч один упав) |
| `map` / `filter` / `reduce` | перетворити / відібрати / згорнути масив в одне значення |
| Чому `sort()` небезпечний? | змінює масив на місці; числа без компаратора сортує як рядки |
| `null` vs `undefined` | `null` — «значення свідомо немає», `undefined` — «не задано» |

> [!QA]
> На питання «навіщо QA знати async/await?» відповідь проста: **кожна** дія Playwright асинхронна. Забутий `await` — найчастіша причина дивних падінь у тестах новачків.

## Алгоритм live coding

1. **Повтори задачу своїми словами** і задай питання: «Порожній масив можливий? Регістр важливий? Що повертати, якщо нічого не знайдено?»
2. **Приклади**: запиши 2–3 вхідні дані й очікуваний результат, зокрема **крайні** (порожньо, один елемент, дублікати, межі).
3. **Озвуч підхід** до коду: «пройду масив, зберу в Set, потім відфільтрую».
4. **Напиши простий робочий варіант**. Оптимізувати можна потім.
5. **Перевір** на своїх прикладах, проговорюючи значення змінних.
6. **Запропонуй тести**, бо ти тестувальник: «я б перевірив порожній масив, межу 8 символів, …».

> [!TIP]
> Говори вголос увесь час. Мовчазні 10 хвилин виглядають як «застряг», навіть коли ти думаєш. А з міркуваннями вголос інтерв'юер може підказати, і це нормально.

## Типові задачі для QA Automation

- порахувати / згрупувати результати тестів за статусом;
- знайти дублікати, унікальні значення, перетин двох списків (flaky = і passed, і failed);
- валідація: email, пароль, дата, з переліком помилок;
- перетворення даних API: `map` полів, фільтр, сортування за кількома ключами;
- рядки: паліндром, підрахунок слів, перший неповторюваний символ;
- асинхронність: виконати запити послідовно / паралельно, обробити помилку.

Практичні завдання цього уроку — саме такі. Розв'язуй їх як на співбесіді: з таймером на 15–20 хвилин і вголос.

## Підсумок

- Повтори базу: `===`, `const/let`, `any/unknown`, `interface/type`, Promise, `async/await`, `Promise.all`, методи масивів, `sort` з компаратором.
- Live coding: уточнити → приклади з крайніми випадками → озвучити підхід → простий робочий код → перевірити → запропонувати тести.
- Говори вголос. Простий правильний код кращий за складний недописаний.
