# TypeScript і live coding на співбесіді

Друга частина технічної співбесіди перевіряє, чи вмієш ти **програмувати** на рівні, потрібному для автотестів. Для Trainee/Junior QA Automation це не алгоритми зі змагань, а впевнена робота з масивами, об'єктами, функціями, типами й асинхронністю. Тобто модулі 11–13. Інтерв'юери кажуть, що найчастіше кандидати «сиплються» саме на базі JavaScript, а не на Playwright.

## База: питання, які ставлять майже завжди

| Питання | Коротка відповідь |
|---|---|
| Типи даних у JS? | 7 примітивів (`string`, `number`, `boolean`, `null`, `undefined`, `bigint`, `symbol`) + `object` (масиви, функції — теж об'єкти) |
| `==` vs `===` | `===` порівнює без приведення типів. У тестах завжди `===` |
| `null` vs `undefined` | `null` — «значення свідомо немає», `undefined` — «не задано»; `typeof null === 'object'` — історичний баг мови |
| `let` vs `const` vs `var` | `const` — не можна перевизначити, `let` — можна, обидва блочні; `var` — застарілий, функціональна область і hoisting зі значенням `undefined` |
| Hoisting | оголошення «піднімаються» на початок області: `function` доступна до оголошення, `var` — як `undefined`, `let/const` — помилка до оголошення (TDZ) |
| Замикання (closure) | функція пам'ятає змінні з області, де її створили, навіть після виходу з неї (лічильник, фабрика функцій) |
| `this` і стрілкові функції | у звичайній функції `this` залежить від виклику; стрілкова бере `this` ззовні, тому зручна в колбеках методів класу |
| Spread і копії | `{ ...obj }` і `[...arr]` — **поверхнева** копія: вкладені об'єкти спільні; глибока — `structuredClone(obj)` |
| `map` / `filter` / `reduce` / `forEach` | перетворити / відібрати / згорнути в одне значення / просто пройти (повертає `undefined`) |
| Чому `sort()` небезпечний? | змінює масив на місці; числа без компаратора сортує як рядки: `[10, 9, 1].sort()` → `[1, 10, 9]` |

## Асинхронність

| Питання | Коротка відповідь |
|---|---|
| Що таке Promise? | об'єкт «результат буде пізніше»: pending → fulfilled / rejected |
| Навіщо `async/await`? | писати асинхронний код як послідовний; `await` чекає Promise; помилки ловить `try/catch` |
| Event loop | JS однопотоковий: спершу синхронний код, потім **мікрозадачі** (колбеки Promise), потім макрозадачі (`setTimeout`). Тому `then` виконується раніше за `setTimeout(…, 0)` |
| `Promise.all` | паралельно, чекає всі; падає на **першій** помилці |
| `Promise.allSettled` | чекає всі і повертає статус кожного (`fulfilled` / `rejected`) — коли потрібні часткові результати |
| `Promise.race` / `any` | перший завершений (будь-як) / перший успішний |
| Послідовно vs паралельно | `for … await` — по черзі (коли кроки залежать); `Promise.all` — паралельно (незалежні запити) |

> [!QA]
> На питання «навіщо QA знати async/await?» відповідь проста: **кожна** дія Playwright асинхронна. Забутий `await` — найчастіша причина дивних падінь у тестах новачків.

## TypeScript і ООП

| Питання | Коротка відповідь |
|---|---|
| Навіщо TypeScript в автотестах? | помилки типів видно ще до запуску, автодоповнення в редакторі, зрозумілі контракти Page Objects і даних API |
| `any` vs `unknown` vs `never` | `any` вимикає перевірку; `unknown` вимагає перевірити тип перед використанням; `never` — значення, якого не буває (функція завжди кидає помилку) |
| `interface` vs `type` | обидва описують форму об'єкта; `interface` можна розширювати й доповнювати, `type` вміє union (`'a' \| 'b'`) і складні типи |
| Union, literal, optional | `status: 'passed' \| 'failed'`, `email?: string`; звужуємо через `if`, `typeof`, `in` (type guards) |
| Generics | тип-параметр: `function first<T>(items: T[]): T \| undefined` — один код для різних типів без втрати типізації |
| Utility types | `Partial<User>`, `Pick<User, 'email'>`, `Omit<User, 'id'>`, `Record<Status, number>` |
| 4 принципи ООП | інкапсуляція (приховати деталі — `private`), наслідування (`extends`), поліморфізм (однаковий виклик — різна поведінка), абстракція (лише потрібне назовні) |
| Модифікатори доступу | `public`, `private`, `protected`, `readonly` |
| `interface` vs `abstract class` | інтерфейс — лише контракт; абстрактний клас може мати спільну реалізацію (наприклад, `BasePage` з `open()`) |
| Де ООП в автотестах? | Page Objects (інкапсуляція локаторів), `BasePage` (наслідування), API-клієнти |

## Алгоритм live coding

1. **Повтори задачу своїми словами** і задай питання: «Порожній масив можливий? Регістр важливий? Що повертати, якщо нічого не знайдено?»
2. **Приклади**: запиши 2–3 вхідні дані й очікуваний результат, зокрема **крайні** (порожньо, один елемент, дублікати, межі).
3. **Озвуч підхід** до коду: «пройду масив, зберу в Set, потім відфільтрую».
4. **Напиши простий робочий варіант**. Оптимізувати можна потім.
5. **Перевір** на своїх прикладах, проговорюючи значення змінних.
6. **Запропонуй тести**, бо ти тестувальник: «я б перевірив порожній масив, межу 8 символів, …».

> [!TIP]
> Говори вголос увесь час. Мовчазні 10 хвилин виглядають як «застряг», навіть коли ти думаєш. А з міркуваннями вголос інтерв'юер може підказати, і це нормально.

## Типові задачі для QA Automation

- **розминка**: паліндром, розвернути слова, найчастіший символ, FizzBuzz;
- порахувати / згрупувати результати тестів за статусом, знайти найповільніші;
- знайти дублікати, унікальні значення, перетин і різницю двох списків (очікувані vs фактичні);
- flaky = і passed, і failed;
- валідація: email, пароль, дата, з переліком помилок;
- перетворення даних API: `map` полів, фільтр, сортування за кількома ключами;
- асинхронність: кілька запитів паралельно, обробити 404 і помилки.

Часто дають функцію і готові тести: треба, щоб усі стали зеленими. Саме так влаштовані задачі цього уроку. Розв'язуй їх як на співбесіді: з таймером на 15–20 хвилин і вголос.

## Підсумок

- База: типи, `===`, `null/undefined`, `let/const/var`, hoisting, замикання, `this`, копії, методи масивів, `sort` з компаратором.
- Асинхронність: Promise, `async/await`, event loop (мікро- і макрозадачі), `all` / `allSettled` / `race`.
- TypeScript і ООП: `unknown`, union, generics, utility types, 4 принципи, Page Object як приклад.
- Live coding: уточнити → приклади з крайніми випадками → озвучити підхід → простий робочий код → перевірити → запропонувати тести.
