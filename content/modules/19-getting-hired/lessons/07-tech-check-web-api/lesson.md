# Технічна перевірка: веб, HTTP і API

Досвідчені інтерв'юери кажуть, що за останні роки планка для джуна змістилася: сучасні продукти розподілені, і багато дефектів **не видно в UI**. Тому від Junior QA чекають, що він уміє заглянути в **Network**, прочитати запит і відповідь, перевірити API в Postman або Playwright і пояснити, **де саме** проблема. Модулі 07 і 08 дали тобі все це. Тут — у форматі «питання → відповідь».

## «Що відбувається, коли вводиш адресу в браузері?»

Класичне питання. Достатньо 6 кроків:

1. Браузер розбирає URL (протокол, домен, шлях, параметри).
2. **DNS** перетворює домен на IP-адресу (спершу кеш браузера і системи).
3. Встановлюється з'єднання (TCP), для `https` — ще й **TLS** (шифрування, сертифікат).
4. Браузер надсилає **HTTP-запит** (`GET /path`, заголовки, cookies).
5. Сервер обробляє запит і повертає **відповідь**: статус-код, заголовки, тіло (HTML).
6. Браузер розбирає HTML, завантажує CSS, JS, картинки (нові запити), будує сторінку; JS робить API-запити за даними.

## HTTP: методи і статус-коди

| Метод | Для чого | Safe | Idempotent |
|---|---|---|---|
| `GET` | отримати ресурс | так | так |
| `POST` | створити / виконати дію | ні | **ні** — повтор може створити дублікат |
| `PUT` | замінити ресурс **повністю** | ні | так |
| `PATCH` | змінити **частину** ресурсу | ні | не гарантовано |
| `DELETE` | видалити | ні | так |

**Idempotent** — повторний однаковий запит дає той самий стан на сервері. Тест-ідея: двічі надіслати `POST /orders` (подвійний клік «Оплатити») — чи не створилося два замовлення?

**PUT vs PATCH** — тест-ідея: надіслати в `PUT` лише одне поле і перевірити, чи не стерлися інші.

| Код | Значення | Приклад |
|---|---|---|
| 200 / 201 / 204 | OK / Created / No Content | отримали дані / створили (часто з `Location`) / видалили без тіла |
| 301 / 302 / 304 | переїхало назавжди / тимчасово / не змінилось (кеш) | |
| 400 | некоректний запит | зламаний JSON, `id=abc` |
| **401** | **не автентифікований** — «я не знаю, хто ти» | немає токена або він протух |
| **403** | **немає прав** — «знаю, хто ти, але тобі не можна» | користувач викликає адмінську дію |
| 404 | не знайдено | неіснуючий id |
| 409 / 422 | конфлікт / не пройшла валідація | email уже існує / `quantity: -1` |
| 429 | забагато запитів | rate limit |
| 500 / 502 / 503 | помилка сервера / шлюзу / сервіс недоступний | |

> [!TIP]
> Групи кодів: **2xx** — успіх, **3xx** — перенаправлення, **4xx** — помилка клієнта (запиту), **5xx** — помилка сервера. Для QA важливо: 5xx у відповідь на некоректні дані — це баг (сервер мав відповісти 4xx з поясненням).

## Запит, заголовки, параметри

- **Path** параметр ідентифікує ресурс: `/api/orders/1002`. **Query** — фільтр, сортування, сторінка: `/api/products?category=phones&page=2`.
- Заголовки: `Content-Type: application/json` (формат тіла), `Authorization: Bearer <token>`, `Cookie` / `Set-Cookie`, `Cache-Control`, `Location` (адреса створеного ресурсу).
- **REST**: ресурси як іменники в URL, дії — методами, сервер **stateless** (кожен запит несе все потрібне, наприклад токен), відповіді в JSON.
- **JSON** типи: рядок, число, `true/false`, `null`, масив, об'єкт. Немає дат — вони рядками (`"2024-09-20"`).

## Автентифікація, сесії, сховища

| Питання | Відповідь |
|---|---|
| Authentication vs authorization | автентифікація — **хто ти** (логін); авторизація — **що тобі можна** (ролі, доступ) |
| Cookie vs localStorage vs sessionStorage | cookie автоматично йде на сервер з кожним запитом, має термін і прапорці (`HttpOnly`, `Secure`); localStorage — у браузері назавжди, лише для JS; sessionStorage — до закриття вкладки |
| Навіщо `HttpOnly`? | JS не може прочитати cookie, тож XSS не вкраде сесію |
| Що таке JWT? | токен з трьох частин `header.payload.signature` (base64url); payload читається будь-ким, тому там не має бути секретів; підпис не дає його підробити |
| Що таке CORS? | правило браузера: сторінка з одного домену може читати відповіді іншого домену, лише якщо той дозволив (заголовки `Access-Control-Allow-*`) |
| Кеш | браузер і сервер можуть віддавати збережену копію; «у мене працює, у тебе ні» — спершу жорстке оновлення або інкогніто |

## DevTools: фронтенд чи бекенд?

| Вкладка | Що там шукати |
|---|---|
| **Elements** | DOM і стилі: чи є елемент, чи прихований, які атрибути |
| **Console** | JS-помилки (`TypeError`), попередження, логи |
| **Network** | запит, метод, статус, **Payload** (що надіслали), **Response** (що прийшло), час; Preserve log, Disable cache, Throttling (повільний інтернет) |
| **Application** | cookies, localStorage, sessionStorage, кеш |

Алгоритм локалізації бага:

1. Знайди запит у **Network**, який робить ця дія.
2. **Payload правильний?** Ні → фронтенд надіслав не те.
3. **Response правильний?** Ні → бекенд.
4. Відповідь правильна, а на сторінці не те, або в **Console** помилка → фронтенд.
5. Запиту немає взагалі → фронтенд (обробник кнопки, валідація) або кеш.

> [!QA]
> У баг-репорті напиши, що бачив у Network: `POST /api/orders → 201, response total: 1500, UI shows 0`. Розробник одразу знає, де шукати, а ти показуєш рівень вище за «не працює».

## Як протестувати ендпоінт

Скелет відповіді на «Як би ти протестував `POST /api/orders`?»:

- **позитивні**: валідне тіло → 201, тіло відповіді (поля, типи, значення), заголовок `Location`, дані збереглися (`GET` за id);
- **валідація**: обов'язкові поля відсутні, неправильні типи, межі (0, 1, max, max+1), зайві поля, порожнє тіло, некоректний JSON → 400/422 зі зрозумілим повідомленням;
- **доступ**: без токена → 401, протухлий токен → 401, чужий ресурс → 403/404, роль без прав → 403;
- **інше**: повторний запит (дублікати), схема відповіді (контракт), час відповіді, неіснуючий `productId` → 404, сервер не віддає 500 на сміття.

Postman і Playwright `request` роблять те саме: запит → перевірки статусу, тіла, заголовків. У Postman — колекції, змінні середовища (`{{baseUrl}}`, `{{token}}`), скрипти з перевірками.

## Підсумок

- URL у браузері: DNS → з'єднання (TLS) → HTTP-запит → відповідь → рендеринг і нові запити.
- Методи і ідемпотентність (POST — ні), PUT vs PATCH, групи статус-кодів, 401 vs 403, 400 vs 422.
- Path vs query, основні заголовки, REST stateless, JSON типи.
- Authentication vs authorization, cookie vs localStorage vs sessionStorage, HttpOnly, JWT, CORS.
- DevTools: Payload правильний? Response правильний? Console? — і ти знаєш, де баг.
- Ендпоінт: позитивні → валідація і межі → доступ → дублікати, контракт, час.
