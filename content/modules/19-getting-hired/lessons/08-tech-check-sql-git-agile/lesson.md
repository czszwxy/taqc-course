# Технічна перевірка: SQL, Git і Agile

Ці три теми рідко займають усю співбесіду, але **питання з них є майже завжди**. Інтерв'юери чесно кажуть: від джуна чекають чотири-п'ять конструкцій SQL, базовий Git і розуміння, як QA працює в команді. OSI-моделі чи реплікації баз даних на рівні Junior зазвичай не питають.

## SQL: що треба знати напевно

| Питання | Відповідь |
|---|---|
| Базові конструкції | `SELECT … FROM … WHERE … ORDER BY …`, `JOIN`, `GROUP BY` з `COUNT/SUM/AVG`, `LIMIT` |
| `WHERE` vs `HAVING` | `WHERE` фільтрує **рядки до** групування; `HAVING` — **групи після** (`HAVING COUNT(*) > 1`) |
| `INNER JOIN` vs `LEFT JOIN` | INNER — лише пари, що збіглися; LEFT — усі рядки лівої таблиці, для відсутніх пар — `NULL` |
| Як знайти записи без пари? | `LEFT JOIN … WHERE right.id IS NULL` (користувачі без замовлень) |
| Як знайти дублікати? | `GROUP BY email HAVING COUNT(*) > 1` |
| `NULL` | невідоме значення: порівнюють через `IS NULL`, а не `= NULL`; `COUNT(column)` не рахує `NULL`, `COUNT(*)` рахує всі рядки |
| `DISTINCT` | прибирає повтори в результаті |
| Primary key / foreign key | PK — унікальний ідентифікатор рядка; FK — посилання на PK іншої таблиці (замовлення → користувач) |
| `DELETE` vs `TRUNCATE` vs `DROP` | видалити рядки (можна з `WHERE`) / усі рядки швидко / таблицю повністю разом зі структурою |
| Порядок виконання | `FROM/JOIN → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT` |
| Навіщо індекс? | прискорює пошук за колонкою, але сповільнює запис |
| Як QA використовує SQL? | перевірити дані після дії в UI/API, підготувати тестові дані, знайти аномалії (дублікати, «сироти», некоректні суми) |

### Класичні live SQL задачі

- користувачі **без** замовлень;
- топ-3 клієнти за сумою покупок;
- кількість замовлень за статусом, лише статуси з ≥ 2 замовленнями;
- **другий** за ціною товар;
- дублікати email (з урахуванням регістру — `LOWER(email)`);
- замовлення, де `total` не дорівнює сумі позицій.

> [!TIP]
> Кажи вголос, що робиш: «спершу з'єдную users і orders через LEFT JOIN, бо мені потрібні і ті, хто не замовляв…». Синтаксичну помилку інтерв'юер пробачить, хибну логіку — ні.

## Git: базові питання

| Питання | Відповідь |
|---|---|
| Навіщо Git? | історія змін, робота кількох людей паралельно в гілках, відкат, code review |
| `fetch` vs `pull` | `fetch` завантажує зміни, не чіпаючи твою гілку; `pull` = `fetch` + `merge` (або rebase) |
| `merge` vs `rebase` | merge — об'єднує гілки комітом злиття, історія як була; rebase — переносить твої коміти поверх іншої гілки, історія лінійна; спільні гілки не ребейзять |
| Конфлікт злиття | обидві гілки змінили ті самі рядки: відкрити файл, вибрати правильний варіант, прибрати маркери `<<<<<<<`, `add` + `commit` |
| `revert` vs `reset` | `revert` створює новий коміт, що скасовує зміни (безпечно для спільних гілок); `reset` переписує історію (лише локально) |
| `stash` | тимчасово сховати незакомічені зміни |
| Pull request | запит влити гілку: рев'ю коду, перевірки CI, обговорення |
| Що в `.gitignore`? | `node_modules`, звіти й результати тестів, `.env` із секретами, артефакти збірки |

## Agile і Scrum: де тут QA

- **Ролі Scrum**: Product Owner (цінність, пріоритети беклогу), Scrum Master (процес, перешкоди), Developers — **уся команда розробки, включно з QA**.
- **Події**: Sprint (1–4 тижні), Sprint Planning, Daily Scrum (15 хв: прогрес до цілі, блокери), Sprint Review (показ результату), Sprint Retrospective (як покращити роботу). Плюс регулярний **refinement** беклогу.
- **Артефакти**: Product Backlog, Sprint Backlog, Increment. **Definition of Done** — спільні критерії «готово» (наприклад, код у main, тести пройдені, баги критичні закриті).
- **User story**: «As a *user*, I want *…*, so that *…*» + **acceptance criteria** (часто Given / When / Then).
- **Kanban**: потік задач через колонки, ліміти незавершеної роботи (WIP), без спринтів.

**Роль QA у спринті** (часте питання «опиши свій спринт»):

1. На refinement і planning — уточнює acceptance criteria, ставить питання, оцінює обсяг тестування.
2. Поки фіча в розробці — пише тест-кейси / чекліст, готує дані, автотести.
3. Коли фіча готова — тестує, заводить баги, перевіряє фікси, оновлює автотести.
4. Під кінець — регресія (автоматична на CI + ручна для ризиків), участь у Review.
5. На ретро — пропонує покращення процесу (наприклад, раніше бачити макети).

> [!QA]
> Ключова думка для співбесіди: QA в Agile — не «останній етап перед релізом», а учасник з першого дня. Знаходити проблеми у вимогах дешевше, ніж у готовому коді.

## Підсумок

- SQL: базові конструкції, WHERE vs HAVING, INNER vs LEFT JOIN, NULL, дублікати, ключі, DELETE/TRUNCATE/DROP, порядок виконання.
- Git: fetch/pull, merge/rebase, конфлікти, revert/reset, PR, `.gitignore`.
- Scrum: 3 ролі (QA — частина Developers), 5 подій, 3 артефакти, DoD, user story з acceptance criteria.
- QA у спринті: з refinement до ретро, а не лише в кінці.
