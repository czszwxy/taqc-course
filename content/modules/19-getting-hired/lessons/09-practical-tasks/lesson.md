# Практичні задачі на співбесіді

Майже на кожній технічній співбесіді Junior QA є «практика на місці»: інтерв'юер дає 5–15 хвилин і просить **написати чекліст**, **придумати тестові дані** або **протестувати предмет**. Тут перевіряють не знання, а **мислення**: чи системно ти покриваєш функцію, чи думаєш про межі, негативні сценарії і безпеку.

## Типові задачі

| Задача | На що звернути увагу |
|---|---|
| Чекліст для кошика / форми оплати / логіну / реєстрації / пошуку | позитивні, валідація полів, межі, повідомлення про помилки, UI, безпека |
| Тестові дані для поля «вік 18–99» | класи еквівалентності + граничні значення: 17, 18, 99, 100, плюс нечислові, порожнє, від'ємне, дробове |
| Тестові дані «дата народження, молодше 18 — заборонено» | рівно 18 років сьогодні (можна), на день менше (не можна), 29 лютого, майбутня дата, сьогоднішня, дуже стара, неправильний формат |
| Негативні тести для форми email + пароль | порожні поля, неправильний email, пробіли, дуже довгі значення, SQL / HTML у полях, неправильний пароль, заблокований акаунт |
| Протестуй чайник / тостер / ліфт / ручку | уточнити вимоги → функції → межі → негативні → нефункціональні (безпека!) |
| «Не працює чайник — напиши баг-репорт» | заголовок «що, де, коли», кроки, expected/actual, середовище (модель, мережа), severity |
| Smoke для месенджера після нового білда | 6–10 перевірок критичного шляху: вхід, список чатів, надіслати й отримати повідомлення, сповіщення, фото |
| Калькулятор: ділення | 0, ділення на 0, від'ємні, дробові, дуже великі числа, округлення, переповнення поля |
| Скільки тест-кейсів за EP? | порахуй класи для кожної умови: зазвичай по одному на клас + межі |
| Поясни базу даних 7-річній дитині | проста аналогія: «шафа з підписаними шухлядами» — перевіряють уміння пояснювати |

## Як відповідати: 5 кроків

1. **Уточни** 1–3 речі: «Які типи карток? Чи зберігаємо картку? Яка мова?». Якщо часу мало — назви припущення вголос.
2. **Структуруй** за групами: позитивні → валідація і межі → помилки → UI/UX → нефункціональні → безпека.
3. **Пріоритезуй**: спершу те, що ламає головний сценарій або гроші.
4. **Будь конкретним**: не «перевірити поле», а «номер з 15 цифр → помилка "Card number must have 16 digits"».
5. **Говори вголос** і скажи, що додав би з більшим часом.

> [!TIP]
> Інтерв'юер часто зупиняє тебе через 5 хвилин. Тому починай з **найважливішого**, а не з кольору кнопки.

## Приклад: поле «Дата народження», користувачам молодше 18 — заборонено

Припустимо, сьогодні 15.05.2026:

- **15.05.2008** — рівно 18 років сьогодні → дозволено (межа);
- **16.05.2008** — 18 виповниться завтра → заборонено (межа + 1 день);
- **29.02.2008** — високосний рік: коли настає 18-річчя в невисокосному році?;
- **15.05.2026** (сьогодні), **16.05.2026** (майбутнє) → заборонено;
- **01.01.1900** — дуже стара дата: приймаємо чи ні, за вимогою;
- **31.02.2008**, **2008-13-01**, порожньо, літери → помилка формату.

## Мінімальний чекліст безпеки

Пентест — робота окремих фахівців, але базові перевірки від QA чекають уже на рівні Junior:

| Перевірка | Як | Чого чекаємо |
|---|---|---|
| Пароль приховано | поле пароля | символи замасковані, є кнопка «показати» за потреби |
| Повідомлення не розкривають зайвого | неправильний email / пароль | однакове «Invalid email or password», без «такого користувача немає» (інакше можна перебрати існуючі email) |
| Захист від перебору | 10 невдалих спроб входу | блокування, затримка або CAPTCHA |
| XSS | ввести `<script>alert(1)</script>` у поле імені, потім відкрити сторінку | текст показано як текст, скрипт не виконується |
| SQL-ін'єкція | `' OR '1'='1` у поле логіну чи пошуку | звичайна помилка валідації, не вхід і не 500 |
| Доступ до чужих даних (IDOR) | змінити id в URL або запиті: `/invoices/502` → `/invoices/501` (чужий рахунок) | 403 або 404, а не чужі дані |
| Сесія | вийти і натиснути «Назад»; відкрити старий токен | дані не показуються, токен недійсний |
| HTTPS | адреса, форми входу й оплати | лише HTTPS, без змішаного контенту |
| Чутливі дані | Network, URL, localStorage | паролі, CVV, токени не потрапляють в URL, логи і відповіді API |

> [!WARNING]
> Перевіряй безпеку лише на **своїх** або навчальних системах чи з дозволу власника. «Протестувати» чужий сайт без дозволу — порушення закону.

> [!QA]
> Згадати безпеку в чеклісті форми оплати чи логіну — один із найпростіших способів виділитися серед кандидатів: більшість про неї забуває.

## Підсумок

- Практичні задачі перевіряють мислення: уточнити → структурувати → пріоритезувати → бути конкретним → говорити вголос.
- Тестові дані: класи + межі + нестандартні значення (порожньо, формат, дата 29 лютого, майбутнє).
- «Протестуй предмет»: функції → межі → негативні → нефункціональні; безпека окремим пунктом.
- Мінімальна безпека: маска пароля, однакові повідомлення про помилки, захист від перебору, XSS, SQL-ін'єкція, IDOR, сесія, HTTPS, чутливі дані.
