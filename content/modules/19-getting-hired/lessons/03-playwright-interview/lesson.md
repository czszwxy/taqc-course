# Співбесіда: Playwright і автоматизація

Третя частина — про автоматизацію: як ти думаєш про автотести і чи вмієш їх писати. Модулі 15–18 дали відповіді. Тут вони зібрані у формі «питання → що сказати».

## Питання і суть відповіді

| Питання | Що сказати |
|---|---|
| Що автоматизувати першим? | те, що часто запускається і стабільне: smoke, регрес, розрахунки, API; не автоматизую одноразове, суб'єктивне, нестабільне |
| Піраміда тестів? | багато unit, менше API, найменше UI; UI — для ключових сценаріїв |
| Які локатори використовуєш? | `getByRole`, `getByLabel`, `getByText`, `getByTestId`; CSS/XPath — запасний варіант; уникаю шляхів і класів стилів |
| Як Playwright чекає елементи? | автоочікування перед діями (visible, enabled, stable) і web-first перевірки, які повторюються до таймауту; тому `waitForTimeout` не потрібен |
| Що робиш з flaky-тестами? | виявити (retries, repeat-each) → розібрати trace → виправити причину (гонки, спільні дані, паузи) або карантин із задачею |
| Навіщо Page Object? | локатори й дії сторінки в одному місці; тести читаються як сценарії; зміна верстки — одне виправлення |
| Що таке фікстури? | готові до використання ресурси в параметрах тесту з setup і teardown: Page Objects, користувач, дані |
| Як не логінитися в кожному тесті? | storageState: setup-проєкт логіниться раз (часто через API), тести стартують залогіненими |
| Навіщо мокати мережу? | рідкісні стани (500, порожньо, повільно) і стабільність; моки не замінюють тестів справжнього API |
| Як запускаєш тести на CI? | GitHub Actions: `npm ci` → `playwright install --with-deps` → тести → звіт як артефакт; smoke на PR, регресія вночі |
| Паралельність? | workers і fullyParallel; тести мають бути незалежними: свої дані, без порядку |
| Чому Playwright, а не Selenium? | (модуль 15) автоочікування, вбудований раннер, trace, кілька браузерів, API-тести; але вибір залежить від проєкту |

## Live coding автотестів

Часто просять за 15–30 хвилин написати тести для простої сторінки. Що оцінюють:

- **з чого почав**: перелік сценаріїв уголос (позитивний, межі, негативні);
- **структуру**: `beforeEach`, хелпер або маленький Page Object;
- **локатори**: user-facing, без крихких CSS-шляхів;
- **перевірки**: web-first, точні значення з вимог;
- **без пауз** і без `force`;
- **як дебажиш**, коли щось не працює: читаєш помилку, а не перебираєш варіанти навмання.

> [!TIP]
> Якщо не встигаєш, скажи, що б ти ще додав: «далі я б перевірив межу 4-ї спроби і зробив Page Object». Інтерв'юер оцінює і план, не лише набраний код.

## «Розкажи про свій фреймворк»

Майже обов'язкове питання. Структура відповіді (2–3 хвилини):

1. **Контекст**: що тестує (навчальний магазин, UI + API), скільки тестів.
2. **Стек**: TypeScript, Playwright Test, GitHub Actions.
3. **Структура**: Page Objects, API-клієнти, фікстури (дані з прибиранням, авторизація через storageState).
4. **Стабільність**: user-facing локатори, web-first перевірки, незалежні тести, retries лише на CI з trace.
5. **CI і звіти**: smoke на PR, повний прогін вночі, HTML-звіт з trace як артефакт.
6. **Що покращив би**: візуальні тести, шардинг, більше API-контрактів.

> [!QA]
> Чесно кажи, що проєкт навчальний: ніхто не чекає від Trainee продакшн-досвіду. Цінуються **рішення і розуміння**: чому так, а не інакше.

## Підсумок

- Тримай у голові короткі відповіді про локатори, автоочікування, flaky, POM, фікстури, storageState, моки, CI, паралельність.
- Live coding: сценарії вголос → структура → user-facing локатори → web-first перевірки → без пауз.
- «Розкажи про фреймворк»: контекст → стек → структура → стабільність → CI → що покращив би.
