# Співбесіда: Playwright і автоматизація

Третя частина — про автоматизацію: як ти думаєш про автотести і чи вмієш їх писати. Модулі 14–18 дали відповіді. Тут вони зібрані у формі «питання → що сказати». За оглядами питань 2025–2026 років, найчастіше питають про **browser / context / page**, **локатори**, **автоочікування**, **storageState**, **фікстури**, **flaky і retries** та **trace viewer**.

## Підхід до автоматизації

| Питання | Що сказати |
|---|---|
| Що автоматизувати першим? | те, що часто запускається і стабільне: smoke, регрес, розрахунки, API; не автоматизую одноразове, суб'єктивне (дизайн «на око»), нестабільне |
| Піраміда тестів? | багато unit, менше API, найменше UI; UI — для ключових сценаріїв |
| Чим добрий автотест? | незалежний, детермінований, швидкий, перевіряє одну поведінку, зрозуміла назва, падає з корисним повідомленням |
| Чому Playwright, а не Selenium? | автоочікування, вбудований раннер з паралельністю, trace viewer, кілька браузерів, API-тести, моки мережі; але вибір залежить від проєкту і команди |

## Ядро Playwright

| Питання | Що сказати |
|---|---|
| Browser vs context vs page? | browser — запущений браузер; context — ізольована «сесія» (свої cookies, storage), як окремий профіль; page — вкладка в контексті. Кожен тест отримує новий context, тому тести ізольовані |
| Які локатори використовуєш? | `getByRole`, `getByLabel`, `getByText`, `getByTestId`; CSS/XPath — запасний варіант; уникаю шляхів і класів стилів |
| Strict mode violation? | локатор знайшов кілька елементів, а дія потребує одного: уточню (`{ name, exact }`, `filter({ hasText })`, ланцюжок від контейнера), а не `.first()` навмання |
| Як Playwright чекає елементи? | автоочікування перед діями (visible, enabled, stable, отримує події) і web-first перевірки, що повторюються до таймауту; тому `waitForTimeout` не потрібен |
| `isVisible()` vs `toBeVisible()`? | `isVisible()` — миттєва відповідь без очікування; `await expect(locator).toBeVisible()` — чекає і повторює |
| `expect.soft`, `expect.poll`, `toPass`? | soft — тест продовжується після невдалої перевірки; poll — повторює функцію, доки значення не стане очікуваним (наприклад, статус з API); `toPass` — повторює блок перевірок |
| Хуки? | `beforeAll`, `beforeEach`, `afterEach`, `afterAll`; на рівні файлу або `describe`; спільний setup — краще у фікстурах |
| Iframe, нова вкладка, діалоги, файли? | `page.frameLocator(...)` / `locator.contentFrame()`; `context.waitForEvent('page')` або `page.waitForEvent('popup')`; `page.on('dialog')`; `setInputFiles`, `waitForEvent('download')` |
| Як дебажиш падіння? | читаю помилку → HTML-звіт → **trace viewer** (кроки, DOM-знімки, мережа, консоль) → `--ui` / `--debug` локально; `codegen` — щоб швидко підглянути локатор |

## Фреймворк і запуск

| Питання | Що сказати |
|---|---|
| Навіщо Page Object? | локатори й дії сторінки в одному місці; тести читаються як сценарії; зміна верстки — одне виправлення; перевірки — переважно в тестах |
| Що таке фікстури? Скоупи? | ресурси в параметрах тесту з setup і teardown (Page Objects, користувач, дані); `test` scope — новий для кожного тесту, `worker` scope — один на воркер (наприклад, дорогий акаунт) |
| Як не логінитися в кожному тесті? | storageState: setup-проєкт логіниться раз (часто через API), тести стартують залогіненими |
| Кілька ролей в одному тесті? | два контексти з різним storageState (admin і user) в одному тесті |
| Навіщо мокати мережу? | рідкісні стани (500, порожньо, повільно) і стабільність через `page.route`; моки не замінюють тестів справжнього API |
| API-тести в Playwright? | фікстура `request`: `request.post('/api/orders', { data })`, перевірка статусу і тіла; API для підготовки даних перед UI-тестом |
| Projects у конфігу? | різні браузери / пристрої / налаштування як окремі проєкти; setup-проєкт як залежність (`dependencies`) |
| Паралельність? | workers і `fullyParallel`; тести незалежні: свої дані, без порядку; `test.describe.configure({ mode: 'serial' })` — лише якщо інакше ніяк |
| Flaky-тести? | виявити (retries, `--repeat-each`) → розібрати trace → виправити причину (гонки, спільні дані, паузи, нестабільні локатори) або карантин із задачею |
| Як запускаєш на CI? | GitHub Actions: `npm ci` → `npx playwright install --with-deps` → тести → звіт як артефакт; smoke на PR, регресія вночі; шардинг для великих наборів |

## Нове питання 2025–2026: AI-інструменти

Тепер часто питають: «Чи користуєшся AI-помічниками і як?». Добра відповідь чесна і показує **контроль**:

- використовую для чернетки тест-ідей, пояснення помилки, шаблону коду, тестових даних;
- **завжди перевіряю** результат: запускаю тест, читаю кожен рядок, перевіряю локатори на сторінці, бо AI може вигадати неіснуючий API чи елемент;
- не передаю в AI-сервіси секрети, токени, персональні дані і код компанії без дозволу;
- розумію і можу пояснити все, що закомітив.

> [!WARNING]
> «AI пише мені тести, я їх не читаю» — червоний прапорець. На співбесіді попросять пояснити рядок коду з твого репозиторію.

## Live coding автотестів

Часто просять за 15–30 хвилин написати тести для простої сторінки або **розширити** твоє ж тестове завдання. Що оцінюють:

- **з чого почав**: перелік сценаріїв уголос (позитивний, межі, негативні);
- **структуру**: `beforeEach`, хелпер або маленький Page Object;
- **локатори**: user-facing, без крихких CSS-шляхів;
- **перевірки**: web-first, точні значення з вимог;
- **без пауз** і без `force`;
- **як дебажиш**, коли щось не працює: читаєш помилку, а не перебираєш варіанти навмання.

Ще один формат — **code review**: тобі показують поганий тест і просять знайти проблеми. Таке завдання є в практиці цього уроку.

> [!TIP]
> Якщо не встигаєш, скажи, що б ти ще додав: «далі я б перевірив порожні поля і зробив Page Object». Інтерв'юер оцінює і план, не лише набраний код.

## «Розкажи про свій фреймворк»

Майже обов'язкове питання. Структура відповіді (2–3 хвилини):

1. **Контекст**: що тестує (навчальний магазин, UI + API), скільки тестів.
2. **Стек**: TypeScript, Playwright Test, GitHub Actions.
3. **Структура**: Page Objects, API-клієнти, фікстури (дані з прибиранням, авторизація через storageState).
4. **Стабільність**: user-facing локатори, web-first перевірки, незалежні тести, retries лише на CI з trace.
5. **CI і звіти**: smoke на PR, повний прогін вночі, HTML-звіт з trace як артефакт.
6. **Що покращив би**: візуальні тести, шардинг, більше API-контрактів.

> [!QA]
> Чесно кажи, що проєкт навчальний: ніхто не чекає від Trainee продакшн-досвіду. Цінуються **рішення і розуміння**: чому так, а не інакше. Будь готовий, що інтерв'юер відкриє твій GitHub і спитає про конкретний файл.

## Підсумок

- Тримай у голові короткі відповіді: browser/context/page, локатори і strict mode, автоочікування, `toBeVisible` vs `isVisible`, фікстури і скоупи, storageState, моки, projects, паралельність, flaky, trace viewer, CI.
- Про AI: використовую як помічника, але все перевіряю і розумію.
- Live coding і code review: сценарії вголос → структура → user-facing локатори → web-first перевірки → без пауз і залежностей між тестами.
- «Розкажи про фреймворк»: контекст → стек → структура → стабільність → CI → що покращив би.
