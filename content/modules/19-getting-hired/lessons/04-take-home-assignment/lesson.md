# Тестове завдання (take-home assignment)

Багато компаній замість живого coding або на додачу до нього дають **тестове завдання**: протестувати сторінку чи API і автоматизувати кілька сценаріїв за 1–3 дні. Для Trainee це часто **головний фільтр**. Добре виконане тестове відкриває двері навіть без комерційного досвіду.

## Типовий текст завдання

> Here is our demo account page: `<link>`. Test account: `qa@gadgetly.test` / `Test1234`.
>
> 1. Write a short test plan or a checklist.
> 2. Report the bugs you find.
> 3. Automate the most important scenarios (Playwright + TypeScript).
> 4. Push everything to a public GitHub repository with a README.
>
> Expected effort: 4–6 hours. Deadline: 3 days.

## Як працювати

1. **Прочитай повністю двічі.** Випиши, що саме треба здати і в якому форматі.
2. **Задай питання одразу**, у перший день: «Які браузери?», «Баги — у README чи окремим файлом?», «Чи можна використовувати моки?». Якщо відповіді немає, **зафіксуй припущення** в README.
3. **Розплануй час** (timebox). Наприклад, з 6 годин: 1 год план і дослідження, 1,5 год баги, 2,5 год автотести, 1 год README і прибирання.
4. **Спершу досліди вручну**, потім автоматизуй. Ручне дослідження показує, що найважливіше і де ризики.
5. **Автоматизуй мало, але якісно**: 5–8 ключових сценаріїв з охайним кодом кращі за 40 копіпаст-тестів.
6. **Здай вчасно**. Не встиг — здай зроблене з розділом «What I would do next».

> [!IMPORTANT]
> Тест, що падає через **справжній баг**, не «виправляй», підлаштовуючи перевірку під неправильну поведінку. Перевірка лишається на правильну поведінку з вимог. Познач тест `test.fail()` (або `test.fixme`) з посиланням на баг-репорт і поясни це в README.

## Що оцінює рев'юер

| Що | Як виглядає добре |
|---|---|
| Мислення тестувальника | план із пріоритетами і ризиками; позитивні, негативні, межові сценарії |
| Баг-репорти | короткий точний заголовок, кроки, actual / expected, severity з поясненням |
| Вибір сценаріїв для автоматизації | ключові і стабільні, з поясненням, чому саме вони |
| Якість коду | user-facing локатори, web-first перевірки, без пауз, хелпери / Page Objects, зрозумілі назви |
| Репозиторій | README, `.gitignore` (без `node_modules`, звітів, секретів), осмислені коміти |
| Комунікація | припущення, обмеження, що зробив би далі |

## README тестового завдання

```text
# Gadgetly account page — test assignment
## How to run        (npm ci, npx playwright install, npm test, report)
## What is covered    (scenarios + why these)
## Bugs found         (list with links to reports, severity)
## Assumptions        (what was unclear and what I assumed)
## Not covered / next steps
```

> [!TIP]
> Перевір себе очима рев'юера: склонуй свій репозиторій у нову папку і пройди README крок за кроком. Якщо щось не запускається, рев'юер не стане розбиратися.

## Симуляція в цьому уроці

Практика уроку — повне тестове завдання на сторінці **My account** (`/playground/account`):

1. **Частина 1** — план: питання, scope, чекліст, вибір сценаріїв, timebox.
2. **Частина 2** — баг-репорти (щонайменше 3).
3. **Частина 3** — автотести Playwright, перевірені на зламаних версіях сторінки.
4. **Частина 4** — README.

Засічи час: орієнтир 3–4 години на все. Так ти відчуєш реальний темп.

> [!QA]
> Збережи результат у власному репозиторії. Це вже готовий пункт для портфоліо і тема для розмови на співбесіді: «розкажи про своє тестове».

## Підсумок

- Прочитай двічі → питання одразу → припущення в README → timebox.
- Спершу ручне дослідження, потім 5–8 якісних автотестів.
- Тест на справжній баг не підлаштовуй: `test.fail()` + посилання на репорт.
- README: як запустити, що покрито і чому, баги, припущення, наступні кроки.
- Здавай вчасно, навіть якщо не все встиг.
