# Співбесіда: теорія тестування

Навіть на позицію QA Automation перша частина технічної співбесіди майже завжди про **теорію тестування**. Інтерв'юер перевіряє, чи розумієш ти, **що** і **навіщо** тестувати. Інструменти другорядні. Модулі 01–06 уже дали тобі всі відповіді. Залишилось навчитися їх **говорити**: коротко, своїми словами і з прикладом.

> [!NOTE]
> На джуна найчастіше питають не визначення напам'ять, а **застосування**: «які значення ти візьмеш для поля 18–99?», «чим цей баг blocker?». Тому до кожної відповіді готуй приклад.

## Формула доброї відповіді

1. **Визначення** — одним-двома реченнями, своїми словами.
2. **Приклад** — з реального або навчального проєкту (Gadgetly, Taskly).
3. **Навіщо це QA** — як це впливає на роботу.

> Питання: «Чим severity відрізняється від priority?»
>
> **Відповідь**: «Severity — наскільки дефект впливає на систему, priority — наскільки терміново його виправляти. Зазвичай вони збігаються, але не завжди. Друкарська помилка в назві компанії на головній сторінці має низьку severity, але високий priority. А падіння рідкісного звіту для адміна — висока severity, але priority може бути середнім. Severity зазвичай ставить QA, а priority — продакт або тімлід».

## Банк питань (коротко)

| Питання | Суть відповіді |
|---|---|
| Що таке тестування? Навіщо воно? | перевірка продукту, щоб знайти дефекти і дати команді інформацію про якість і ризики до релізу |
| QA vs QC vs testing? | QA — процеси, що запобігають дефектам; QC — перевірка продукту; testing — частина QC, конкретні перевірки |
| Error, defect, failure? | помилка людини → дефект у коді → збій під час виконання |
| Verification vs validation? | «чи правильно робимо продукт» (за специфікацією) vs «чи робимо правильний продукт» (для користувача) |
| Принципи тестування? | показує наявність дефектів, а не їх відсутність; вичерпне тестування неможливе; раннє тестування; скупчення дефектів; парадокс пестициду; залежить від контексту; «відсутність помилок» — оманлива ідея |
| SDLC і STLC? | SDLC — життєвий цикл розробки; STLC — аналіз вимог → планування → тест-дизайн → підготовка середовища → виконання → завершення |
| Entry / exit criteria? | умови початку (білд задеплоєно, smoke зелений) і завершення тестування (критичні кейси пройдені, немає відкритих blocker) |
| Рівні тестування? | unit → integration → system → acceptance |
| Функціональне vs нефункціональне? | «що робить» система vs «як добре»: швидкість, безпека, зручність, сумісність, доступність |
| Чорна / біла / сіра скринька? | без знання коду / зі знанням коду / частково (наприклад, перевірка БД після дії в UI) |
| Smoke, sanity, regression, retest? | smoke — базова працездатність білда; sanity — швидка перевірка конкретної зміни; regression — нічого старого не зламалося; retest — перевірка виправленого бага |
| Exploratory testing? | одночасне вивчення, тест-дизайн і виконання; часто в сесіях з charter і таймбоксом |
| Статичне тестування? | перевірка без запуску коду: рев'ю вимог, коду, тест-кейсів |
| Техніки тест-дизайну? | класи еквівалентності, граничні значення, таблиці рішень, переходи станів, попарне тестування, error guessing |
| Risk-based testing? | спершу тестуємо те, де ймовірність і наслідки збою найбільші (оплата, логін, дані) |
| Тест-план — що в ньому? | scope (in/out), підхід, середовища, ролі, графік, ризики, критерії входу/виходу, deliverables |
| Тест-кейс vs чекліст? | детальні кроки, дані й очікування vs список перевірок без деталей |
| Що в баг-репорті? | заголовок, середовище, передумови, кроки, actual, expected, severity/priority, вкладення |
| Рівні severity? | blocker → critical → major → minor → trivial |
| Життєвий цикл бага? | New → Assigned → In progress → Fixed → Retest → Closed / Reopened (+ Rejected, Duplicate, Deferred) |
| Позитивне vs негативне тестування? | коректні дані й очікувані дії vs некоректні дані й неочікувані дії (система має коректно відмовити) |
| Alpha vs beta? | alpha — внутрішнє приймальне тестування; beta — на реальних користувачах до повного релізу |

> [!TIP]
> Якщо не знаєш відповіді, не вигадуй. Скажи: «Точного визначення не пам'ятаю, але як я це розумію…» і поясни на прикладі. Чесність і логіка цінуються більше за завчений термін.

## Ситуаційні питання

Ними перевіряють мислення і поведінку. Скелет відповіді: **уточню → зберу факти → дію → повідомлю**.

| Ситуація | Що сказати |
|---|---|
| Баг не відтворюється | уточню середовище (браузер, акаунт, дані), перевірю логи, Network, консоль; спробую інші дані й послідовність; якщо ні — опишу, що відомо, з частотою «intermittent», додам відео |
| Розробник каже «це не баг» | спокійно звернуся до вимоги або до впливу на користувача; якщо вимоги немає — до продакта, щоб він вирішив; без суперечки «хто правий» |
| Реліз завтра, знайдено критичний баг | одразу повідомлю тімліда і продакта з фактами (що, де, вплив, як відтворити); рішення «релізити чи ні» приймає команда, моя задача — дати інформацію |
| Вимог немає | спитаю продакта / аналітика, подивлюся на схожі продукти, конкурентів, старі версії; запишу свої припущення і узгоджу їх |
| Як зрозуміти, що тестування достатньо? | виконані exit criteria: критичні сценарії пройдені, немає відкритих blocker/critical, ризики названо; тестування завжди обмежене часом |
| Ти пропустив баг у продакшн | визнаю, допоможу відтворити й перевірити фікс, додам перевірку в чекліст / автотест, розберу, чому пропустили |
| Мало часу на тестування | пріоритети за ризиками: smoke і критичні шляхи спершу, решту — що встигну; повідомлю, що не перевірено |

## Класика: «Протестуй ліфт»

Питання на мислення, а не на правильну відповідь. Так само питають про ручку, чайник, тостер, калькулятор чи форму оплати. Покажи **структуру**:

1. **Уточни вимоги**: скільки поверхів, вантажопідйомність, чи є підземний паркінг, чи потрібна картка доступу.
2. **Функціональні перевірки**: виклик з кожного поверху, вибір поверху, двері (відкриття, закриття, перешкода), кнопки «відкрити» / «закрити».
3. **Граничні значення**: перший і останній поверх, вантаж рівно на межі (і +1 кг → сигнал перевантаження).
4. **Негативні сценарії**: натиснути всі кнопки одразу, неіснуючий поверх, відкрити двері під час руху.
5. **Нефункціональні**: безпека (аварійна кнопка, зв'язок, зупинка при відключенні світла), швидкість, шум, доступність (шрифт Брайля, голосові оголошення), навантаження в час пік.

> [!QA]
> Інтерв'юер оцінює, чи ставиш ти питання перед тестуванням, чи думаєш про межі й негативні сценарії і чи згадуєш нефункціональні аспекти. Так само ти мислиш про будь-яку фічу на роботі. Більше практичних задач такого типу — в уроці 9 цього модуля.

## Як готуватися

- Пройди банк питань **уголос**: письмова відповідь у голові часто «розвалюється», коли її треба сказати.
- Квіз цього уроку щоразу бере нову вибірку. Проходь його кілька разів, поки не буде 100 %.
- Запиши 2–3 відповіді на диктофон і послухай: чи є приклад, чи немає «води».

## Підсумок

- Формула відповіді: визначення → приклад → навіщо це QA.
- Повтори ключові пари: error/defect/failure, severity/priority, verification/validation, smoke/sanity/regression/retest.
- Ситуаційні питання: уточню → зберу факти → дію → повідомлю; без звинувачень.
- «Протестуй предмет»: уточнити вимоги → функціональні → межі → негативні → нефункціональні.
- Не знаєш — чесно скажи і поясни міркування.
