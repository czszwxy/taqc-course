# Співбесіда: теорія тестування

Навіть на позицію QA Automation перша частина співбесіди майже завжди про **теорію тестування**. Інтерв'юер перевіряє, чи розумієш ти, **що** і **навіщо** тестувати. Інструменти другорядні. Добра новина: модулі 01–06 уже дали тобі всі відповіді. Залишилось навчитися їх **говорити**.

## Формула доброї відповіді

1. **Визначення** — одним-двома реченнями, своїми словами.
2. **Приклад** — з реального або навчального проєкту (Gadgetly, Taskly).
3. **Навіщо це QA** — як це впливає на роботу.

> Питання: «Чим severity відрізняється від priority?»
>
> **Відповідь**: «Severity — наскільки дефект впливає на систему, priority — наскільки терміново його виправляти. Зазвичай вони збігаються, але не завжди. Друкарська помилка в назві компанії на головній сторінці має низьку severity, але високий priority. А падіння рідкісного звіту для адміна — висока severity, але priority може бути середнім. Severity зазвичай ставить QA, а priority — продакт або тімлід».

## Часті питання (коротко)

| Питання | Суть відповіді |
|---|---|
| Error, defect, failure? | помилка людини → дефект у коді → збій під час виконання |
| Verification vs validation? | «чи правильно робимо продукт» (за специфікацією) vs «чи робимо правильний продукт» (для користувача) |
| Smoke, sanity, regression? | smoke — базова працездатність білда; sanity — швидка перевірка конкретної зміни; regression — нічого старого не зламалося |
| Рівні тестування? | unit → integration → system → acceptance |
| Чорна / біла / сіра скринька? | без знання коду / зі знанням коду / частково (наприклад, перевірка БД після дії в UI) |
| Техніки тест-дизайну? | класи еквівалентності, граничні значення, таблиці рішень, переходи станів, попарне тестування, error guessing |
| Що таке баг-репорт і що в ньому? | заголовок, середовище, кроки, actual, expected, severity/priority, вкладення |
| Життєвий цикл бага? | New → Assigned → In progress → Fixed → Retest → Closed / Reopened (+ Rejected, Duplicate, Deferred) |
| Тест-кейс vs чекліст? | детальні кроки й очікування vs список перевірок без деталей |
| Принципи тестування? | тестування показує наявність дефектів, а не їх відсутність; вичерпне тестування неможливе; раннє тестування; скупчення дефектів; парадокс пестициду; залежить від контексту; «відсутність помилок» — оманлива ідея |

> [!TIP]
> Якщо не знаєш відповіді, не вигадуй. Скажи: «Точного визначення не пам'ятаю, але як я це розумію…» і поясни на прикладі. Чесність і логіка цінуються більше за завчений термін.

## Класика: «Протестуй ліфт»

Питання на мислення, а не на правильну відповідь. Покажи **структуру**:

1. **Уточни вимоги**: скільки поверхів, вантажопідйомність, чи є підземний паркінг, чи потрібна картка доступу.
2. **Функціональні перевірки**: виклик з кожного поверху, вибір поверху, двері (відкриття, закриття, перешкода), кнопки «відкрити» / «закрити».
3. **Граничні значення**: перший і останній поверх, вантаж рівно на межі (і +1 кг → сигнал перевантаження).
4. **Негативні сценарії**: натиснути всі кнопки одразу, неіснуючий поверх, відкрити двері під час руху.
5. **Нефункціональні**: безпека (аварійна кнопка, зв'язок, зупинка при відключенні світла), швидкість, шум, доступність (шрифт Брайля, голосові оголошення), навантаження в час пік.

> [!QA]
> Інтерв'юер оцінює, чи ставиш ти питання перед тестуванням, чи думаєш про межі й негативні сценарії і чи згадуєш нефункціональні аспекти. Так само ти мислиш про будь-яку фічу на роботі.

## Підсумок

- Формула відповіді: визначення → приклад → навіщо це QA.
- Повтори ключові пари: error/defect/failure, severity/priority, verification/validation, smoke/sanity/regression.
- «Протестуй предмет»: уточнити вимоги → функціональні → межі → негативні → нефункціональні.
- Не знаєш — чесно скажи і поясни міркування.
