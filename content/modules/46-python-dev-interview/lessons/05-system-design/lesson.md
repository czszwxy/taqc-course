# Основи system design для джуна

Від джуна не чекають, що він спроєктує Instagram. Але питання «як би ти зробив(ла) цю фічу?» або «спроєктуй сервіс коротких посилань» трапляються навіть на junior-позиціях. Інтерв'юер дивиться на **структуру мислення**: чи питаєш ти про вимоги, чи рахуєш навантаження, чи знаєш основні будівельні блоки і чи бачиш компроміси. Чесне «у продакшені я такого не робив(ла), але почав(ла) б так…» — нормальна відповідь.

## Шість кроків

| Крок | Що робиш | Приклад: галерея фото для клубу фотографів |
|---|---|---|
| 1. Вимоги | що система **робить** і **наскільки добре** (користувачі, затримка, доступність) | завантажити фото, переглядати альбоми; 20 тис. користувачів, фото до 10 МБ |
| 2. Оцінка | грубі числа: запити за секунду, обсяг даних | 2 000 фото на день × 5 МБ = 10 ГБ на день, ~3,6 ТБ на рік |
| 3. API | основні ендпоінти | `POST /photos/upload-url`, `GET /albums/{id}/photos` |
| 4. Дані | таблиці, ключі, що де зберігається | метадані — у PostgreSQL, самі файли — в об'єктному сховищі |
| 5. Схема | компоненти й шлях запиту | клієнт → балансувальник → застосунок → база; файли — напряму в сховище |
| 6. Вузькі місця | що впаде першим і як масштабувати; компроміси | генерація мініатюр — у чергу; роздача — через CDN |

Не починай з кроку 5. Без вимог і чисел будь-яка схема — вгадування.

## Оцінка «на серветці»

Точність не потрібна — потрібен порядок величини.

- У добі **86 400 секунд**, приблизно 10⁵. Тож 1 млн запитів на добу ≈ **12 запитів за секунду** в середньому.
- Пік зазвичай у кілька разів вищий за середнє — закладай ×5–10.
- Обсяг: кількість записів × розмір запису × час зберігання.
- Один екземпляр звичайного Python-застосунку з базою витримує десятки–сотні простих запитів за секунду, тож 12 запитів за секунду — це не «високе навантаження». Сказати це вголос — плюс.

## Будівельні блоки

| Блок | Навіщо | Компроміс |
|---|---|---|
| Балансувальник + кілька екземплярів застосунку | більше запитів, без простою при падінні одного | застосунок має бути **без стану** — сесії й файли не на диску сервера |
| Кеш (Redis) | швидкі читання того, що змінюється рідко | застарілі дані, інвалідація |
| Черга + воркери (Celery, RQ) | довгі й ненадійні операції поза запитом | at-least-once → ідемпотентні обробники |
| Об'єктне сховище + CDN | файли, фото, відео; швидка роздача по світу | кешування CDN треба інвалідувати |
| Репліка для читання | важкі `SELECT` (звіти) не заважають запису | **затримка реплікації**: щойно записане може ще не бути на репліці |
| Пошуковий рушій (OpenSearch, Elasticsearch) | повнотекстовий пошук, помилки в словах, релевантність | ще одна система, яку треба синхронізувати з базою |
| Обмеження частоти (rate limiter) | захист від надто активних клієнтів (`429`) | легітимні клієнти теж можуть упертися в ліміт |
| Планувальник (cron, Celery beat) | регулярні задачі: нічні перерахунки, прибирання | задача не має запускатися двічі паралельно |

## Приклад: завантаження фото

```text
клієнт ──POST /photos/upload-url──▶ застосунок ──▶ PostgreSQL (запис "pending")
клієнт ──PUT файл за підписаним URL──▶ об'єктне сховище
сховище ──подія "файл є"──▶ черга ──▶ воркер: мініатюри, статус "ready"
переглядач ──GET мініатюри──▶ CDN ──(промах)──▶ об'єктне сховище
```

Чому так: великий файл не проходить через застосунок (він не тримає воркер на 10 МБ), мініатюри робляться у фоні і не сповільнюють відповідь, а роздача через CDN не навантажує ні застосунок, ні сховище.

## Масштабування і узгодженість

- **Вертикальне** масштабування — більший сервер: просто, але має стелю. **Горизонтальне** — більше серверів: потрібен застосунок без стану.
- Зазвичай першою не встигає **база**. Порядок ліків: індекси й оптимізація запитів → кеш → репліки для читання → поділ даних (шардинг) — останнім, бо він найскладніший.
- **Кінцева узгодженість** (eventual consistency): дані на всіх копіях стануть однаковими, але не миттєво. Лічильник переглядів може відставати на кілька секунд — це прийнятно; баланс рахунку — ні. Уміння сказати, де яка узгодженість потрібна, — сильна відповідь.

> [!TIP]
> Закінчуй відповідь коротким підсумком і переліком того, що ти **свідомо не робив(ла)**: «Без мікросервісів — один застосунок, бо команда маленька; шардинг не потрібен на 4 ТБ на рік; якщо фото стане в 10 разів більше — додамо…». Це показує, що ти бачиш межі свого рішення.

## Типові помилки

- Одразу малювати мікросервіси, Kubernetes і Kafka для 12 запитів за секунду.
- Не спитати про вимоги й не назвати жодного числа.
- Описувати всі деталі одного компонента і не дійти до основного шляху запиту.
- Не назвати жодного компромісу: «кеш робить швидше» без «але дані можуть бути застарілими».
- Мовчати про збої: що, якщо впаде воркер, черга, база?

## Підсумок

- Вимоги → оцінка → API → дані → схема → вузькі місця й компроміси.
- 1 млн запитів на добу ≈ 12 за секунду; пік ×5–10.
- Знай будівельні блоки і **ціну** кожного.
- Застосунок без стану масштабується горизонтально; база зазвичай — перше вузьке місце.
- Говори про узгодженість і збої, а наприкінці — що свідомо не робиш.
