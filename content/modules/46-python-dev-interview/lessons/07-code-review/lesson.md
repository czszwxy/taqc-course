# Код-рев'ю на співбесіді

Дедалі більше компаній замість чи на додачу до алгоритмічних задач дають **рев'ю чужого коду**: 50–100 рядків PR і 20–30 хвилин. Причина проста: у роботі ти читатимеш код частіше, ніж писатимеш. Інтерв'юер дивиться, **що** ти знаходиш, **у якому порядку** і **як** про це говориш.

## Порядок перевірки

Не читай рядок за рядком, коментуючи все підряд. Іди від найважливішого:

| Крок | Питання |
|---|---|
| 1. Коректність | чи робить код те, що в задачі? межі, `None`, порожні дані, помилки |
| 2. Безпека | ін'єкції, перевірка прав, валідація вводу, секрети в коді |
| 3. Цілісність даних | транзакції, гонки, повторні запити, міграції |
| 4. Продуктивність | N+1, завантаження всієї таблиці, блокувальні виклики в `async def` |
| 5. Надійність | тайм-аути, обробка помилок зовнішніх сервісів, логи |
| 6. Тести | чи перевірено нову поведінку і межі |
| 7. Читабельність | імена, розмір функцій, дублювання |
| 8. Стиль | лишити лінтеру (ruff) і форматеру |

## Рівні важливості

| Рівень | Значення | Приклад |
|---|---|---|
| **Blocker** | зливати не можна: баг, діра в безпеці, втрата даних | SQL з даними користувача через f-рядок |
| **Should fix** | важливо, але не ламає продукт прямо зараз | немає тесту на межу, N+1 на сторінці з 20 рядками |
| **Nit** | дрібниця, на розсуд автора | «`d` → `discount`?», порядок імпортів |

Позначай рівень явно: `blocker:`, `nit:`. Так автор PR розуміє, з чого почати, а інтерв'юер бачить, що ти вмієш розставляти пріоритети.

## Як писати коментар

Коментар — про **код**, а не про людину; з **причиною** і **пропозицією**.

| Погано | Добре |
|---|---|
| «Це неправильно» | «blocker: `q` іде в SQL через f-рядок — ін'єкція (`' OR 1=1 --`). Передай параметром: `execute(\"... LIKE ?\", (f\"%{q}%\",))`» |
| «Навіщо тут цикл??» | «should fix: тут запит до бази на кожен тікет (N+1). Можна одним `JOIN`, або `selectinload` в ORM» |
| «Перейменуй» | «nit: `res` → `open_tickets`? Так легше читати нижче» |

Питання теж працюють: «Що буде, якщо агент ще не призначений?» — інколи автор знає те, чого не знаєш ти. І відзнач добре: «Гарно, що час приходить залежністю — тест простий».

## Розбір: ендпоінт пошуку в службі підтримки

```python
@app.get("/tickets/search")
def search(q: str, db=Depends(get_db)):
    rows = db.execute(f"SELECT * FROM tickets WHERE title LIKE '%{q}%'").fetchall()
    result = []
    for row in rows:
        agent = db.execute("SELECT name FROM agents WHERE id = ?", (row.agent_id,)).fetchone()
        result.append({**row._mapping, "agent": agent.name})
    return result
```

1. **blocker**: SQL-ін'єкція — `q` вставлено в запит f-рядком.
2. **blocker**: тікет без агента (`agent_id` = `NULL`) → `agent` = `None` → `AttributeError` → `500`.
3. **should fix**: N+1 — окремий запит на кожен тікет; один `LEFT JOIN agents`.
4. **should fix**: немає `LIMIT` — пошук «а» поверне всю таблицю.
5. **should fix**: `SELECT *` віддає назовні всі стовпці, зокрема внутрішні; краще модель відповіді з потрібними полями.
6. **question**: чи всі користувачі можуть шукати всі тікети, чи потрібна перевірка прав?

## Червоні прапорці в Python-бекенді

- SQL через f-рядок або `+` замість параметрів.
- Запит у циклі (N+1).
- `requests`, `time.sleep`, важкі обчислення всередині `async def` — блокують цикл подій.
- Вихідний HTTP-виклик без `timeout`.
- `except Exception: pass` — помилка зникає без сліду; `raise` нового винятку без `from`.
- `float` для грошей.
- Немає перевірки, що ресурс належить користувачу.
- Змінюваний аргумент за замовчуванням.
- `datetime.now()` без часового поясу поруч з датами, що мають пояс.
- Секрети в коді, `print` замість логера.
- Зміна статусу без перевірки результату зовнішнього виклику (повернення коштів «пройшло», хоча банк відмовив).

> [!TIP]
> На співбесіді спершу проговори 2–3 найважливіші проблеми, а дрібниці — наприкінці й коротко. Десять зауважень про пробіли без жодного про ін'єкцію — найгірший результат.

## Тести в PR

Перевір, чи тести ловлять саме нову поведінку: прибери в голові новий рядок коду — чи впаде хоч один тест? Чи є межі (рівно ліміт, `None`, порожній список)? Чи не залежать тести від справжнього часу й мережі?

## Типові помилки на співбесіді

- Лише стиль і жодної змістовної проблеми.
- Список без пріоритетів — автор не знає, з чого почати.
- Різкий тон: «хто так пише?».
- «Я б переписав(ла) все» замість конкретних змін.
- Не спитати про контекст: можливо, `float` тут — координати, а не гроші.

## Підсумок

- Порядок: коректність → безпека → дані → продуктивність → надійність → тести → читабельність → стиль.
- Позначай рівень: blocker / should fix / nit.
- Коментар = проблема + причина + пропозиція, про код, а не про людину.
- Знай червоні прапорці: ін'єкції, N+1, блокування в async, без тайм-ауту, проковтнуті винятки, float для грошей, перевірка прав.
- Починай з найважливішого і відзначай хороше.
