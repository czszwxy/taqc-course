# SQL на співбесіді

На співбесіді Python-розробника SQL є майже завжди: написати запит на дошці чи в редакторі, пояснити, чому запит повільний, розповісти про транзакції. Основи — `SELECT`, `JOIN`, `GROUP BY` — ти вже знаєш з модуля «SQL for Testers», а роботу з базою з Python — з модуля про SQLAlchemy. Тут — те, чим відрізняється співбесіда розробника: **віконні функції, індекси та ізоляція транзакцій**.

Приклади в теорії — про бібліотеку з таблицями `books (id, title, genre, pages)` і `loans (id, book_id, reader_id, taken_on)`. У задачах — база магазину.

## Логічний порядок виконання

Запит пишуть в одному порядку, а база «думає» в іншому:

| Крок | Частина | Наслідок |
|---|---|---|
| 1 | `FROM`, `JOIN` | спершу збирається таблиця рядків |
| 2 | `WHERE` | фільтр **окремих рядків**; агрегатів ще немає |
| 3 | `GROUP BY` | рядки складаються в групи |
| 4 | `HAVING` | фільтр **груп** — тут можна `COUNT(*) > 1` |
| 5 | `SELECT` | обчислюються вирази й **віконні функції** |
| 6 | `DISTINCT`, `ORDER BY` | сортування бачить псевдоніми з `SELECT` |
| 7 | `LIMIT`, `OFFSET` | відрізається потрібна частина |

Звідси дві пастки: `WHERE COUNT(*) > 1` — помилка (агрегат ще не порахований, треба `HAVING`), а віконну функцію не можна поставити у `WHERE` — її результат з'являється лише на кроці 5. Тому «топ-N у групі» пишуть через підзапит або CTE.

## NULL і COUNT

- `x = NULL` ніколи не правда — тільки `x IS NULL`.
- `COUNT(*)` рахує рядки, `COUNT(column)` — лише не-`NULL` значення. Після `LEFT JOIN` це різні числа.
- `NOT IN (SELECT reader_id FROM loans)` поверне **нуль рядків**, якщо в підзапиті є хоч один `NULL`. Безпечніше `NOT EXISTS` або `LEFT JOIN ... WHERE ... IS NULL`.

## CTE

`WITH` дає підзапиту ім'я — запит читається зверху вниз, як код з проміжними змінними:

```sql
WITH busy_readers AS (
    SELECT reader_id, COUNT(*) AS loans_count
    FROM loans
    GROUP BY reader_id
)
SELECT reader_id FROM busy_readers WHERE loans_count >= 10;
```

## Віконні функції

Агрегат з `GROUP BY` **згортає** рядки в один на групу. Віконна функція рахує щось по групі рядків, але **лишає кожен рядок**:

```sql
SELECT title, genre, pages,
       ROW_NUMBER() OVER (PARTITION BY genre ORDER BY pages DESC) AS place
FROM books;
```

- `PARTITION BY` — на які групи ділити (як `GROUP BY`, але без згортання); без нього вікно — уся таблиця.
- `ORDER BY` усередині `OVER` — порядок у групі.

Різниця між трьома функціями нумерації — на однакових значеннях:

| `pages` | `ROW_NUMBER()` | `RANK()` | `DENSE_RANK()` |
|---|---|---|---|
| 600 | 1 | 1 | 1 |
| 450 | 2 | 2 | 2 |
| 450 | 3 | 2 | 2 |
| 300 | 4 | 4 | 3 |

Інші часті віконні функції:

- `SUM(pages) OVER (ORDER BY taken_on)` — **наростаючий підсумок**: сума від початку до поточного рядка (рядки з однаковим значенням сортування потрапляють разом);
- `LAG(taken_on) OVER (PARTITION BY reader_id ORDER BY taken_on)` — значення з **попереднього** рядка групи (`LEAD` — з наступного); для першого — `NULL`;
- `AVG(pages) OVER (PARTITION BY genre)` — середнє по жанру поруч з кожною книжкою.

Шаблон «топ-N у кожній групі»:

```sql
WITH ranked AS (
    SELECT title, genre, ROW_NUMBER() OVER (PARTITION BY genre ORDER BY pages DESC) AS place
    FROM books
)
SELECT title, genre FROM ranked WHERE place <= 3;
```

## Класичні задачі

| Задача | Підхід |
|---|---|
| Друге за величиною значення | `MAX(x) WHERE x < (SELECT MAX(x) ...)` або `DISTINCT ... ORDER BY x DESC LIMIT 1 OFFSET 1` |
| Дублікати | `GROUP BY ... HAVING COUNT(*) > 1` |
| Рядки без пари | `LEFT JOIN ... WHERE right.id IS NULL` або `NOT EXISTS` |
| «Усі / жоден» у групі | `HAVING SUM(CASE WHEN ... THEN 1 ELSE 0 END) = 0` |
| Топ-N у групі | `ROW_NUMBER()` у CTE, потім `WHERE place <= N` |
| Наростаючий підсумок | `SUM(...) OVER (ORDER BY ...)` |
| Порівняння з попереднім | `LAG(...)` |

## Індекси

Індекс (найчастіше **B-tree**) — відсортована копія значень стовпця з посиланнями на рядки. Він прискорює пошук за рівністю й діапазоном, `JOIN` за ключем і `ORDER BY`, але **сповільнює запис** (кожен `INSERT` / `UPDATE` оновлює індекси) і займає місце.

**Складений індекс** `(reader_id, taken_on)` працює як телефонний довідник «прізвище, ім'я»: за прізвищем шукати швидко, за прізвищем і ім'ям — теж, а лише за ім'ям — ні. Це правило **крайнього лівого стовпця**.

Коли звичайний індекс не допоможе:

- функція чи обчислення над стовпцем: `WHERE lower(title) = 'dune'` (потрібен індекс за виразом);
- шаблон з `%` на початку: `LIKE '%dune'`;
- умова лише за другим стовпцем складеного індексу (деякі бази вміють «skip scan», але це виняток, а не правило);
- умова, під яку підходить більшість рядків: базі дешевше прочитати всю таблицю.

Як перевірити — `EXPLAIN` (у PostgreSQL `EXPLAIN ANALYZE` ще й виконує запит і показує реальний час). Це сильна відповідь на «що робити з повільним запитом?»: **подивитися план**, а не вгадувати.

## Транзакції й ізоляція

ACID: атомарність (усе або нічого), узгодженість (обмеження виконуються), ізоляція (паралельні транзакції не заважають одна одній — наскільки дозволяє рівень), довговічність (після коміту дані не зникнуть).

| Аномалія | Що відбувається |
|---|---|
| Брудне читання | бачиш незакомічені зміни іншої транзакції |
| Неповторюване читання | той самий рядок, прочитаний двічі, має різні значення |
| Фантомне читання | той самий `WHERE` повертає інший набір рядків |
| Втрачене оновлення | дві транзакції читають `stock = 5`, обидві пишуть `4` — один продаж зник |

Рівні ізоляції: Read Uncommitted, **Read Committed** (за замовчуванням у PostgreSQL), Repeatable Read (за замовчуванням у MySQL InnoDB), Serializable. Що вищий рівень — то менше аномалій і більше блокувань або повторів транзакцій.

Втрачене оновлення найчастіше лікують атомарною умовною зміною, як у модулі про бази: `UPDATE books SET copies = copies - 1 WHERE id = ? AND copies > 0` і перевірка `rowcount`. Інший варіант — `SELECT ... FOR UPDATE`, що блокує рядок до кінця транзакції.

> [!TIP]
> Пиши запит на співбесіді по кроках уголос: «спершу зберу рядки з `JOIN`, відфільтрую скасовані, згрупую…». Почни з `SELECT *` на маленькому прикладі в голові, потім додавай частини. І завжди питай про `NULL` і однакові значення — це половина помилок.

## Підсумок

- Порядок: `FROM` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` (вікна) → `ORDER BY` → `LIMIT`.
- `HAVING` — для умов на агрегати; віконні функції фільтрують через CTE.
- `ROW_NUMBER` / `RANK` / `DENSE_RANK` розходяться на однакових значеннях.
- `NOT IN` з `NULL` дає порожній результат — бери `NOT EXISTS`.
- Індекс: швидке читання, повільніший запис; крайній лівий стовпець; функції й `%` на початку його вимикають; перевіряй `EXPLAIN`.
- Read Committed — типовий за замовчуванням; втрачене оновлення — атомарний `UPDATE ... WHERE` або `FOR UPDATE`.
