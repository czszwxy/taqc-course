# Тестове завдання на FastAPI

Багато компаній замість (або після) live coding дають **тестове завдання**: невеликий сервіс за брифом, 4–8 годин роботи і кілька днів на здачу. Тестове показує те, чого не видно за 40 хвилин співбесіди: як ти структуруєш проєкт, пишеш тести, обробляєш помилки й пояснюєш рішення. А потім часто є **розмова про твій код** — тож кожен рядок треба вміти пояснити.

## Читаємо бриф

Приклад брифу для бібліотеки: «Сервіс видачі книжок: читач бере книжку, повертає, бачить свої видачі. Не більше 5 книжок одночасно, термін — 30 днів, за прострочку — блокування нових видач».

1. Випиши **вимоги** списком — кожна стане тестом.
2. Випиши **неоднозначності**: «30 днів» — включно? Що з книжкою, якої немає в наявності? Блокування — до повернення чи на час? Хто такий «читач» — потрібна автентифікація?
3. Надішли питання рекрутеру одним листом. Це **плюс**, а не слабкість. Якщо відповіді немає — обери розумне припущення і запиши його в README.

## План на обмежений час

| Час | Що |
|---|---|
| 30 хв | бриф, питання, план, структура репозиторію |
| 2 год | доменна логіка без FastAPI + тести на межі |
| 1,5 год | HTTP-шар: моделі Pydantic, ендпоінти, коди помилок, тести API |
| 1 год | README, перевірка «з нуля», прибирання |
| запас | Docker / compose, лінтер — лише якщо основне готове |

Головне правило: **спершу робоче ядро з тестами**, потім «прикраси». Нескінчений проєкт з Docker і CI програє простому, але завершеному.

## Структура репозиторію

```text
library-loans/
├── app/
│   ├── domain.py      ← правила: видати, повернути, прострочка (без FastAPI)
│   ├── schemas.py     ← моделі Pydantic для запитів і відповідей
│   ├── api.py         ← ендпоінти, залежності, коди помилок
│   └── main.py        ← створення app, підключення роутерів
├── tests/
│   ├── test_domain.py
│   └── test_api.py
├── pyproject.toml     ← залежності з версіями, налаштування pytest
├── README.md
└── .gitignore         ← .venv/, __pycache__/, .env
```

Чому домен окремо: правила тестуються простими функціями, без HTTP і бази, — швидко і на всі межі. HTTP-шар лише перекладає запит у виклики домену й доменні помилки в коди статусу. Час (`now`) і сховище приходять **залежностями** — тест підмінить їх через `app.dependency_overrides`, як ти робив(ла) в модулі про FastAPI.

## Що перевіряє рев'юер

| Що | Як перевіряють |
|---|---|
| Запускається | клонують і виконують команди з README — дослівно |
| Коректність | вимоги брифу, межі, некоректні дані |
| Тести | чи є, чи зелені, чи перевіряють межі, а не лише «щасливий шлях» |
| Помилки | зрозумілі коди й тіла (`400` з кодом помилки, `422` від валідації), жодних `500` на поганий ввід |
| Структура | домен окремо від фреймворку, зрозумілі імена, без мертвого коду |
| Історія git | невеликі коміти з осмисленими повідомленнями, а не один «done» |
| Безпека | жодних паролів і ключів у репозиторії, `.env` у `.gitignore` |
| Пояснення | README: припущення, рішення, що зробив(ла) б далі |

## Тести

- **Домен**: межі — рівно ліміт і на одиницю більше, момент закінчення терміну і секунду до нього, порожні дані.
- **API**: `TestClient`, підміна часу й даних через `dependency_overrides`; на кожен код помилки — тест.
- Один наскрізний сценарій: «взяв → повернув → взяв знову».
- Тести мають бути **детерміновані**: жодного справжнього `datetime.now()` у перевірках.

## Після здачі: розмова про код

Готуйся до питань «чому так?», «що буде при 10× навантаженні?», «як додати X?», «що б ти змінив(ла)?». Якщо в тестовому допомагав ШІ-асистент — це часто дозволено, але **кожен рядок** має бути зрозумілим тобі: питання на кшталт «навіщо тут `Annotated`?» швидко показують, хто писав код.

> [!WARNING]
> Типові причини відмови після тестового: не запускається за README, немає тестів, `500` на некоректні дані, секрети в репозиторії, «геройська» архітектура (мікросервіси, Kafka) замість простого робочого рішення, і невміння пояснити власний код.

## Підсумок

- Бриф → вимоги списком → питання → припущення в README.
- Спершу домен з тестами, потім HTTP, потім README; Docker — лише якщо лишився час.
- Домен без фреймворку, час і дані — залежностями.
- Рев'юер запускає проєкт за README дослівно і шукає тести на межі.
- Будь готовий(а) пояснити кожен рядок на розмові після тестового.
