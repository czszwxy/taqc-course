# Питання про pytest і Playwright

Друга половина технічної співбесіди — інструменти. Тут перевіряють не визначення, а **досвід**: чи писав ти фікстури з прибиранням, чи стикався з нестабільними тестами, чи можеш за 20 хвилин написати робочий UI-тест і пояснити, чому він стабільний.

## Що питають і що за цим стоїть

| Питання | Що хочуть почути |
|---|---|
| «Як ти готуєш і прибираєш тестові дані?» | фікстура з `yield`, дані через API, кожен тест — свої дані |
| «Який scope ти обираєш для фікстури?» | незмінне — `session`, змінне — `function`; ризики спільного стану |
| «Як запускаєш лише smoke-тести?» | маркери, `-m smoke`, реєстрація маркерів, `--strict-markers` |
| «Як тестуєш з різними даними?» | `parametrize`, `ids`, `pytest.param` |
| «Які локатори обираєш?» | `get_by_role` / `get_by_label` / `get_by_test_id`, а не CSS-ланцюжки |
| «Навіщо `expect`, а не `assert`?» | авто-очікування, стабільність |
| «Як не логінитися в кожному тесті?» | storage state або токен з API |
| «Тест іноді падає. Що робиш?» | відтворити, трейс, причина, виправлення — не `sleep` і не `--reruns` |

> [!QA]
> На кожне питання відповідай **з власного коду**: «У модулі з API-тестами в мене була фікстура `order`: створює замовлення через `POST`, віддає тесту, після `yield` видаляє. Тому тести не залежать один від одного й не залишають сміття».

## Live coding UI-тесту за 20 хвилин

Формат: відкривають сторінку і кажуть «напиши кілька тестів». Що оцінюють:

| Критерій | Як виглядає добре |
|---|---|
| Вибір сценаріїв | спершу найважливіші вимоги, а не «кнопка має колір» |
| Локатори | ролі, підписи, `data-testid` |
| Перевірки | `expect(...)` з конкретним очікуваним значенням |
| Незалежність | кожен тест сам відкриває сторінку і готує стан |
| Читабельність | назва тесту = поведінка; Arrange → Act → Assert |
| Комунікація | проговорюєш, що перевіряєш і чому |

План на 20 хвилин: 2 хвилини — прочитати вимоги й вибрати 3–4 сценарії, 3 хвилини — перший тест до зеленого, далі — по тесту за 4–5 хвилин, наприкінці — проговорити, що ще перевірив би.

> [!TIP]
> Почни з **одного** зеленого тесту, а не з п'яти напівготових. Робочий тест показує, що ти вмієш запускати Playwright, а далі кожен новий — це вже швидка зміна.

## Рев'ю чужого тесту

Ще один популярний формат — «що не так з цим тестом?». Шукай за списком:

| Що перевірити | Червоний прапорець |
|---|---|
| Очікування | `time.sleep`, `wait_for_timeout`, `is_visible()` без `expect` |
| Локатори | `#root > div > div:nth-child(2)`, класи стилів |
| Незалежність | глобальні змінні між тестами, порядок виконання |
| Дані й секрети | пароль і повна адреса в коді |
| Перевірки | `assert r.status_code` (завжди істина), немає перевірки результату |
| Ресурси | свій `sync_playwright()` замість фікстури `page`, браузер не закритий |
| Назви | `test_1`, `test_2` |

## Типові помилки на цій частині співбесіди

- «Я завжди використовую `--reruns`» — звучить як «я ховаю нестабільні тести».
- Відповідь без прикладу: «фікстури — це для підготовки».
- На live coding — п'ять тестів без жодного запуску.
- На рев'ю — лише стильові зауваження, без головних проблем (sleep, залежність тестів, слабкі перевірки).

## Підсумок

- Питання про інструменти — це питання про досвід: відповідай прикладами зі свого коду.
- Live coding: вимоги → 3–4 сценарії → перший зелений тест → решта → що ще перевірив би.
- Добрий UI-тест: стійкі локатори, `expect` з конкретним значенням, незалежність, зрозуміла назва.
- Рев'ю: очікування, локатори, незалежність, секрети, сила перевірок, ресурси, назви.
