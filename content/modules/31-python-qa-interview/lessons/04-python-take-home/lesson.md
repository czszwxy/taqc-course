# Тестове завдання на Python

Після технічної співбесіди (або замість неї) часто дають **take-home**: «Ось застосунок і його API. Напиши автотести на Python, 3–4 години, надішли посилання на репозиторій». Рев'юер не запускає твій код у голові — він **клонує репозиторій і пробує його запустити**. Тому половина успіху — не самі тести, а те, як легко їх запустити й зрозуміти.

> [!QA]
> Take-home — це твоє портфоліо в мініатюрі. Рев'юер оцінює ті самі речі, що й тімлід на код-рев'ю: структуру, стабільність, ясність і професійні звички (секрети, залежності, README).

## Розбір брифа

| Крок | Що робиш |
|---|---|
| Прочитати двічі | виписати, що саме просять: API? UI? звіт про баги? CI? |
| Обмеження | час, мова, інструменти, формат здачі |
| Питання | якщо щось неясно — **одне листування** з уточненнями краще, ніж здогадки |
| Пріоритети | що найризиковіше для бізнесу — те й автоматизуєш першим |
| Межі | що свідомо **не** робиш — і пишеш про це в README |

## План на 4 години

| Час | Що |
|---|---|
| 0:00–0:30 | бриф, дослідження застосунку руками, список сценаріїв з пріоритетами |
| 0:30–1:00 | скелет проєкту: `pyproject.toml`, `requirements.txt`, `conftest.py`, перший зелений тест |
| 1:00–2:45 | тести за пріоритетом: API (швидко й стабільно), потім ключові UI-сценарії |
| 2:45–3:30 | прибрати, перевірити стабільність (`--count` або кілька прогонів), запуск з чистого клону |
| 3:30–4:00 | README: як запустити, що покрито, що ні й чому, знайдені проблеми |

## Структура репозиторію

```text
catalog-tests/
├── api/client.py            ← клієнт API каталогу
├── models/product.py        ← pydantic-модель товару
├── pages/catalog_page.py    ← page object сторінки пошуку
├── tests/
│   ├── api/test_products.py
│   └── ui/test_catalog.py
├── conftest.py              ← фікстури: налаштування, клієнт, page object
├── pyproject.toml           ← testpaths, markers, base_url
├── requirements.txt         ← зафіксовані версії
├── .gitignore               ← .venv, __pycache__, test-results, reports
└── README.md
```

Для маленького завдання можна й простіше — але шари (тести / page objects / клієнт / моделі) варто показати: це те, що рев'юер шукає.

## Що перевіряє рев'юер

| Перевірка | Що бачить, коли добре |
|---|---|
| Запуск за 5 хвилин | README з командами, `requirements.txt`, `python -m pytest` працює одразу |
| Структура | шари, а не один файл на 500 рядків |
| Якість тестів | одна поведінка на тест, конкретні перевірки, назви-описи |
| Стабільність | без `sleep`, `expect` з очікуванням, незалежні тести |
| Дані | тест сам створює й прибирає дані; немає залежності від порядку |
| Безпека | жодних паролів і токенів у коді та історії git |
| Історія git | кілька змістовних комітів, а не один «done» |
| Чесність | README каже, що не встиг і що зробив би далі |

## Червоні прапорці

- Закомічені `.venv/`, `__pycache__/`, звіти й трейси.
- `requirements.txt` без версій (або взагалі немає).
- Тести, що падають на «чистому» запуску — навіть один.
- Пароль тестового акаунта в коді.
- README з одним рядком «run pytest».
- Знайдені баги «сховані» через `skip` без пояснення.

> [!TIP]
> Якщо твій тест знаходить справжню проблему продукту — це плюс, а не мінус. Залиш тест червоним або познач `xfail(strict=True)` з посиланням на опис у `BUGS.md`, і напиши про це в README.

## Підсумок

- Take-home оцінюють, клонуючи й запускаючи: README і залежності — половина оцінки.
- Спершу план і пріоритети, потім скелет з першим зеленим тестом, далі тести за ризиком.
- Шари: тести, page objects, клієнт API, моделі, conftest, pyproject.
- Перед здачею — запуск з чистого клону, перевірка стабільності, жодних секретів.
- README чесно каже, що покрито, що ні, і що далі.
