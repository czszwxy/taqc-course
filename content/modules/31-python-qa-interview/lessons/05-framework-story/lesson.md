# Розповідь про свій Python-фреймворк

«Розкажи про свій фреймворк» — питання, яке ставлять майже на кожній співбесіді на Automation QA, і на ньому найлегше виділитися. Більшість кандидатів перелічує бібліотеки: «pytest, Playwright, requests». Сильна відповідь пояснює **рішення**: чому так побудовано, що це дало і що б ти змінив.

> [!QA]
> Інтерв'юер слухає не список технологій, а ознаки досвіду: ти знаєш, де тести ламаються, чому дані створюються через API, навіщо strict-маркери. Кожне «бо…» у відповіді важить більше, ніж назва ще одного плагіна.

## Структура відповіді

| Частина | Що сказати | Приклад |
|---|---|---|
| 1. Контекст | що тестує, обсяг, хто ти в проєкті | «Навчальний проєкт: API і UI магазину, ~40 тестів, робив сам» |
| 2. Архітектура | шари і як вони пов'язані | «tests → page objects / API-клієнт → моделі; фікстури в conftest» |
| 3. Рішення | 1–2 рішення з причиною і ціною | «Дані — через API у фікстурі з yield: швидко й без залежностей, але треба API» |
| 4. Стабільність | як тримаєш тести зеленими й чесними | «expect замість assert, свої дані на тест, без sleep, flaky — у карантин» |
| 5. CI і звіти | де й коли запускається, що бачить команда | «GitHub Actions на PR і вночі, JUnit, трейси упалих тестів» |
| 6. Що покращив би | чесно і конкретно | «Паралельний запуск і матриця браузерів» |

## Версія на 1 хвилину

> «Це мій фреймворк на Python для API і UI тестів інтернет-магазину. pytest — раннер, Playwright — браузер, requests і pydantic — API і контракти. Тести працюють через page objects і API-клієнт, а фікстури в conftest.py готують і прибирають дані через API, тож тести незалежні. Налаштування — зі змінних оточення, секрети — у GitHub Secrets. У CI на кожен pull request іде smoke, вночі — повна регресія; JUnit і трейси упалих тестів — в артефактах. Далі хочу додати матрицю браузерів».

Після короткої версії інтерв'юер сам вибере, у що заглибитися. Розгорнута версія (2–3 хвилини) — ті самі 6 частин з прикладами коду словами.

## Конкретика замість загальних слів

| Розмито | Конкретно |
|---|---|
| «Я використовую best practices» | «Локатори — за ролями й підписами; CSS лише там, де немає ні того, ні іншого» |
| «Тести стабільні» | «За останні 30 прогонів у CI — жодного flaky; перевіряв `--count=20` для нових тестів» |
| «Є звіти» | «JUnit для PR, HTML одним файлом, трейс для кожного упалого UI-тесту» |
| «Гарна архітектура» | «Зміна локатора кнопки — правка в одному page object, тести не чіпаю» |

## Чесність

Навчальний чи власний проєкт — це нормально для junior, і його не треба видавати за «комерційний досвід у команді». Кажи «я», а не «ми», якщо робив сам. Інтерв'юер легко перевіряє уточнювальними питаннями, а впіймана неправда закриває співбесіду. Сильний хід — показати, що ти **розумієш межі**: «тут у мене один браузер; у реальному проєкті я б додав матрицю».

## Типові уточнювальні питання

| Питання | Про що насправді |
|---|---|
| «Чому pytest, а не unittest?» | чи розумієш переваги фікстур і плагінів |
| «Чому page objects, а не просто функції?» | чи розумієш, навіщо інкапсулювати локатори |
| «Як готуєте й прибираєте дані?» | незалежність тестів |
| «Що робите з flaky-тестами?» | зрілість: причина, а не reruns |
| «Що зміниться, якщо тестів стане 2000?» | масштаб: паралельність, шардинг, теги, час прогону |
| «Що б ви зробили інакше?» | рефлексія і готовність вчитися |

## Як показати репозиторій

Якщо просять показати код: відкрий **README** (як запустити, структура), потім **один** UI-тест і його page object, потім **conftest.py** з фікстурою з `yield`, наостанок — workflow CI і останній зелений прогін. Не гортай усі файли підряд — веди за тією самою структурою, що й у розповіді.

## Типові помилки

- Перелік бібліотек без жодного «бо».
- 10 хвилин монологу без пауз — інтерв'юер не встигає поставити питання.
- «Ми» про проєкт, який робив сам; цифри, яких не можеш пояснити.
- «Нічого б не змінив» — звучить як відсутність рефлексії.
- Критика фреймворку попередньої команди замість власних рішень.

## Підсумок

- Структура: контекст → архітектура → рішення з причинами → стабільність → CI і звіти → що покращив би.
- Готуй версію на 1 хвилину і на 3 хвилини.
- Конкретні факти й «бо…» замість загальних слів.
- Чесно про масштаб і свою роль; межі проєкту — теж ознака розуміння.
- Підготуй відповіді на типові уточнення й маршрут показу репозиторію.
