# Шар бази даних

Правила готові. Тепер заявки треба зберігати, шукати й змінювати так, щоб дані не ламалися навіть тоді, коли двоє людей натискають кнопку одночасно. У цьому уроці три файли:

| Файл | Відповідає за | Робить commit? |
|---|---|---|
| `models.py` | таблиці, обмеження, зв'язки | — |
| `repository.py` | як знайти й зберегти заявки | **ні**, лише `flush` |
| `services.py` | один сценарій від початку до кінця | **так**, це межа транзакції |

> [!NOTE]
> Приклади знову з бібліотеки: видачі книжок (`Loan`) та їхня історія. Код Gadgetly Repairs — у задачах.

## Моделі: база теж перевіряє правила

Домен перевіряє правила в Python, але в базу можна потрапити й іншим шляхом: скриптом міграції, ручним `UPDATE`, кодом колеги. Тому найважливіші інваріанти дублюють **обмеженнями** в самій базі:

```python
class Loan(Base):
    __tablename__ = "loans"
    __table_args__ = (
        CheckConstraint("state IN ('reserved', 'on_loan', 'returned')", name="loan_state"),
        CheckConstraint("fine IS NULL OR fine >= 0", name="loan_fine"),
    )

    id: Mapped[int] = mapped_column(primary_key=True)
    reader_email: Mapped[str] = mapped_column(String(254), index=True)
    state: Mapped[str] = mapped_column(String(20), default="reserved")
    fine: Mapped[int | None]
    version: Mapped[int] = mapped_column(default=1)

    events: Mapped[list["LoanEvent"]] = relationship(
        back_populates="loan", cascade="all, delete-orphan", order_by="LoanEvent.id"
    )
```

- `Mapped[int | None]` — стовпець може бути `NULL`; просто `Mapped[int]` — `NOT NULL`.
- `index=True` на стовпці, за яким часто фільтрують (тут — «мої видачі»).
- `order_by` у `relationship` — історія завжди приходить у порядку подій, а не як заманеться базі.
- `cascade="all, delete-orphan"` — подія, прибрана зі списку, видаляється з бази; видалення видачі видаляє її історію.

> [!WARNING]
> `fine >= 0` і `fine IS NULL OR fine >= 0` — не одне й те саме для читача коду, хоча SQL пропустить `NULL` в обох. Пиши явно: так видно, що «немає штрафу» і «штраф 0» — різні стани.

## Репозиторій: пошук без commit

Репозиторій знає, **як** шукати, але не вирішує, **коли** фіксувати. Фільтри складаються з умов, що додаються лише тоді, коли параметр передано:

```python
def search(self, *, reader=None, state=None, limit=20, offset=0):
    query = select(Loan)
    if reader is not None:
        query = query.where(Loan.reader_email == reader)
    if state is not None:
        query = query.where(Loan.state == state)
    total = self.session.scalar(select(func.count()).select_from(query.subquery()))
    page = query.order_by(Loan.id).limit(limit).offset(offset)
    return list(self.session.scalars(page)), total
```

`total` рахує база одним `SELECT count(*)` по тому самому запиту, обгорнутому в підзапит. `len(self.session.scalars(query).all())` дав би те саме число, але завантажив би **всі** рядки в пам'ять. На 10 рядках різниці не видно, а на 100 000 сторінка списку стане секундною.

Сортування для сторінок має бути **повним**: якщо дві заявки мають однаковий дедлайн, без другого ключа (`id`) база може віддати їх у різному порядку на різних сторінках — і одна заявка з'явиться двічі, а інша зникне.

## Сервіс: один сценарій — одна транзакція

Зміна статусу — це кілька записів, які мають статися **разом або ніяк**: новий статус, рядок історії, повідомлення клієнту. Тому сценарій живе в одній функції сервісу, яка в кінці робить один `commit`. Якщо щось пішло не так раніше — нічого не записано.

## Оптимістичне блокування

Звичайний шлях «прочитав → перевірив у Python → записав» ламається, коли двоє роблять це одночасно: обидва прочитали версію 3, обидва перевірили, обидва записали. Друга зміна мовчки затерла першу.

Рішення — зробити перевірку й запис **одним** SQL-запитом:

```python
result = session.execute(
    update(Loan)
    .where(Loan.id == loan_id, Loan.version == version)
    .values(state="returned", version=Loan.version + 1)
)
if result.rowcount == 0:
    session.rollback()
    raise LoanError("conflict")
```

База виконує `UPDATE … WHERE id = ? AND version = ?` атомарно: якщо версію вже змінили, умова не збігається, оновлено **0 рядків**, і ми знаємо про конфлікт. `version=Loan.version + 1` — вираз SQL («поточне значення + 1»), а не число з Python.

> [!TIP]
> SQLAlchemy вміє робити це й сам (`version_id_col` у `__mapper_args__`). Ручний `update` корисно написати хоча б раз: так видно, що саме робить база, і це легко пояснити на співбесіді.

## Outbox: повідомлення в тій самій транзакції

Надсилати лист прямо в сервісі погано з двох боків:

| Порядок | Що може статися |
|---|---|
| спершу лист, потім `commit` | лист пішов, а `commit` упав — клієнт чекає готовий пристрій, якого немає |
| спершу `commit`, потім лист | статус змінено, а пошта недоступна — лист загубився назавжди |

**Outbox** (вихідна скринька): сервіс не надсилає лист, а **додає рядок** у таблицю повідомлень у тій самій транзакції. Або є і статус, і повідомлення, або немає нічого. Окремий процес потім читає скриньку й доставляє з повторами (урок 5).

```python
session.add(LoanEvent(loan_id=loan_id, kind="returned"))
if new_state == "on_loan":
    session.add(Message(loan_id=loan_id, recipient=email, text="Your book is waiting"))
session.commit()  # статус, подія і повідомлення — разом
```

## Як перевірити, що зафіксовано

Тест не довіряє об'єкту в пам'яті: він закриває сесію (незафіксоване відкочується) і читає дані **новою** `Session(engine)` — так, як побачить їх наступний запит. А щоб перевірити, що після помилки «нічого не лишилося», тест робить `commit` після винятку: якщо сервіс встиг додати рядок історії й не відкотив сесію, `commit` цей рядок збереже, і тест це побачить.

> [!QA]
> «Нічого не змінилося після помилки» — окремий тест для кожної гілки помилки: не знайдено, не та роль, немає переходу, стара версія. Саме там найчастіше лишаються напівзаписані дані.

## Підсумок

- Інваріанти — і в домені, і в базі (`CheckConstraint`); `NULL` дозволяй явно.
- Репозиторій лише `flush`; `total` рахує база через `count()` по підзапиту; сортування для сторінок — повне.
- Сервіс — межа транзакції: статус, історія й повідомлення фіксуються одним `commit`.
- Оптимістичне блокування — умовний `UPDATE … WHERE version = ?` і `rowcount == 0` → конфлікт.
- Outbox: повідомлення — рядок у тій самій транзакції; доставка — окремо.
