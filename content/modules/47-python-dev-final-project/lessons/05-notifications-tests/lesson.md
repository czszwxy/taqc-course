# Повідомлення й тести

У базі вже з'являються рядки `Notification` зі статусом `pending` — сервіс записує їх у тій самій транзакції, що й `ready`. Лишилося дві речі: **доставити** повідомлення, навіть коли пошта падає, і написати **тести**, які впіймають регресії в API.

> [!NOTE]
> Приклади — з бібліотеки: нагадування «повернути книжку завтра». Код Gadgetly Repairs — у задачах.

## Процес доставки

Процес доставки (worker) — звичайна функція, яку запускають за розкладом або в нескінченному циклі поруч з API. Перша версія, яку пишуть майже всі:

```python
def send_reminders(session, send):
    pending = session.scalars(
        select(Reminder).where(Reminder.status == "pending").order_by(Reminder.id)
    ).all()
    for reminder in pending:
        send(reminder.email, reminder.text)
        reminder.status = "sent"
    session.commit()
```

Вона працює, доки все добре. Що з нею не так:

| Проблема | Що станеться | Як виправити |
|---|---|---|
| немає `try` навколо `send` | одна недійсна адреса кидає виняток, і решта черги не доставляється ніколи | ловити `Exception` на **кожне** повідомлення й іти далі |
| один `commit` у кінці | процес упав на 50-му листі — перші 49 ще `pending` і підуть удруге | `commit` після **кожного** повідомлення |
| немає лічильника спроб | недійсна адреса повторюється вічно й забиває чергу | `attempts += 1` на кожну спробу, після N невдач — `failed` |
| причина невдачі губиться | ніхто не знає, чому лист не дійшов | зберігати `str(error)` у `last_error` |

Що в ній правильно: `send` — **параметр** (у тестах — фейк, що записує виклики й «падає» на потрібних адресах; у продакшні — клієнт пошти), і вибираються лише `pending` за `id` — надіслані не йдуть удруге, порядок передбачуваний.

## At-least-once: лист може прийти двічі

Навіть з `commit` після кожного повідомлення лишається вузьке місце: лист надіслано, а процес упав **до** `commit`. Після перезапуску повідомлення ще `pending`, і лист піде вдруге. Це гарантія **at-least-once** — «щонайменше один раз». «Рівно один раз» між двома різними системами (база і пошта) без їхньої співпраці не буває.

Що з цим роблять:

- передають одержувачу **ідентифікатор повідомлення** (наприклад, `notification-42`), і поштовий сервіс відкидає дублікат;
- роблять повідомлення безпечними для повтору: два однакові листи «пристрій готовий» неприємні, але нешкідливі.

> [!TIP]
> Те саме питання ставлять на співбесіді: «Що буде, якщо процес упаде між send і commit?». Хороша відповідь називає at-least-once і ідемпотентність одержувача, а не обіцяє «рівно один раз».

## Повтори й остаточна невдача

`attempts` рахує кожну спробу, а `last_error` зберігає причину останньої невдачі для того, хто розбиратиметься. Після `max_attempts` невдач повідомлення стає `failed` і більше не намагається: недійсна адреса ніколи не запрацює, а безкінечні повтори забивають чергу. У реальних системах між спробами ще роблять паузу, що зростає (exponential backoff) — поле `next_attempt_at` і умова в `select`.

## Де запускати worker

| Спосіб | Коли |
|---|---|
| окремий процес `python -m app.worker` з циклом і `sleep` | найпростіше; у compose — окремий сервіс з тим самим образом |
| розклад (cron, scheduled job у хмарі) раз на хвилину | коли запізнення на хвилину не критичне |
| черга (Celery, RQ, брокер) | коли повідомлень багато і потрібне масштабування |

Для портфоліо достатньо першого: другий сервіс у `compose.yaml` з тією самою базою.

## Стратегія тестів проєкту

| Шар | Чим тестувати | Що перевіряти | Скільки |
|---|---|---|---|
| домен (`repairs.py`) | прості функції | усі межі: дати, хвилини, гарантія, переходи | найбільше |
| база (`repository`, `services`) | SQLite в пам'яті, нова `Session` | фільтри, сторінки, транзакції, версії, «нічого не лишилося після помилки» | середньо |
| API (`app.py`) | `TestClient` + `dependency_overrides` | коди, формат помилок, ролі, чужі дані, валідація | середньо |
| повний сценарій | `TestClient` від створення до видачі | що шари з'єднано правильно | кілька |

Тест API не повторює всі межі домену: якщо `due_date` покрито двадцятьма тестами, API достатньо одного-двох, що він **викликає** `due_date` з правильним пріоритетом.

## Тести API

```python
@pytest.fixture
def client(engine):
    def test_session():
        with Session(engine) as session:
            yield session

    app.dependency_overrides[get_session] = test_session
    app.dependency_overrides[get_today] = lambda: date(2026, 11, 18)
    yield TestClient(app)
    app.dependency_overrides.clear()
```

`StaticPool` і `check_same_thread=False` у рушії потрібні, бо `TestClient` виконує синхронні ендпоінти в іншому потоці, а база в пам'яті живе в одному з'єднанні. Дані для тесту кладуть **прямо в базу** (`seed(...)`), а не через API: тест на `GET /tickets/1` не має падати через баг у `POST /tickets`.

> [!QA]
> Найцінніші тести API — ті, що ловлять **діри в безпеці**: клієнт бачить чужу заявку в списку, змінює чужу заявку, отримує `403` замість `404`. Їх пишуть першими, бо такий баг у продакшні — це витік даних.

## Підсумок

- Worker: лише `pending` за `id`, `send` — параметр, `except` на кожне повідомлення, `commit` після кожного.
- Гарантія — at-least-once; від дублікатів захищає ідентифікатор повідомлення в одержувача.
- `attempts`, `last_error`, `failed` після `max_attempts` — щоб черга не забивалася й причину було видно.
- Тести: межі — в домені, транзакції — на базі в пам'яті, коди й доступ — через `TestClient`, кілька повних сценаріїв.
- Дані для тестів API кладуть у базу напряму; залежності підмінюють і очищають після тесту.
