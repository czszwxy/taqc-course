# Бриф і план

Фінальний проєкт — це не ще одна задача «на тему уроку». Ти збереш **цілий бекенд** з того, що вже вмієш: правила на чистому Python, базу на SQLAlchemy, API на FastAPI, тести на pytest, Docker і CI. Кожен крок перевіряють приховані тести, як у звичайних задачах. Наприкінці модуля шматки складаються в окремий репозиторій, який можна показати роботодавцю.

> [!IMPORTANT]
> Кожен наступний крок отримує **еталон** попереднього як файл лише для читання. Помилка на кроці 2 не блокує крок 3: можна йти далі, а потім повернутися.

## Бриф

> **Gadgetly Repairs.** Gadgetly opens a service centre. Customers hand in a gadget, describe the problem and track the repair online. Staff diagnose the device, send a cost estimate, repair it after the customer agrees and hand it back. The customer gets a message when the device is ready. We need a REST API for the website and for the staff app.

Користувачі двох ролей:

| Роль | Хто це | Що робить |
|---|---|---|
| `customer` | клієнт магазину | створює заявку, бачить **лише свої** заявки, погоджує або відхиляє кошторис, може скасувати заявку, поки її не взяли в роботу |
| `staff` | майстер сервісного центру | бачить усі заявки, діагностує, надсилає кошторис, ремонтує, видає пристрій |

## Статуси заявки

Заявка (ticket) живе за простою машиною станів:

| Звідки | Куди | Хто може |
|---|---|---|
| `received` | `diagnosing` | staff |
| `received` | `cancelled` | customer, staff |
| `diagnosing` | `waiting_approval` | staff — **лише разом із кошторисом** |
| `diagnosing` | `cancelled` | staff |
| `waiting_approval` | `repairing` | customer (погодився) |
| `waiting_approval` | `cancelled` | customer (відмовився) |
| `repairing` | `ready` | staff |
| `ready` | `closed` | staff (пристрій видано) |

Будь-якого іншого переходу не існує: `closed` і `cancelled` — кінцеві статуси.

## Строки (SLA)

Строк ремонту рахується в **робочих днях** (пн–пт, без свят) від дня прийому. **День прийому не рахується**:

| Пріоритет | Робочих днів |
|---|---|
| `urgent` | 1 |
| `normal` (за замовчуванням) | 3 |
| `low` | 5 |

Приклад: прийнято в середу 18 листопада 2026, `normal` → чт (1), пт (2), сб і нд пропускаємо, пн 23 листопада (3) — це і є `due_on`.

Заявка **прострочена**, коли сьогодні **пізніше** за `due_on` (у сам день дедлайну — ще вчасно) і годинник SLA йде. Годинник іде в `received`, `diagnosing` і `repairing`. Поки клієнт думає над кошторисом (`waiting_approval`) або ремонт завершено (`ready`, `closed`, `cancelled`), заявка не може бути простроченою.

## Кошторис

- Деталі — за ціною з кошторису (цілі гривні).
- Робота — **150 грн за кожні розпочаті 15 хвилин**: 15 хв = 150, 16 хв = 300.
- **Гарантія** покриває роботу й деталі. Деталь, пошкоджену з вини клієнта (`accidental`), клієнт оплачує й за гарантією.
- Кошторис 0 грн (повністю гарантійний ремонт) — теж кошторис: клієнт однаково його погоджує.

Приклад: екран 2 400 + задня кришка 300 (`accidental`), 50 хвилин роботи. Без гарантії: 2 700 + 4 блоки × 150 = **3 300**. За гарантією: **300** (лише кришка).

## Повідомлення

Коли заявка стає `ready`, клієнт отримує лист: *«Your Phone X2 is ready for pickup (ticket #1).»* Поштовий сервіс буває недоступний, але це не причина ламати зміну статусу. Тому повідомлення спершу записується в базу, а окремий процес доставляє його з повторами (урок 5).

## Одночасні зміни

Двоє майстрів відкрили ту саму заявку, і обидва натискають кнопку. Друга зміна не повинна мовчки затерти першу. Тому в кожної заявки є `version`: клієнт API надсилає версію, яку бачив, і якщо заявку тим часом змінили, отримує `409 conflict`. Це **оптимістичне блокування** (урок 3).

## Шари проєкту

```text
API (FastAPI)          app.py         HTTP → виклики нижче → JSON; коди статусів
  │
Сервіси                services.py    один сценарій = одна транзакція (статус + історія + повідомлення)
  │
Репозиторій            repository.py  як знайти й зберегти заявки (фільтри, сторінки)
  │
Моделі                 models.py      таблиці й обмеження (SQLAlchemy)
  │
Домен                  repairs.py     правила: статуси, строки, кошторис — чистий Python
```

Кожен шар залежить лише від тих, що під ним. Правила в `repairs.py` не знають про HTTP і базу, тому їх тестують простими функціями на всі межі. API лише перекладає запити на виклики нижніх шарів, а їхні помилки — на коди статусів.

> [!TIP]
> Цей поділ — головна тема для розмови на співбесіді: «чому правила окремо від FastAPI», «де межа транзакції», «хто робить commit». Відповіді на ці питання — у твоєму коді.

## Як читати бриф

Бриф ніколи не буває повним. Розробник(ця) читає його з двома списками в голові:

1. **Питання** — що не сказано, але від чого залежить код. Наприклад, «чи може клієнт скасувати заявку під час діагностики?», «у якому часовому поясі рахуємо "сьогодні"?».
2. **Припущення** — що обереш, якщо відповіді не буде, щоб не стояти. Кожне припущення потрапляє в README і покривається тестом.

> [!WARNING]
> Найдорожча помилка на старті — мовчки вгадати. Питання, поставлене до написання коду, коштує хвилину. Неправильне правило, знайдене після релізу, коштує міграцію даних і листи клієнтам.

## Підсумок

- Gadgetly Repairs — API для двох ролей: `customer` бачить і змінює лише свої заявки, `staff` веде ремонт.
- Статуси й переходи задані таблицею, `closed` і `cancelled` — кінцеві.
- Строк = N робочих днів після дня прийому; прострочено лише після дедлайну і лише поки годинник SLA іде.
- Кошторис: деталі + 150 грн за кожні розпочаті 15 хвилин; гарантія не покриває `accidental` деталі.
- Повідомлення пишуться в базу й доставляються окремо; одночасні зміни ловить `version`.
- Шари: домен → моделі → репозиторій → сервіси → API, кожен тестується окремо.
