# Поєднання API і UI

UI-тест, що сам готує всі дані через інтерфейс, повільний і крихкий: щоб перевірити список замовлень, він мусить увійти через форму, знайти товар, додати в кошик, оформити… Гібридний тест бере найкраще з обох світів: **підготовка й прибирання — через API** (швидко, стабільно), **перевірка того, що бачить користувач, — в UI**.

> [!QA]
> Кожен шар перевіряй там, де він живе. Що сума показана в гривнях з комою — питання UI. Що сума правильно порахована — питання API. Гібридний тест чесно перевіряє зв'язок між ними: дані з сервера доходять до екрана без спотворень.

## Чотири прийоми

| Прийом | Приклад |
|---|---|
| Підготовка через API | створити замовлення `POST /orders` перед тестом сторінки «My orders» |
| Вхід без форми | отримати токен через API і покласти в localStorage / storage state |
| Дія в UI, перевірка через API | натиснути кнопку в UI, потім `GET` переконатися, що сервер змінився |
| Прибирання через API | `DELETE` створених даних у фікстурі після `yield` |

## Вхід без форми

Сторінка акаунта Gadgetly тримає токен у localStorage під ключем `gadgetly:token`. `page.add_init_script` виконує JavaScript **перед** скриптами сторінки — токен уже на місці, коли сторінка перевіряє, чи ти увійшов:

```python
import json


def open_account(page, token):
    page.add_init_script(f"localStorage.setItem('gadgetly:token', {json.dumps(token)})")
    page.goto("/playground/account")
    expect(page.get_by_role("heading", name="My account")).to_be_visible()


def test_account_shows_who_is_signed_in(page, token):
    open_account(page, token)
    expect(page.get_by_test_id("account-email")).to_have_text("Signed in as qa@gadgetly.test")
```

`json.dumps(token)` перетворює токен на рядок JavaScript у лапках — безпечно навіть для спецсимволів. Інший спосіб — storage state з модуля «Playwright in Practice».

## Розбір: гібридний тест від початку до кінця

| Крок | Шар | Що відбувається |
|---|---|---|
| 1 | API | session-фікстура входить і отримує токен (один раз на запуск) |
| 2 | API | фікстура створює тестові дані й віддає їх тесту |
| 3 | UI | сторінка відкривається вже «залогіненою» (токен з кроку 1) |
| 4 | UI | тест перевіряє, що бачить користувач: рядок, суму, статус |
| 5 | API | (за потреби) тест змінює дані через API і **перезавантажує** сторінку |
| 6 | API | після `yield` фікстура видаляє створене |

## Коли UI треба оновити

Сторінка вже завантажила дані — зміна через API в цей момент на екрані сама не з'явиться. Тому порядок такий: змінити через API → `page.reload()` (або відкрити сторінку після зміни) → перевірити в UI. Якщо застосунок оновлює дані сам (WebSocket, періодичне опитування), `expect` дочекається оновлення без reload.

## Чого не робити

- Не перевіряй через API те, що є лише в UI: текст кнопки, формат суми, стан галочки.
- Не готуй дані через UI, якщо є API — хіба що сама підготовка і є тим, що тестуєш.
- Не залишай дані: фікстура з `yield` прибирає навіть після падіння.
- Не змішуй дані різних тестів: кожен тест працює зі своїм `id`.

## Типові помилки

- Зміна через API без `reload()` — тест бачить старі дані і «падає без причини».
- `page.goto` до `add_init_script` — скрипт спрацює лише на наступному завантаженні.
- Пошук рядка за текстом `Order #…` серед чужих замовлень замість `get_by_test_id(f"order-{id}")`.
- Перевірка лише UI після дії, що мала змінити сервер: інтерфейс міг оновити себе, а сервер — ні.

## Підсумок

- Підготовка, вхід і прибирання — через API; перевірка того, що бачить користувач, — в UI.
- Вхід без форми: токен з API → `page.add_init_script(...)` до `goto` (або storage state).
- Після зміни даних через API — `reload()` перед перевіркою в UI.
- Дія в UI — перевірка наслідку через API.
- Кожен тест працює зі своїми даними за `id` і прибирає їх.
