# Чекліст, тест-кейси і баг-репорти

Тепер — від правил до перевірок. Для системи з грошима і датами працюють три техніки, які ти знаєш з модуля про тест-дизайн: **таблиця рішень** (комбінації умов → сума), **граничні значення** (вікно повернення, кількість, довжина коментаря) і **стани** (пошук → форма → запит → відстеження → скасування).

## Чекліст за областями

| Область | Що перевірити |
|---|---|
| Пошук | номер + email у різному регістрі; чужий email; неіснуючий номер; не доставлене замовлення |
| Товари | вибір, «−» / «+» на межах 1 і купленої кількості; подарункова картка; жодного товару |
| Вікно | 14-й і 15-й день; 30-й і 31-й для Defective; повідомлення з датою |
| Гроші | кожна комбінація причини, стану і способу; округлення; перерахунок після **кожної** зміни |
| Коментар | 9 / 10 і 300 / 301 символ; обов'язковість для Defective і Damaged |
| Запит | підтвердження: номер і **та сама** сума, що в підсумку |
| Відстеження | правильний і чужий email; скасування; повторне скасування |
| API | те саме без UI: недозволені кількості й товари, межі, доступ |

## Таблиця рішень для суми

Умови: **причина** (Changed my mind / брак / не той товар / пошкодження), **стан** (Unopened / Opened), **спосіб** (картка / кредит). Дії: комісія, доставка повернення, бонус. Брак, не той товар і пошкодження поводяться однаково — їх можна об'єднати в одну колонку «з вини магазину», і таблиця скорочується з 16 до 8 правил.

## Граничні значення вікна

| День після доставки | Changed my mind | Defective | Замовлення |
|---|---|---|---|
| 14 | ✅ дозволено (останній день) | ✅ | #5002 |
| 15 | ❌ «Return window closed» | ✅ | #5003 |
| 30 | ❌ | ✅ дозволено (останній день) | #5004 |
| 31 | ❌ | ❌ | #5006 |

## Перевірка API без сторінки

Частину правил сторінка «захищає» сама (наприклад, не дає вибрати подарункову картку). Але сервер має перевіряти все **незалежно від UI**. Запит з консолі DevTools на сторінці повернень:

```js
await fetch('/api/returns/quote', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ orderId: 5001, email: 'anna.koval@example.test', items: [{ lineId: 1, quantity: 1 }],
    reason: 'defective', condition: 'opened', refundMethod: 'original' }),
}).then((r) => r.json());
```

Або той самий запит з Python через `requests` (див. теорію попереднього уроку).

> [!TIP]
> Для кожного API-бага в репорті вказуй **метод, адресу, тіло запиту, статус і ключові поля відповіді**. Розробник має відтворити його одним копіюванням.

## Баг-репорт для грошей

Хороший репорт про гроші містить **обидві** суми і розрахунок: «Refund 2,550 UAH, expected 2,999 UAH: no restocking fee for defective items (2,999 − 0 − 0)». Severity — від наслідків: клієнт отримує менше грошей (Critical / Major), компанія втрачає гроші (Major), незручність без впливу на суму (Minor).

## Підсумок

- Чекліст за областями, а не за кнопками: пошук, товари, вікно, гроші, коментар, запит, відстеження, API.
- Таблиця рішень для суми; граничні значення для вікна, кількості й коментаря.
- Готові замовлення #5002–#5006 дають межі вікна без маніпуляцій з датою.
- Перевіряй сервер окремо від UI; у репорті — запит, статус, відповідь.
- Репорт про гроші — з обома сумами й розрахунком.
