# Black box, white box, grey box

Ці терміни описують, **на основі чого** ти придумуєш тести: тільки на основі вимог і поведінки, на основі коду, чи на основі часткового знання внутрішньої будови.

## Black box (чорна скринька)

Ти **не дивишся всередину** системи: знаєш лише, що подати на вхід і що має бути на виході за вимогами.

```text
вхідні дані  →  [ ??? система ??? ]  →  результат
                    (код не видно)
```

- Тести базуються на **специфікації**: вимогах, user stories, acceptance criteria, макетах.
- Техніки (модуль 3): **класи еквівалентності, граничні значення, таблиці рішень, переходи станів**, use cases.
- Знаходить: невідповідність вимогам, пропущену функціональність, помилки інтерфейсу й поведінки.
- Більшість роботи manual QA і UI-автоматизації — це black box.

## White box (біла / прозора скринька)

Ти **бачиш код** і будуєш тести на основі його структури: умов, гілок, циклів.

- Зазвичай це розробники та unit-тести.
- Мета — **покрити структуру коду**: виконати кожен оператор, кожну гілку `if`.
- Знаходить: «мертвий» код, неперевірені гілки, помилки в рідкісних шляхах виконання.

### Покриття операторів і гілок

```ts
function getShipping(total: number, isPremium: boolean): number {
  let cost = 50;
  if (total >= 1000) {
    cost = 0;
  }
  if (isPremium) {
    cost = 0;
  }
  return cost;
}
```

- **Statement coverage** (покриття операторів) — частка виконаних рядків-операторів. Один тест `getShipping(1500, true)` проходить усі оператори: 100% statement coverage.
- **Branch coverage** (покриття гілок) — частка виконаних **гілок** рішень. У кожного `if` дві гілки: умова true і умова false. Тут 2 `if` → 4 гілки. Тест `(1500, true)` покриває лише 2 з 4 (обидві true). Щоб покрити всі, додаємо `(500, false)`: обидві умови false.

> [!IMPORTANT]
> 100% branch coverage автоматично дає 100% statement coverage, але **не навпаки**. І навіть 100% покриття не означає відсутність багів: тести можуть виконати рядок, але не перевірити результат.

## Grey box (сіра скринька)

Ти тестуєш переважно ззовні (як black box), але **використовуєш часткове знання** внутрішньої будови: архітектуру, API, структуру бази даних, логи.

Приклади:

- після реєстрації через UI перевіряєш **в базі даних**, що користувач збережений з правильним статусом;
- знаючи, що фронтенд викликає `POST /api/orders`, перевіряєш цей запит у **DevTools → Network** і бачиш, що бекенд повертає 500;
- читаєш **логи сервера**, щоб знайти причину збою для баг-репорту;
- тестуєш **API** напряму, знаючи його контракт.

> [!QA]
> Сучасний QA Automation Engineer працює саме в grey box: тести через UI й API, перевірки в базі, аналіз запитів у DevTools. Тому в курсі є модулі про HTTP, API, SQL і DevTools.

## Порівняння

| | Black box | White box | Grey box |
|---|---|---|---|
| Знання коду | немає | повне | часткове (API, БД, архітектура, логи) |
| Основа тестів | вимоги, поведінка | структура коду | вимоги + внутрішні дані |
| Хто найчастіше | QA, користувачі | розробники | QA, automation QA |
| Приклад | форма відхиляє вік 17 | тест на кожну гілку `if` | після оплати запис у таблиці `orders` має статус `PAID` |

## Experience-based (на основі досвіду)

Окрема група технік, коли тести придумуються з досвіду й інтуїції: **error guessing** (вгадування помилок: «а якщо ввести пробіли?»), **дослідницьке тестування**, тестування за чеклістами. Їх розберемо в цьому модулі (exploratory) і в модулі 3.

## Підсумок

- **Black box** — за вимогами, без знання коду; основні техніки тест-дизайну.
- **White box** — за структурою коду; statement і branch coverage.
- **Grey box** — ззовні, але з частковим знанням API, БД, логів; щоденна реальність automation QA.
- Покриття коду — корисна метрика, але не гарантія якості.
