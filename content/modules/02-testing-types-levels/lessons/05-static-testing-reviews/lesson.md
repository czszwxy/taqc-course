# Статичне тестування і рев'ю

**Статичне тестування** перевіряє артефакти **без запуску** програми: вимоги, user stories, макети, тест-кейси, код. **Динамічне** — перевіряє поведінку працюючої програми. Статичне тестування знаходить дефекти найраніше, тож воно найдешевше.

## Що можна перевіряти статично

- вимоги, user stories, acceptance criteria;
- макети й прототипи;
- архітектурні документи;
- код (через рев'ю і статичний аналіз);
- тестову документацію: тест-план, тест-кейси, автотести.

## Типові дефекти, які знаходить рев'ю вимог

| Проблема | Приклад | Питання тестувальника |
|---|---|---|
| **Неоднозначність** | «система має швидко відповідати» | Скільки секунд? За якого навантаження? |
| **Неповнота** | «показати помилку при неправильних даних» | Які дані неправильні? Який текст помилки? Де її показати? |
| **Суперечність** | п. 3: «пароль від 8 символів», п. 7: «пароль 6–20 символів» | Яка вимога правильна? |
| **Нетестованість** | «інтерфейс має бути інтуїтивним» | За яким критерієм перевіримо? |
| **Пропущені сценарії** | описано успішну оплату, але не відмову банку | Що бачить користувач, якщо оплату відхилено? |

> [!QA]
> Найкращі питання — **конкретні**: не «вимога незрозуміла», а «що станеться, якщо користувач введе email з великими літерами — він вважається тим самим?».

## Види рев'ю

Від найменш до найбільш формального:

| Вид | Як проходить |
|---|---|
| **Informal review** | колега швидко переглядає документ чи код, без чіткого процесу (наприклад, pull request з коментарями) |
| **Walkthrough** | автор «проводить» учасників через документ, пояснює, збирає питання й ідеї |
| **Technical review** | технічні експерти обговорюють рішення, шукають дефекти й альтернативи |
| **Inspection** | найформальніше: ролі (модератор, автор, рев'юери, секретар), чеклісти, метрики, обов'язкові виправлення |

## Статичний аналіз

Інструменти, які аналізують код **без запуску**:

- **компілятор TypeScript** — знаходить помилки типів (ти вже бачив це в задачах модуля 11!);
- **лінтери** (ESLint) — потенційні помилки й порушення стилю;
- аналізатори безпеки й складності коду.

> [!TIP]
> Коли TypeScript підкреслив `const n: number = 'five'` — це статичне тестування в чистому вигляді: дефект знайдено, жодного разу не запустивши програму.

## Verification vs validation

| | Verification (верифікація) | Validation (валідація) |
|---|---|---|
| Питання | **Чи правильно ми робимо продукт?** (*building the product right*) | **Чи той продукт ми робимо?** (*building the right product*) |
| Перевіряємо | відповідність специфікації, вимогам, стандартам | відповідність реальним потребам користувачів |
| Приклади | рев'ю коду, тест за тест-кейсом, перевірка за acceptance criteria | UAT, демо користувачам, A/B-тест, бета-тестування |

Верифікація без валідації — це принцип «absence-of-defects fallacy» з модуля 1: продукт ідеально відповідає специфікації, але нікому не потрібен.

## Статичне + динамічне = разом

Статичне тестування не замінює динамічне: воно не покаже, що сторінка повільна чи що інтеграція з банком падає. Але знаходить дефекти, **які динамічне знайде пізно або не знайде взагалі**: суперечності у вимогах, нетестовані формулювання, пропущені сценарії, мертвий код.

## Підсумок

- Статичне тестування — без запуску; динамічне — з запуском.
- Рев'ю вимог шукає неоднозначність, неповноту, суперечності, нетестованість, пропущені сценарії.
- Види рев'ю: informal → walkthrough → technical review → inspection.
- Статичний аналіз: компілятор, лінтери.
- Verification — «правильно робимо», validation — «робимо те, що треба».
