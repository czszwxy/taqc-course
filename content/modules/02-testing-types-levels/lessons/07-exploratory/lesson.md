# Дослідницьке тестування

Тест-кейси добре перевіряють те, що ми **очікуємо**. Але найцікавіші баги часто ховаються там, де ніхто не думав дивитися. **Дослідницьке тестування** (exploratory testing) — підхід, у якому тестувальник **одночасно** вивчає продукт, придумує тести і виконує їх, підлаштовуючи наступний крок під те, що щойно побачив.

## Scripted vs exploratory

| | Скриптоване (scripted) | Дослідницьке (exploratory) |
|---|---|---|
| Тести придумують | заздалегідь, записують у тест-кейси | під час тестування |
| Сильні сторони | повторюваність, регресія, автоматизація, звітність | швидкий фідбек, пошук неочевидних багів, нові фічі з неповними вимогами |
| Слабкі сторони | бачить лише те, що передбачили | залежить від досвіду, складніше звітувати |
| Коли | регресія, критичні сценарії, вимоги регулятора | нова фіча, мало часу, розмиті вимоги, «щось не так, але незрозуміло що» |

Ці підходи **доповнюють** один одного: кращі команди поєднують обидва.

## Ad-hoc — не те саме

**Ad-hoc тестування** — неформальне тестування без плану й документації («потикав і подивився»). Дослідницьке тестування теж гнучке, але **структуроване**: має мету, обмеження в часі, нотатки і звіт.

## Session-based test management (SBTM)

Спосіб зробити дослідницьке тестування керованим і прозорим:

1. **Charter (чартер)** — мета сесії. Популярний шаблон (Elisabeth Hendrickson, книга *Explore It!*):

   ```text
   Explore <ціль>
   with <ресурси, інструменти, дані>
   to discover <яку інформацію шукаємо>
   ```

   Приклад: *Explore the sign-up form with boundary values, very long strings and keyboard-only navigation to discover validation and accessibility problems.*

2. **Timebox** — фіксована тривалість без перерв, зазвичай 45–90 хвилин.
3. **Нотатки** під час сесії: що перевірено, які ідеї виникли, що знайдено, питання.
4. **Debrief** — коротке обговорення результатів з колегою чи лідом: баги, ризики, питання, ідеї для наступних сесій.

> [!TIP]
> Пиши нотатки одразу, коротко: «Age 18 → помилка ❗ (BUG)», «email з пробілами → обрізається ✅», «❓ що з паролем 20 символів?». Після сесії з них легко зробити баг-репорти і звіт.

## Евристики: звідки брати ідеї

Евристики — підказки, щоб не застрягнути. Кілька корисних:

| Евристика | Ідеї |
|---|---|
| **Межі** | мінімум, максимум, ±1, порожньо, нуль |
| **Дивні дані** | пробіли, емодзі, кирилиця, дуже довгі рядки, спецсимволи `' " < > &`, від'ємні числа |
| **Перерви** | оновити сторінку посеред процесу, кнопка «Назад», обрив мережі, закрити вкладку |
| **Повтори** | подвійний клік, повторна відправка форми, ті самі дані двічі |
| **Порядок** | інший порядок кроків, пропустити крок, повернутися назад |
| **Ролі** | гість, звичайний користувач, адмін, заблокований |
| **Середовище** | інший браузер, мобільний розмір екрана, повільна мережа (DevTools), темна тема |
| **CRUD** | створити, прочитати, оновити, видалити й перевірити, що бачать інші частини системи |

Відома мнемоніка **SFDIPOT** (James Bach) нагадує, з яких боків дивитися на продукт: Structure, Function, Data, Interfaces, Platform, Operations, Time.

> [!QA]
> Дослідницьке тестування — не «тестування без підготовки». Чим краще ти знаєш продукт, вимоги, техніки тест-дизайну й типові баги, тим ефективніші твої сесії.

## Тури (tours)

Ще один спосіб структурувати дослідження — «екскурсії» продуктом із певною метою: **тур по грошах** (усе, що пов'язане з оплатою), **тур по даних** (де дані створюються, змінюються, відображаються), **тур поганого сусіда** (модулі, де вже знаходили багато багів).

## Підсумок

- Дослідницьке тестування: одночасно вчимося, придумуємо й виконуємо тести.
- Воно структуроване: **charter** (мета), **timebox**, нотатки, **debrief**.
- Шаблон чартера: Explore … with … to discover …
- Евристики (межі, дивні дані, перерви, повтори, ролі, середовище) допомагають знаходити ідеї.
- Scripted і exploratory тестування доповнюють одне одного.
