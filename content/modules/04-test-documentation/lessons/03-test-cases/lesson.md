# Тест-кейси: будова і найкращі практики

**Тест-кейс** (test case) — документ, який описує **одну** перевірку настільки детально, що будь-хто в команді виконає її однаково й однозначно визначить результат. Хороший тест-кейс — це також готова специфікація для майбутнього автотесту.

## Поля тест-кейсу

| Поле | Що писати | Приклад |
|---|---|---|
| **ID** | унікальний номер (зазвичай ставить інструмент) | TC-104 |
| **Title** (назва) | **що** перевіряємо і **за якої умови** | Cart: promo code SALE10 reduces the total by 10% |
| **Preconditions** | стан системи **до** першого кроку | користувач залогінений; у кошику 1 товар за 1500 грн |
| **Test data** | конкретні значення | промокод `SALE10` |
| **Steps** | одна дія на крок, нумеровані | 1. Open the cart. 2. Enter SALE10. 3. Click Apply |
| **Expected result** | спостережуваний, перевірюваний результат | сума 1350 грн, рядок «Discount −150 грн» |
| **Priority** | важливість тесту | High |
| **Type** | позитивний / негативний (+ smoke, regression…) | Positive |
| **Links** | вимога, user story, баг | US-58 |

Деякі команди додають **postconditions** (що прибрати після тесту), **автора**, **статус автоматизації**.

## Назва

Шаблон: **[Область]: [що відбувається] when/if [умова]**.

| ❌ Погано | ✅ Добре |
|---|---|
| Тест промокоду | Cart: SALE10 reduces the total by 10% |
| Перевірка логіну | Login: error message is shown for a wrong password |
| Negative test 5 | Sign-up: registration is rejected when age is 17 |

## Кроки

- **Одна дія — один крок.** Не «заповнити форму й відправити», а окремі кроки.
- Починай з **передумови**: кроки мають вести від описаного стану.
- **Без зайвого.** «Відкрити браузер» зазвичай не потрібне, якщо в передумовах уже «сторінка кошика відкрита».
- **Конкретні дані** або посилання на поле Test data: «ввести промокод з Test data».

## Очікуваний результат

Найважливіше поле. Воно має бути **спостережуваним** і **перевірюваним**:

| ❌ Погано | ✅ Добре |
|---|---|
| Працює правильно | Сума замовлення 1350 грн, з'явився рядок «Discount −150 грн» |
| Показується помилка | Під полем «Promo code» з'являється «Code expired» |
| Користувач залогінений | Відкрилась сторінка «My orders», у шапці відображається ім'я користувача |

> [!TIP]
> Можна давати очікуваний результат **для окремих кроків**, якщо проміжний стан важливий («після кроку 3 кнопка Apply стає неактивною»).

## Принципи хорошого тест-кейсу

1. **Атомарність:** один тест-кейс — одна перевірка (одна мета).
2. **Незалежність:** не залежить від результату інших тест-кейсів; усе потрібне — у передумовах.
3. **Повторюваність:** однаковий результат за однакових умов.
4. **Однозначність:** немає слів «тощо», «якісь дані», «правильно».
5. **Простежуваність:** посилання на вимогу.

> [!QA]
> Перевір себе: чи зможе новий колега, який уперше бачить продукт, виконати твій тест-кейс без жодного питання до тебе? Якщо ні — чогось бракує.

## Де зберігають тест-кейси

Спеціальні **test management** системи: TestRail, Qase, Zephyr і Xray (плагіни Jira), TestLink та інші; у маленьких командах — Google Sheets чи Confluence. Принципи однакові скрізь.

## Підсумок

- Обов'язкові поля: назва, передумови, дані, кроки, очікуваний результат, пріоритет.
- Назва: область + що + за якої умови.
- Одна дія на крок; очікуваний результат — спостережуваний і перевірюваний.
- Атомарний, незалежний, повторюваний, однозначний, простежуваний.
