# Тестові набори і матриця трасованості

Коли тест-кейсів сотні, їх треба **організувати**: швидко знаходити потрібні, запускати групами й розуміти, які вимоги вони покривають.

## Тестовий набір (test suite)

**Test suite** — група тест-кейсів, об'єднаних за якимось принципом:

| Принцип | Приклади наборів |
|---|---|
| **За функціональністю** | Authentication, Cart, Checkout, Profile |
| **За метою** | Smoke, Regression, Sanity для релізу 2.3 |
| **За рівнем / типом** | API tests, UI tests, Performance |
| **За пріоритетом** | Critical path, High priority |

Один тест-кейс може входити в **кілька** наборів: «логін з правильним паролем» — і в Authentication, і в Smoke.

**Test run** (тестовий прогін) — конкретне виконання набору на конкретному білді: «Regression, build 2.3.1, 12 листопада». Набір — це «що запускати», прогін — «коли і з яким результатом».

> [!TIP]
> У Playwright ідея та сама: тести групують у файли й `describe`-блоки за функціональністю, а теги (`@smoke`, `@regression`) дозволяють запускати набори за метою.

## Матриця трасованості (traceability matrix)

**Requirements Traceability Matrix (RTM)** — таблиця зв'язків **вимоги ↔ тест-кейси** (а часто й ↔ дефекти).

| Вимога | TC-01 | TC-02 | TC-03 | TC-04 | TC-05 | Покрито? |
|---|---|---|---|---|---|---|
| REQ-1 Реєстрація | ✅ | ✅ | | | | ✅ |
| REQ-2 Логін | | | ✅ | ✅ | | ✅ |
| REQ-3 Відновлення пароля | | | | | ✅ | ✅ |
| REQ-4 Підписка на розсилку | | | | | | ❌ |

### Що вона дає

- **Прогалини в покритті**: REQ-4 не має жодного тесту — треба написати.
- **Аналіз впливу змін** (impact analysis): змінилась вимога REQ-2 — одразу видно, які тести оновити й перезапустити.
- **Тест без вимоги**: якщо тест не пов'язаний з жодною вимогою, то або вимогу забули записати, або тест зайвий.
- **Звітність**: «усі вимоги релізу покрито, 2 з них мають відкриті дефекти».

> [!QA]
> Пряма трасованість (вимога → тести) показує, чи все **покрито**. Зворотна (тест → вимога) показує, чи **кожен тест потрібен**. Хороша матриця працює в обидва боки.

## Як вести на практиці

- У test management інструментах (TestRail, Qase, Xray) тест-кейс має поле **References / Links** з ID user story чи вимоги, і матриця будується автоматично.
- У маленьких командах — таблиця в Google Sheets.
- В Agile часто трасують до **user stories** та **acceptance criteria**: кожен критерій — щонайменше один тест.

## Підсумок

- Test suite — група тест-кейсів (за функцією, метою, рівнем, пріоритетом); тест може бути в кількох наборах.
- Test run — виконання набору на конкретному білді.
- RTM пов'язує вимоги з тестами (і дефектами): показує прогалини, вплив змін і зайві тести.
