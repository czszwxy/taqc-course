# Бриф фінального проєкту і тест-план

Фінальний проєкт — це **повний цикл роботи QA на одній фічі**, так, ніби ти щойно прийшов у команду: вимоги → питання → план → чекліст і тест-кейси → пошук багів → фреймворк автотестів → API → CI → публікація. Результат має дві цінності: ти закріплюєш усе вивчене, і в тебе з'являється **головний пункт портфоліо** та історія для співбесіди «розкажи про свій проєкт».

## Бриф від команди Gadgetly

> Ми запускаємо нову сторінку **Checkout** (`/playground/checkout`). Користувач змінює кількість товарів у кошику, обирає доставку, вводить контакти, застосовує промокод, оформлює замовлення і може відстежити його за номером і телефоном. Усі суми рахує **сервер** — checkout API. Перед релізом потрібні: план тестування, тестова документація, звіт про дефекти і автотести UI + API, що запускаються на CI.

Вимоги — у жовтій панелі на сторінці. Ключові правила:

| Що | Правило |
|---|---|
| Кількість | 1–5 на товар; «−» неактивна на 1, «+» на 5 |
| Доставка | Pickup — безкоштовно; Post office — 70 UAH; Courier — 150 UAH, **безкоштовно від 10 000 UAH** (subtotal до знижки) |
| Адреса | лише для Post office і Courier; для Pickup поле приховане |
| Промокоди | один за раз, регістр неважливий; `WELCOME5` — 5 % від subtotal (вниз до цілого, доставка не знижується); `MINUS200` — 200 UAH від 2 000 UAH |
| Контакти | ім'я 2–50 символів; телефон `+380` і 9 цифр; місто зі списку |
| Оформлення | одна дія = одне замовлення; у підтвердженні — номер і **та сама** сума, що в order summary |
| Трекінг | номер + телефон з оформлення; інший телефон → «Order not found» |

## Checkout API

| Запит | Що робить | Відповідь |
|---|---|---|
| `GET /api/checkout/products` | каталог | `{ items: [{ id, name, price, inStock }] }` |
| `POST /api/checkout/quote` | розрахунок суми | `{ items, delivery, promoCode, subtotal, discount, deliveryFee, total }` |
| `POST /api/checkout/orders` | оформлення | `201` + замовлення + `Location`; тіло = quote + `customer` |
| `GET /api/checkout/orders/:id?phone=` | трекінг | замовлення або `404` |
| `DELETE /api/checkout/orders/:id?phone=` | скасування (прибирання тестових даних) | `204` або `404` |

```json
POST /api/checkout/quote
{ "items": [{ "productId": 101, "quantity": 1 }, { "productId": 103, "quantity": 1 }],
  "delivery": "courier", "promoCode": "WELCOME5" }
```

Помилки: `400` — невалідне тіло (кількість, доставка, промокод, контакти), `422` — товару не існує, `409` — товару немає в наявності. Каталог: 101 Headphones NC5 (4 500), 102 Keyboard K8 (2 000), 103 Mouse M2 (500), 104 USB-C Cable (250), 105 Laptop Stand (1 250), 106 Webcam 4K (3 000, немає в наявності).

> [!NOTE]
> Як і в справжньому проєкті, і сторінка, і API **мають дефекти**. Знайти їх — частина завдання (урок 2), а автотести (уроки 3–5) перевіряються на версіях системи, де ввімкнено по одному дефекту.

## Етапи і результати

| Урок | Що робиш | Результат у репозиторії |
|---|---|---|
| 1 | рев'ю вимог, тест-план | `docs/test-plan.md` |
| 2 | чекліст, таблиця рішень, тест-кейси, баг-репорти | `docs/checklist.md`, `docs/test-cases.md`, `docs/bugs/` |
| 3 | Page Object і фікстури | `pages/`, `fixtures/`, `tests/ui/` |
| 4 | API-тести і комбіновані сценарії | `api/`, `tests/api/` |
| 5 | регресійний набір, CI, README, публікація | `.github/workflows/`, `README.md` |

Орієнтир — **2–3 тижні** по 1–2 години на день.

> [!TIP]
> Ти працюєш одразу у двох «треках». **Тренування** — завдання в застосунку на Gadgetly Checkout, вони перевіряються автоматично. **Портфоліо** — твій власний репозиторій на GitHub. Gadgetly працює лише локально всередині QA Academy, тому для зеленого CI на GitHub в уроці 5 ти перенесеш той самий підхід на публічний навчальний застосунок (Toolshop) і додаси документацію своєї роботи.

## Рев'ю вимог

Перш ніж тестувати, читай вимоги як тестувальник:

- **неоднозначності**: «вниз до цілого» — до гривні? що, якщо промокод робить total від'ємним?
- **пропуски**: що з телефоном з пробілами? чи можна видалити товар з кошика? що бачить користувач, якщо API недоступний?
- **суперечності** між сторінкою і API;
- **ризики**: гроші (суми, знижки, подвійне списання), персональні дані (трекінг), межі (10 000, 5 шт.).

## Тест-план для фічі

Короткий план (1–2 сторінки) відповідає на питання:

1. **Scope**: що тестуємо і що ні (in / out of scope).
2. **Підхід**: рівні (UI, API), типи (функціональне, межі, негативне, безпека, базова доступність), що ручне, що автоматизуємо і чому.
3. **Середовище і дані**: де запускаємо, які тестові дані, як прибираємо.
4. **Ризики** і як їх зменшуємо.
5. **Критерії входу / виходу**.
6. **Результати** (deliverables) і **графік**.

> [!QA]
> Розподіл «що на API, що на UI» — ознака зрілого плану: правила ціни (межі, знижки, валідація) — на API, швидко і точно; поведінка сторінки (залежні поля, перерахунок, подвійний клік, трекінг) — на UI.

## Підсумок

- Система: Gadgetly Checkout + checkout API; вимоги — у жовтій панелі, API — у таблиці вище.
- 5 етапів: план → документація і баги → UI-фреймворк → API і комбіновані сценарії → регресія, CI, публікація.
- Почни з рев'ю вимог: неоднозначності, пропуски, ризики.
- Тест-план: scope, підхід (API vs UI), середовище й дані, ризики, критерії, результати.
