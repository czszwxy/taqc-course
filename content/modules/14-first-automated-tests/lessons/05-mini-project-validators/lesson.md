# Міні-проєкт: тести для бібліотеки валідаторів

Команда Gadgetly пише модуль валідації для форми оформлення замовлення. Код уже готовий; твоя роль — **QA Automation**: спланувати перевірки і написати набір unit-тестів, якому можна довіряти. Його запускатимуть при кожній зміні коду, тож він має ловити регресії.

## Вимоги до полів

| Поле | Правило | Повідомлення про помилку |
|---|---|---|
| **Card holder** | обов'язкове (після обрізання пробілів); 2–40 символів; лише літери, пробіли, дефіс, апостроф | `Card holder is required` / `Card holder must be 2–40 characters` / `Card holder may contain only letters, spaces, hyphens and apostrophes` |
| **ZIP** | рівно 5 цифр (пробіли по краях ігноруються) | `ZIP code must be exactly 5 digits` |
| **Quantity** | ціле число 1–10 | `Quantity must be a whole number from 1 to 10` |
| **Promo code** | **необов'язкове**; якщо заповнене — 4–10 латинських літер або цифр, регістр не важливий | `Promo code must be 4–10 letters or digits` |

Кожен валідатор повертає текст помилки або `null`, якщо значення валідне. Функція `validateCheckout(form)` перевіряє **всі** поля і повертає об'єкт лише з полями, що мають помилки (`{}`, якщо все добре); `canSubmit(form)` — `true`, якщо помилок немає.

## План роботи

1. **Тест-умови** (завдання 1): для кожного поля — класи еквівалентності, межі, «дивні» значення. Це твій чекліст.
2. **Тести валідаторів** (завдання 2): по тесту на кожну умову. 7 мутантів.
3. **Тести форми** (завдання 3): як валідатори працюють разом. 5 мутантів.

> [!TIP]
> Для кожного поля думай трьома групами: **валідні** значення (типові й граничні), **невалідні** (за межами, не той формат), **особливі** (порожньо, лише пробіли, регістр, кирилиця, апостроф у прізвищі O'Neil).

> [!QA]
> Mutation testing — найчесніший спосіб оцінити набір тестів. «100% покриття коду» можна отримати тестами без жодного `expect`; а от зловити всіх мутантів — лише тестами, які справді перевіряють поведінку. Інструмент для справжніх проєктів — Stryker.

## Корисні прийоми

```ts
// a table of cases for one validator
const holderCases: [string, string | null][] = [
  ['Olena Petrenko', null],
  ["O'Neil", null],
  ['', 'Card holder is required'],
];
for (const [value, expected] of holderCases) {
  it(`card holder "${value}" → ${expected ?? 'valid'}`, () => {
    expect(validateCardHolder(value)).toBe(expected);
  });
}

// a valid form as the base, changing one field per test
const validForm: CheckoutForm = { cardHolder: 'Olena Petrenko', zip: '79000', quantity: 1, promo: '' };
it('reports a bad ZIP', () => {
  expect(validateCheckout({ ...validForm, zip: '7900' })).toEqual({ zip: 'ZIP code must be exactly 5 digits' });
});
```

Прийом «валідна форма + одна зміна» — те саме правило з модуля 06: в негативному тесті невалідне **лише одне** поле.

## Підсумок

- Спершу тест-умови (EP, BVA, особливі значення), потім код тестів.
- Таблиці прикладів і цикл — для валідаторів; «валідна форма + одна зміна» — для форми.
- Набір тестів готовий, коли ловить усіх мутантів, а не коли «тестів багато».
