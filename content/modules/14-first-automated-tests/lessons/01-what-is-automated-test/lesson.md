# Що таке автотест. Шаблон AAA

Досі тести за тебе писав автор курсу: ти писала код, а приховані тести його перевіряли. Тепер ролі міняються. **Автотест** — це код, який викликає інший код (функцію, API, сторінку) і **перевіряє результат**. Якщо результат не той — тест падає.

```ts
import { discountedPrice } from './subject';

describe('discountedPrice', () => {
  it('applies a 10% discount', () => {
    // Arrange — prepare the data
    const price = 500;

    // Act — do the thing we test
    const result = discountedPrice(price, 10);

    // Assert — check the result
    expect(result).toBe(450);
  });
});
```

## Arrange — Act — Assert

| Крок | Що робимо | У Playwright |
|---|---|---|
| **Arrange** | готуємо дані й стан | відкрити сторінку, увійти, створити тестові дані |
| **Act** | виконуємо **одну** дію, яку тестуємо | клік, заповнення форми, запит до API |
| **Assert** | перевіряємо результат | `await expect(page.getByText('Welcome')).toBeVisible()` |

> [!TIP]
> Один тест — одна поведінка. Тест «перевіряє все про кошик» важко читати, і коли він падає, незрозуміло, що саме зламалося. Краще п'ять маленьких тестів з точними назвами.

## Pass і fail

- Тест **проходить** (pass), якщо всі `expect` виконались і нічого не кинуло помилку.
- Тест **падає** (fail), якщо будь-який `expect` не справдився або код кинув помилку.

> [!WARNING]
> Тест без `expect` **завжди** зелений — навіть якщо функція повертає повну нісенітницю. Порожній тест гірший за відсутній: він створює хибне відчуття безпеки.

## Хороший тест падає на зламаному коді

Як перевірити, що тести хороші? Навмисно зламати код і подивитися, чи вони це помітять. Це називається **mutation testing**, а зламані версії коду — **мутантами**:

```ts
// the real code
return Math.round(price * (100 - percent)) / 100;

// a mutant: forgot the discount
return price;
```

Якщо твої тести проходять і на справжньому коді, і на мутанті — вони **не перевіряють** знижку. У завданнях цього модуля кожен «зловлений» мутант зараховується, а для «вцілілого» ти отримаєш підказку, який випадок ще не протестовано.

## Unit, API, UI

| Рівень | Що тестує | Швидкість | Приклад |
|---|---|---|---|
| **Unit** | одну функцію чи клас | мілісекунди | `discountedPrice(500, 10)` |
| **API** | ендпоінт сервера | десятки мс | `POST /api/orders` → 201 |
| **UI / E2E** | сценарій у браузері | секунди | користувач входить і оформлює замовлення |

У цьому модулі — unit-тести: найпростіші й найшвидші. Але структура (AAA, describe/it/expect) та сама в API- і UI-тестах на Playwright.

> [!QA]
> Автотест не замінює мислення тестувальника — він **автоматизує перевірку**, яку ти вже придумала. Техніки з модулів 02–04 (EP, BVA, таблиці рішень) визначають, **які** тести писати; код лише виконує їх швидко й без утоми.

## Підсумок

- Автотест: виклик коду + перевірка результату через `expect`.
- AAA: Arrange (підготовка) → Act (одна дія) → Assert (перевірка).
- Тест без `expect` завжди зелений — це небезпечно.
- Хороші тести падають на зламаному коді (мутантах).
