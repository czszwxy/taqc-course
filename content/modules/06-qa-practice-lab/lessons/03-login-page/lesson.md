# Сторінка входу: чекліст і тест-кейси

Логін — найчастіше тестована сторінка у світі. Вона маленька, але через неї проходять **усі** користувачі, тому баг тут — це або «ніхто не може увійти» (Blocker), або діра в безпеці. На співбесіді питання «Як би ти протестував логін?» звучить майже завжди.

У цьому уроці ти пройдеш повний цикл на сторінці [Login page](/playground/login): вимоги → чекліст → тест-кейс → пошук багів.

## Крок 1. Розбери вимоги на правила

Відкрий сторінку й уважно прочитай жовтий блок **Requirements**. Кожен пункт — це одне або кілька правил, які треба перевірити:

| Що | Правило | Ідеї для перевірок |
|---|---|---|
| Обов'язкові поля | Email і Password required | обидва порожні, лише один порожній, пробіли замість email |
| Email | case-insensitive, пробіли ігноруються | `Demo@Taskly.test`, `" demo@taskly.test "` |
| Password | case-sensitive | `demo1234` замість `Demo1234` має **не** пускати |
| Повідомлення про помилку | однакове для неіснуючого email і неправильного пароля | порівняй тексти двох випадків |
| Блокування | після 3 невдалих спроб поспіль | 2 спроби → ще можна; 3 → блок; правильний пароль після блоку → відмова |
| Заблокований акаунт | правильні дані → «Your account is locked» | `locked@taskly.test` / `Locked123` |
| Show password | показує і **знову ховає** | перемкни туди й назад |
| Remember me | з галочкою email зберігається після Log out, без — ні | обидва варіанти |
| Forgot password | потрібен email | порожнє поле, заповнене поле |

> [!QA]
> Чому повідомлення має бути **однаковим** для «немає такого email» і «неправильний пароль»? Якщо сайт каже «User not found», зловмисник може перебором дізнатися, які email зареєстровані (user enumeration). Тестувальник перевіряє і такі «невидимі» вимоги безпеки.

## Крок 2. Чекліст

Чекліст — короткий список перевірок без деталей. Його швидко написати й легко пройти. Групуй пункти:

- **Позитивні:** вхід з валідними даними; email з великими літерами; email з пробілами.
- **Негативні:** неправильний пароль; неіснуючий email; порожні поля; пароль в іншому регістрі.
- **Безпека:** однакові повідомлення; блокування після 3 спроб; заблокований акаунт; пароль прихований за замовчуванням.
- **Зручність:** Show password, Remember me, Forgot password, вхід клавішею Enter.

## Крок 3. Тест-кейси для найважливішого

Не все з чекліста потребує детального тест-кейсу. Пиши тест-кейси для **ризикових і складних** перевірок, наприклад для блокування: там є послідовність кроків, лічильник і точне очікуване повідомлення.

```text
Title:   Login: account is locked after 3 failed attempts in a row
Steps:   1. Enter demo@taskly.test + wrong password → Log in   (attempt 1)
         2. Repeat with another wrong password                  (attempt 2)
         3. Repeat with a third wrong password                  (attempt 3)
         4. Enter the correct password Demo1234 → Log in
Expected: after attempt 3 — "Too many failed attempts…";
          step 4 is rejected with the same message
```

> [!TIP]
> Блокування після N спроб — це **межа**. Перевір значення навколо неї: 2 невдалі спроби (ще не блокує), 3 (блокує), а також що успішний вхід **скидає** лічильник.

## Крок 4. Досліджуй і шукай баги

Пройди чекліст на сторінці. На кожну невідповідність вимогам — окремий баг-репорт. Нагадування:

- одна перевірка = одне правило, решта даних валідні;
- у summary — **що** не так і **за якої умови**;
- у actual result — точний текст повідомлення, який ти побачив.

Якщо щось «зламалося» (наприклад, акаунт заблокувався) — натисни **Reset demo data** або онови сторінку.

## Підсумок

- Логін тестують з чотирьох боків: позитивні, негативні, безпека, зручність.
- Вимоги → правила → чекліст → тест-кейси для ризикових перевірок.
- Блокування після N спроб — гранична умова: перевіряй N−1, N і скидання лічильника.
- Повідомлення про помилку не повинне розкривати, що саме неправильне.
