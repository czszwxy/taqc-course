# Регресійний прогін і звіт

Нова збірка готова до релізу. Перед тим як випустити її, команда проганяє **регресійний набір** — тести, які підтверджують, що те, що працювало раніше, досі працює. Твоє завдання — чесно виконати тести, зафіксувати статуси й коротко повідомити команді: **можна випускати чи ні**.

Практика — на сторінці [Login page](/playground/login) з готовим набором тест-кейсів.

## Retest vs regression

| | Retest (confirmation testing) | Regression testing |
|---|---|---|
| Що перевіряємо | що **конкретний** баг виправлено | що виправлення чи нова функція **не зламали** інше |
| Які тести | кроки з баг-репорту | набір тестів для всієї функції або продукту |
| Коли | після статусу «Fixed» | перед релізом, після змін у коді |

## Статуси виконання

- **Passed** — фактичний результат збігається з очікуваним.
- **Failed** — не збігається → посилання на баг (новий або існуючий).
- **Blocked** — тест неможливо виконати (наприклад, сторінка не відкривається).
- **Not run / Skipped** — не виконувався (не встигли, неактуально).

> [!WARNING]
> Статус — це **факт**, а не думка. Якщо expected каже «повідомлення X», а ти бачиш «повідомлення Y», це Failed, навіть якщо Y тобі здається кращим. Не згоден з вимогою — постав питання окремо.

## Як проганяти

1. Починай зі **smoke**-тестів: якщо не працює вхід з валідними даними, решту можна позначити Blocked і одразу повідомити команду.
2. Кожен тест — з **чистого стану** (Reset demo data), інакше попередній тест вплине на наступний (наприклад, лічильник невдалих спроб).
3. Failed — одразу перевір, чи є вже баг-репорт; якщо ні — заведи.

## Прогалини в покритті

Набір тестів — не вся правда про якість. Порівняй його з вимогами: якщо для якогось правила **немає** тесту, баг там може пройти непоміченим. Це теж треба написати у звіті як **ризик**.

## Test summary report

Короткий звіт для команди (5–10 рядків):

```text
Scope:     Login page, build 1.4.0, Chrome 131 / Windows 11
Executed:  12 / 12   Passed: 8   Failed: 4   Blocked: 0
Failed:    TC-05 email case → BUG-101 …
Risks:     requirement X is not covered by the suite
Recommendation: NO-GO until security bugs are fixed
```

> [!QA]
> Рішення про реліз приймає команда / продакт, а не лише QA. Твоя роль — дати **чесну інформацію і рекомендацію**: що працює, що ні, наскільки це ризиковано для користувачів. Баги безпеки або втрати грошей — серйозний аргумент за «no-go».

## Підсумок

- Retest — перевірка конкретного виправлення; regression — перевірка, що нічого не зламалося.
- Статуси: Passed / Failed / Blocked / Not run — лише за фактом.
- Кожен тест — з чистого стану; починай зі smoke.
- Звіт: обсяг, цифри, failed з багами, ризики (зокрема прогалини в покритті), рекомендація.
