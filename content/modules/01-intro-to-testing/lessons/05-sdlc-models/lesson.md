# Моделі SDLC: Waterfall, V-model, ітеративні

**SDLC (Software Development Life Cycle)** — життєвий цикл розробки ПЗ: етапи, через які проходить продукт від ідеї до підтримки. Від моделі SDLC залежить, **коли і як** у проєкті тестують. Тому тестувальнику важливо розуміти, як влаштований процес у його команді.

## Типові етапи

| Етап | Що відбувається | Роль QA |
|---|---|---|
| **Requirements** (вимоги) | збирають і описують, що має робити система | рев'ю вимог, питання, оцінка тестованості |
| **Design** (проєктування) | архітектура, макети, структура даних | рев'ю дизайну, планування тестування |
| **Implementation** (розробка) | пишуть код | підготовка тест-кейсів і даних, автотести |
| **Testing** (тестування) | перевіряють систему | виконання тестів, баги, звіти |
| **Deployment** (розгортання) | випуск для користувачів | smoke-тести після релізу |
| **Maintenance** (підтримка) | виправлення, дрібні покращення | регресія, перевірка виправлень |

## Waterfall (каскадна модель)

Етапи йдуть **строго послідовно**: наступний починається, коли попередній завершено.

```text
Requirements → Design → Implementation → Testing → Deployment → Maintenance
```

| Плюси | Мінуси |
|---|---|
| просте планування, зрозумілі етапи | зміни вимог дорогі й болючі |
| багато документації | тестування починається пізно → баги знаходять пізно і дорого |
| підходить для стабільних, чітко визначених вимог | користувач бачить продукт лише в кінці |

> [!WARNING]
> Головний ризик Waterfall для якості: якщо тестування стоїть наприкінці, дефекти у вимогах і архітектурі виявляються саме тоді, коли їх виправляти найдорожче.

## V-model (V-модель)

Розвиток каскадної моделі, у якій **кожному етапу розробки відповідає рівень тестування**. Ліва гілка «V» — розробка, права — тестування. Тестування **планують і готують паралельно** з розробкою, а не наприкінці.

```text
Business requirements ─────────────────────── Acceptance testing
   System requirements ─────────────────── System testing
      Architecture (high-level design) ── Integration testing
         Module (detailed) design ───── Unit (component) testing
                        \           /
                         Implementation
                           (coding)
```

| Етап розробки (ліва гілка) | Рівень тестування (права гілка) | Що перевіряємо |
|---|---|---|
| Бізнес-вимоги, потреби користувачів | **Acceptance testing** | чи вирішує система задачу замовника |
| Вимоги до системи (специфікація) | **System testing** | чи відповідає вся система специфікації |
| Архітектура (high-level design) | **Integration testing** | чи правильно взаємодіють модулі |
| Детальний дизайн модулів | **Unit (component) testing** | чи правильно працює кожен модуль окремо |

> [!QA]
> Головна ідея V-моделі, корисна в будь-якому процесі: **тести для кожного рівня можна готувати одразу, щойно з'явився відповідний документ**. Отримав вимоги — вже можна писати приймальні сценарії.

## Ітеративні та інкрементні моделі

Продукт будують **частинами** (інкрементами) і в **кілька циклів** (ітерацій). Кожна ітерація — міні-цикл: вимоги → розробка → тестування → демонстрація. Користувач бачить робочу версію рано і впливає на наступні кроки.

```text
[ітерація 1: базовий каталог] → [ітерація 2: кошик] → [ітерація 3: оплата] → …
   кожна: plan → build → test → review
```

Сюди належать **Agile**-підходи (Scrum, Kanban), про які наступний урок. Окремо згадують **Spiral** (спіральну модель), де кожен виток починається з аналізу ризиків; на практиці зараз зустрічається рідко.

| | Waterfall | V-model | Iterative / Agile |
|---|---|---|---|
| Коли тестують | наприкінці | планують паралельно, виконують після розробки | у кожній ітерації, постійно |
| Зміни вимог | дорого | дорого | очікувані й нормальні |
| Документація | багато | багато | достатня, «жива» |
| Типове застосування | фіксований обсяг, регульовані галузі | системи з високими вимогами до надійності | більшість сучасних продуктових команд |

## Підсумок

- SDLC — етапи життя продукту; від моделі залежить, коли і як тестують.
- **Waterfall**: послідовні етапи, тестування наприкінці, зміни дорогі.
- **V-model**: кожному етапу розробки відповідає рівень тестування (unit ↔ дизайн модуля, integration ↔ архітектура, system ↔ вимоги до системи, acceptance ↔ бізнес-вимоги).
- **Ітеративні моделі** (зокрема Agile): продукт росте маленькими частинами, тестування — в кожній ітерації.
