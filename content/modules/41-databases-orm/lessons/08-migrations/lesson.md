# Міграції схеми з Alembic

Схема живе разом із застосунком: додаємо телефон читачу, нову таблицю, індекс. На своєму ноутбуці можна видалити базу й зробити `create_all` заново — а в продакшені в тих самих таблицях лежать дані клієнтів. `create_all` наявні таблиці **не змінює**. Потрібні **міграції** — пронумеровані скрипти змін схеми, що лежать у git поруч із кодом і виконуються однаково на кожній базі: у розробника, у CI, на staging і в продакшені.

## Як це влаштовано

| Ідея | Що це |
|---|---|
| ревізія | один файл міграції з унікальним id |
| `down_revision` | id попередньої ревізії — так ревізії утворюють ланцюжок |
| `upgrade()` | як застосувати зміну |
| `downgrade()` | як її скасувати |
| таблиця `alembic_version` | у самій базі: id ревізії, на якій база зараз |

Alembic порівнює `alembic_version` з ланцюжком у git і виконує лише ті ревізії, яких база ще не бачила. Тому команду `alembic upgrade head` можна запускати скільки завгодно разів: друга й наступні нічого не змінять.

## Налаштування і перша міграція

```bash
pip install alembic
alembic init migrations          # alembic.ini, migrations/env.py, migrations/versions/
```

У `migrations/env.py` вказують метадані моделей, щоб Alembic знав «як має бути»: `target_metadata = Base.metadata`, а URL бази — в `alembic.ini` або зі змінної оточення.

```python
"""add phone to members

Revision ID: 3f2a1c9d8e7b
Revises: 9b1e4d2c6a5f
"""
from alembic import op
import sqlalchemy as sa

revision = "3f2a1c9d8e7b"
down_revision = "9b1e4d2c6a5f"


def upgrade():
    op.add_column("members", sa.Column("phone", sa.String(20), nullable=True))
    op.create_index("ix_members_phone", "members", ["phone"])


def downgrade():
    op.drop_index("ix_members_phone", table_name="members")
    op.drop_column("members", "phone")
```

`downgrade()` робить кроки у **зворотному** порядку.

## Команди

```bash
alembic revision -m "add phone to members"                  # порожній файл міграції
alembic revision --autogenerate -m "add phone to members"   # чернетка з порівняння моделей і бази
alembic upgrade head                                        # застосувати все, чого ще немає
alembic downgrade -1                                        # відкотити останню
alembic current                                             # на якій ревізії база
alembic history                                             # ланцюжок ревізій
```

## Autogenerate — чернетка, а не готова міграція

`--autogenerate` порівнює `Base.metadata` з базою і пише чернетку: нові таблиці, стовпці, індекси, зміни nullable. Але:

- **перейменування** він не бачить: перейменований стовпець виглядає як «видалити старий + додати новий» — разом зі стовпцем зникнуть дані;
- частину змін (наприклад, деякі обмеження чи типи) він не помічає або помічає лише з налаштуваннями;
- переносу даних (`UPDATE ...`) він не напише ніколи — це `op.execute(...)` вручну.

Тому кожну згенеровану міграцію **читають** перед комітом, як звичайний код.

## SQLite і batch mode

SQLite вміє лише частину `ALTER TABLE` (додати стовпець — так, змінити тип чи прибрати обмеження — ні). Alembic обходить це «пакетним» режимом: створює нову таблицю, копіює дані й підміняє стару.

```python
with op.batch_alter_table("members") as batch:
    batch.alter_column("phone", type_=sa.String(30))
```

## Зміни на живій базі: expand / contract

Під час деплою стара версія коду ще працює, поки запускається нова. Тому небезпечні зміни роблять у кілька кроків: спершу **розширюють** схему так, щоб працювали обидві версії коду, потім переносять дані, і лише коли старий код зник — **звужують**.

| Зміна | Чому небезпечна | Як безпечно |
|---|---|---|
| новий `NOT NULL` стовпець без default | таблиця з рядками його не прийме, старий код не заповнює | додати nullable → заповнити → зробити `NOT NULL` |
| перейменування стовпця | старий код читає стару назву | новий стовпець → писати в обидва → перенести дані → читати новий → видалити старий |
| видалення стовпця | старий код ще його читає | спершу прибрати з коду, видалити наступним релізом |

## Правила

- Застосовану міграцію **не редагують** — помилку виправляють новою ревізією (інакше бази розійдуться).
- Міграції в git і в code review разом з моделлю.
- У CI: `alembic upgrade head` на чистій базі (і бажано `downgrade` / `upgrade` ще раз).
- Перед міграцією продакшену — бекап; великі таблиці мігрують обережно (індекс на мільйонах рядків може блокувати записи).

> [!QA]
> Міграції тестують на копії даних, схожих на продакшн: на порожній базі `ALTER` пройде, а на мільйоні рядків з `NULL` у новому `NOT NULL` стовпці — впаде.

## Підсумок
- Міграція — версійований скрипт зміни схеми; `create_all` для наявних таблиць не годиться.
- Alembic: ланцюжок ревізій (`revision` / `down_revision`), `upgrade()` / `downgrade()`, поточна версія — в `alembic_version`.
- `upgrade head` виконує лише відсутні ревізії; `downgrade -1` відкочує останню.
- Autogenerate — чернетка: перейменування бачить як drop + add, дані не переносить — читай кожну міграцію.
- На живій базі — expand / contract; застосовані міграції не редагують.
