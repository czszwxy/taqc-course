# Транзакції та помилки бази

Бронювання квитка на концерт — це **дві** зміни: зменшити кількість вільних місць і створити бронь. Якщо програма впаде між ними, місце «зникне» без броні. **Транзакція** об'єднує кілька змін в одну: або вони відбуваються всі, або жодна.

## ACID — чотири обіцянки

| Літера | Обіцянка | На прикладі броні |
|---|---|---|
| **A**tomicity | все або нічого | місце не зменшиться без броні |
| **C**onsistency | обмеження виконуються | `free_seats` не стане від'ємним (`CHECK`) |
| **I**solation | паралельні транзакції не бачать незавершених змін одна одної | інший запит не бачить «половини» броні |
| **D**urability | після commit дані не зникнуть | бронь переживе перезапуск сервера |

## Як sqlite3 керує транзакціями

У звичайному режимі модуль `sqlite3` сам відкриває транзакцію (`BEGIN`) перед першим `INSERT`, `UPDATE` чи `DELETE`. Далі все накопичується, доки не буде:

- `conn.commit()` — зафіксувати;
- `conn.rollback()` — скасувати все з моменту `BEGIN`.

Блок `with conn:` робить це за тебе і **не ховає** винятки:

```python
def book_seat(conn, event_id, guest):
    with conn:                                  # commit у кінці або rollback при винятку
        conn.execute("UPDATE events SET free_seats = free_seats - 1 WHERE id = ?", (event_id,))
        conn.execute("INSERT INTO bookings (event_id, guest) VALUES (?, ?)", (event_id, guest))
```

## Розбір: що буде, якщо другий запит упаде

| Крок | Що відбувається | Стан бази для інших |
|---|---|---|
| 1 | `UPDATE events ...` → sqlite3 виконує `BEGIN`, місць стає 9 | 10 місць, бронювань немає |
| 2 | `INSERT INTO bookings ...` порушує `UNIQUE` → `IntegrityError` | без змін |
| 3 | `with conn:` бачить виняток → `rollback()` | 10 місць, бронювань немає |
| 4 | виняток летить далі, до того, хто викликав `book_seat` | без змін |

## Гонка «перевірив — зробив»

```python
free = conn.execute("SELECT free_seats FROM events WHERE id = ?", (event_id,)).fetchone()[0]
if free > 0:                      # два запити одночасно бачать free = 1...
    ...                           # ...і обидва бронюють останнє місце
```

Між перевіркою і зміною інший запит встигає зробити те саме. Надійніше перевіряти **в самому UPDATE** і дивитися, скільки рядків він змінив:

```python
cursor = conn.execute(
    "UPDATE events SET free_seats = free_seats - ? WHERE id = ? AND free_seats >= ?",
    (seats, event_id, seats),
)
if cursor.rowcount == 0:          # умова не виконалась: місць замало або події немає
    raise NoSeatsLeft(event_id)
```

База виконує один `UPDATE` атомарно, тож двом запитам не дістанеться те саме місце.

## Помилки бази → помилки застосунку

Код вище за базою (API, UI) не має знати про `sqlite3.IntegrityError`. Перехопи її там, де розумієш значення, і кинь власний виняток:

```python
class SeatTaken(Exception):
    pass

try:
    with conn:
        conn.execute("INSERT INTO bookings (event_id, seat) VALUES (?, ?)", (event_id, seat))
except sqlite3.IntegrityError as err:
    raise SeatTaken(seat) from err          # from err зберігає першопричину в traceback
```

## Режим autocommit=False (Python 3.12+)

`sqlite3.connect(path, autocommit=False)` вмикає поведінку з PEP 249: транзакція відкрита **завжди**, навіть для `CREATE TABLE` і `ALTER TABLE`. Тоді й зміни схеми можна відкотити — це знадобиться в уроці про міграції.

## Типові помилки

- `commit()` всередині циклу: половина змін збережена, коли падає середина.
- Перехопили виняток і не зробили `rollback()`: незавершені зміни лишились у транзакції й потраплять у наступний `commit()`.
- `except Exception: pass` — помилка зникла, дані в невідомому стані.
- Перевірка `SELECT` → `if` → `UPDATE` без умови в самому `UPDATE` (гонка).

> [!QA]
> Найцінніший тест транзакції — **негативний**: зламай другий крок (немає товару, дубль email) і перевір, що від першого кроку не лишилося й сліду — ні в цьому з'єднанні, ні в іншому.

## Підсумок
- Транзакція — все або нічого; ACID: атомарність, узгодженість, ізоляція, довговічність.
- sqlite3 відкриває транзакцію перед першою зміною; `commit()` / `rollback()` її закривають; `with conn:` робить це автоматично й пропускає виняток далі.
- Перевіряй умову в самому `UPDATE ... WHERE ... AND stock >= ?` і дивись на `rowcount` — без гонки.
- `IntegrityError` перекладай у доменний виняток: `raise EmailTaken(email) from err`.
