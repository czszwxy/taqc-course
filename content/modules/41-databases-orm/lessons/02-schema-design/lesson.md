# Проєктування схеми

Код можна переписати за вечір, а схему бази з мільйонами рядків — ні. Погана схема породжує баги, які жоден `if` не виправить: два користувачі з одним email, замовлення «нічийого» покупця, ціна `-5`. Тому правила даних записують **у саму базу** — обмеженнями (constraints). Тоді база відхилить погані дані, навіть якщо в коді забули перевірку.

## Приклад: бібліотека

```sql
CREATE TABLE members (
    id         INTEGER PRIMARY KEY,
    email      TEXT    NOT NULL UNIQUE,
    full_name  TEXT    NOT NULL
);

CREATE TABLE books (
    id      INTEGER PRIMARY KEY,
    isbn    TEXT    NOT NULL UNIQUE,
    title   TEXT    NOT NULL,
    copies  INTEGER NOT NULL DEFAULT 1 CHECK (copies >= 0)
);

CREATE TABLE loans (
    id         INTEGER PRIMARY KEY,
    member_id  INTEGER NOT NULL REFERENCES members (id),
    book_id    INTEGER NOT NULL REFERENCES books (id),
    due_date   TEXT    NOT NULL,
    status     TEXT    NOT NULL DEFAULT 'open' CHECK (status IN ('open', 'returned'))
);
```

| Обмеження | Що гарантує | Що відхилить |
|---|---|---|
| `PRIMARY KEY` | унікальний незмінний ідентифікатор рядка | два рядки з одним `id` |
| `NOT NULL` | значення є завжди | книжку без назви |
| `UNIQUE` | значення не повторюється | другого читача з тим самим email |
| `CHECK (умова)` | значення відповідає правилу | `copies = -1`, статус `'lost'` |
| `DEFAULT` | значення, якщо його не передали | — (підставить `'open'`) |
| `REFERENCES t (id)` | **зовнішній ключ**: рядок посилається на наявний | позику неіснуючого читача |

У SQLite `INTEGER PRIMARY KEY` — особливий: якщо `id` не передати, база видасть наступне число сама.

> [!WARNING]
> У SQLite зовнішні ключі **вимкнені за замовчуванням** (заради сумісності зі старими базами). Їх вмикають для кожного з'єднання: `conn.execute("PRAGMA foreign_keys = ON")`. Без цього `REFERENCES` — лише коментар, і база прийме позику для читача № 999. PostgreSQL і MySQL перевіряють зовнішні ключі завжди.

## Що робити з «дітьми» при видаленні батька

| Варіант | Що станеться з позиками, коли видаляють читача |
|---|---|
| за замовчуванням (`NO ACTION` / `RESTRICT`) | видалення заборонено, доки є позики |
| `ON DELETE CASCADE` | позики видаляться разом з читачем |
| `ON DELETE SET NULL` | у позик `member_id` стане NULL (стовпець має дозволяти NULL) |

`CASCADE` доречний для частин цілого (рядки замовлення без замовлення не мають сенсу). Для історії (позики, платежі) частіше забороняють видалення або позначають запис неактивним.

## Три види зв'язків

| Зв'язок | Приклад | Як зробити |
|---|---|---|
| один-до-багатьох | читач → його позики | зовнішній ключ у таблиці «багатьох» (`loans.member_id`) |
| багато-до-багатьох | книжки ↔ жанри | окрема **сполучна таблиця** з двома ключами |
| один-до-одного | читач → читацький квиток | зовнішній ключ + `UNIQUE` на ньому |

Сполучна таблиця для книжок і жанрів:

```sql
CREATE TABLE book_genres (
    book_id   INTEGER NOT NULL REFERENCES books (id) ON DELETE CASCADE,
    genre_id  INTEGER NOT NULL REFERENCES genres (id) ON DELETE CASCADE,
    PRIMARY KEY (book_id, genre_id)        -- складений ключ: пара не повторюється
);
```

## Нормалізація без фанатизму

Головна ідея: **кожен факт зберігається в одному місці**.

| Погано | Чому | Краще |
|---|---|---|
| `books.genres = 'fantasy,classic'` | не знайти книжки жанру, не перевірити назву жанру | сполучна таблиця `book_genres` |
| `loans.member_email` поруч з `member_id` | змінив email — і старі позики показують старий | лише `member_id`, email — у `members` |
| `members.phone1`, `phone2`, `phone3` | четвертий телефон не влазить | таблиця `member_phones` |

Але копія буває **іншим фактом**. Ціна в рядку замовлення (`unit_price`) — не дублікат ціни товару, а ціна **на момент покупки**: товар подорожчає, а стара покупка не має змінитись.

## Гроші й час

- Гроші — цілими числами в найменших одиницях (копійки) або `NUMERIC` / `Decimal`, **не** `float`: `0.1 + 0.2 != 0.3`.
- Дати в SQLite — текст ISO 8601 (`'2026-03-20'`, `'2026-03-20T10:15:00Z'`): такі рядки правильно сортуються й порівнюються. Час краще зберігати в UTC.

## Індекси

Індекс — окрема відсортована структура, що прискорює пошук за стовпцем (як алфавітний покажчик у книжці): `CREATE INDEX idx_loans_member ON loans (member_id);`. Його варто мати на стовпцях з `WHERE` і `JOIN`. Ціна — місце і повільніші `INSERT` / `UPDATE` (індекс теж треба оновити). `PRIMARY KEY` і `UNIQUE` створюють індекс автоматично.

> [!QA]
> Обмеження — остання лінія оборони, і їх теж тестують: спробуй вставити дубль email, від'ємну кількість, позику неіснуючого читача — база має відповісти `IntegrityError`. Такий тест одразу ловить забутий `PRAGMA foreign_keys = ON`.

## Підсумок
- Правила даних — у схемі: `PRIMARY KEY`, `NOT NULL`, `UNIQUE`, `CHECK`, `DEFAULT`, `REFERENCES`.
- У SQLite зовнішні ключі вмикають на кожному з'єднанні: `PRAGMA foreign_keys = ON`.
- Один-до-багатьох — ключ у таблиці «багатьох»; багато-до-багатьох — сполучна таблиця зі складеним ключем; один-до-одного — ключ + `UNIQUE`.
- Кожен факт — в одному місці; знімок на момент події (ціна покупки) — окремий факт.
- Гроші — не `float`; індекси прискорюють читання, але сповільнюють запис.
