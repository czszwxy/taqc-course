# Динамічне програмування, жадібні алгоритми і задача на співбесіді

Останній урок модуля — про два підходи до задач оптимізації («найменше», «найбільше», «скільки способів») і про те, як поводитися з будь-якою алгоритмічною задачею на співбесіді.

## Коли рекурсія рахує те саме тисячі разів

Скількома способами можна піднятися сходами з `n` сходинок, ступаючи на 1 або 2 сходинки? На останню сходинку приходять або з `n - 1`, або з `n - 2`:

```python
def ways(n):
    if n <= 1:
        return 1
    return ways(n - 1) + ways(n - 2)
```

Код правильний, але `ways(40)` рахує хвилинами: `ways(38)` обчислюється з двох гілок, `ways(37)` — з трьох, і так далі. Кількість викликів росте експоненційно.

## Розбір: скільки разів рахується кожна підзадача у ways(6)

| Виклик | Скільки разів обчислюється без кешу |
|---|---|
| `ways(5)` | 1 |
| `ways(4)` | 2 |
| `ways(3)` | 3 |
| `ways(2)` | 5 |
| `ways(1)` | 8 |

Це **перекривні підзадачі** — ознака динамічного програмування (DP). Рішення: рахувати кожну підзадачу **один раз**.

## Мемоізація: рекурсія + кеш

```python
from functools import cache


@cache
def ways(n):
    if n <= 1:
        return 1
    return ways(n - 1) + ways(n - 2)
```

Одна стрічка — і `ways(40)` миттєвий: кожне значення рахується раз і береться з кешу. Але для великих `n` рекурсія впреться в ліміт глибини.

## Таблиця знизу вгору

```python
def ways(n):
    table = [1, 1] + [0] * (n - 1)       # table[i] — кількість способів для i сходинок
    for step in range(2, n + 1):
        table[step] = table[step - 1] + table[step - 2]
    return table[n]
```

Ті самі формули, але від малих значень до великих, у циклі, без рекурсії. Схема DP у будь-якій задачі: **що означає `table[i]`** → **як отримати `table[i]` з менших** → **з чого почати** → **де відповідь**.

## Жадібні алгоритми

Жадібний алгоритм на кожному кроці бере найкращий **зараз** варіант. Видати решту гривневими номіналами (500, 200, 100, 50, 20, 10, 5, 2, 1) жадібно — щоразу найбільший, що влазить, — дає мінімальну кількість купюр і монет. Але це властивість саме таких номіналів, а не загальне правило:

| Монети 1, 3, 4, сума 6 | Монет |
|---|---|
| Жадібно: 4 + 1 + 1 | 3 |
| Оптимально: 3 + 3 | 2 |

Жадібність швидка і проста, але її правильність треба довести (або знайти контрприклад). Якщо контрприклад є — потрібне DP.

## Один прохід замість двох циклів

Багато задач «найкраща пара (i, j), i < j» розв'язуються одним проходом, якщо пам'ятати найкраще, що було **досі**. Приклад: найбільший приріст відвідувачів між двома днями (спершу менший день, потім більший) — достатньо пам'ятати мінімум до поточного дня.

## Задача на співбесіді: покроково

| Крок | Що робити вголос |
|---|---|
| 1. Зрозуміти | перефразувати умову, уточнити вхід, обмеження, порожні дані, повтори, від'ємні числа |
| 2. Приклади | розібрати 1–2 маленькі приклади руками, включно з граничним |
| 3. Просте рішення | описати «в лоб» і його складність — це вже бал |
| 4. Оптимізація | шукати знайомий прийом: множина / словник, два вказівники, сортування, вікно, BFS, DP |
| 5. Код | писати, пояснюючи; змістовні назви; невеликі функції |
| 6. Перевірка | пройти код руками на прикладах і граничних випадках |
| 7. Складність | назвати час і пам'ять, сказати, що можна покращити |

Інтерв'юер оцінює не лише відповідь, а й мислення: мовчазне правильне рішення гірше за озвучене просте з чесною оцінкою складності.

## Типові помилки

- Рекурсія без кешу для задач з перекривними підзадачами — експоненційний час.
- Жадібне рішення без перевірки контрприкладів.
- У DP переплутати порядок циклів (кількість **комбінацій** монет ≠ кількість **послідовностей**).
- Почати писати код, не уточнивши умову і граничні випадки.

## Підсумок

- Перекривні підзадачі → DP: мемоізація (`@cache`) або таблиця знизу вгору.
- Схема DP: значення `table[i]`, перехід, початкові значення, відповідь.
- Жадібний алгоритм — лише коли доведено, що локально найкращий крок веде до глобального оптимуму.
- «Найкраща пара i < j» часто розв'язується одним проходом з пам'яттю про найкраще досі.
- На співбесіді: зрозуміти → приклади → просте рішення → оптимізація → код → перевірка → складність.
