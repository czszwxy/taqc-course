# Хеш-таблиці: dict і set в алгоритмах

Половина задач співбесіди «оптимізуй з `O(n²)` до `O(n)`» розв'язується одним прийомом: замість вкладеного циклу — словник або множина. Щоб користуватися цим свідомо, корисно знати, що відбувається всередині.

## Як dict знаходить ключ за O(1)

| Крок | Що відбувається з `prices["KB-01"]` |
|---|---|
| 1 | Python рахує `hash("KB-01")` — велике ціле число |
| 2 | з хешу обчислює номер «кошика» (комірки) у внутрішній таблиці |
| 3 | дивиться в цю комірку: там ключ з таким самим хешем? |
| 4 | якщо хеш збігся — порівнює ключі через `==` (бо різні ключі можуть мати однаковий хеш — **колізія**) |
| 5 | знайшов — повертає значення; ні — пробує наступну комірку за правилом |

Перебору всіх ключів немає: кілька кроків незалежно від розміру словника. Тому пошук, вставка і видалення — `O(1)` **у середньому**. Множина влаштована так само, лише без значень.

## Чому ключ має бути незмінним

Хеш рахують під час вставки. Якби ключ змінився, він лежав би в «чужому» кошику і вже не знаходився б. Тому ключами можуть бути лише **хешовані** (незмінні) значення: `str`, `int`, `tuple` з незмінних, `frozenset`. Список як ключ дасть `TypeError: unhashable type: 'list'` — замість нього беруть `tuple(...)`.

## Патерн 1: підрахунок частот

```python
from collections import Counter

counts = Counter(order["user_id"] for order in orders)    # O(n)
returning_customers = [user for user, count in counts.items() if count > 1]
```

Замість «для кожного користувача порахувати `list.count`» (`O(n²)`) — один прохід.

## Патерн 2: «доповнення» — шукати те, чого бракує

Задача: два товари на суму `budget` у **невідсортованому** списку. Для кожної ціни питаємо: «чи бачили ми вже `budget - price`?»

```python
def has_pair(prices, budget):
    seen = set()
    for price in prices:
        if budget - price in seen:
            return True
        seen.add(price)
    return False
```

## Розбір: has_pair([500, 900, 300, 700], 1000)

| price | шукаємо `1000 - price` | `seen` до кроку | Результат |
|---|---|---|---|
| 500 | 500 | `{}` | немає → додати 500 |
| 900 | 100 | `{500}` | немає → додати 900 |
| 300 | 700 | `{500, 900}` | немає → додати 300 |
| 700 | 300 | `{500, 900, 300}` | **є** → `True` |

Порядок «спершу перевірити, потім додати» не дає елементу утворити пару сам із собою (500 + 500 при одному товарі за 500). Щоб повернути не `True`, а **індекси**, замість множини беруть словник «ціна → індекс».

## Патерн 3: групування за підписом

Елементи, «однакові з точністю до…», групують за ключем-підписом: анаграми — `tuple(sorted(word))`, запити з тими самими словами в іншому порядку — `tuple(sorted(query.lower().split()))`, email без регістру — `email.lower()`.

```python
groups = {}
for word in ["listen", "silent", "enlist", "google"]:
    groups.setdefault("".join(sorted(word)), []).append(word)
list(groups.values())    # [['listen', 'silent', 'enlist'], ['google']]
```

## Патерн 4: повтори без втрати порядку

```python
list(dict.fromkeys(["b", "a", "b", "c", "a"]))     # ['b', 'a', 'c']
```

`set(...)` теж прибирає повтори, але **не зберігає порядок**. Словник зберігає порядок вставки (з Python 3.7), тож `dict.fromkeys` — коротке рішення.

## Ціна

Хеш-таблиця займає `O(n)` пам'яті і в гіршому випадку (багато колізій) деградує, але для звичайних даних це найкращий інструмент «знайти швидко».

## Типові помилки

- Список як ключ словника або елемент множини — `unhashable type`.
- `set(...)`, коли важливий порядок.
- «Спершу додати, потім перевірити» в задачі про пари — елемент парується сам із собою.
- Змінювати об'єкт, який уже лежить у множині як ключ (наприклад, власний клас з `__hash__` за змінним полем).

## Підсумок

- `dict` і `set`: хеш → кошик → порівняння `==` лише при збігу хешу; у середньому `O(1)`.
- Ключі — лише хешовані (незмінні) значення; список → `tuple`.
- Патерни: частоти (`Counter`), доповнення (`budget - price in seen`), групування за підписом, `dict.fromkeys` для повторів.
- Платимо пам'яттю `O(n)` за швидкість.
