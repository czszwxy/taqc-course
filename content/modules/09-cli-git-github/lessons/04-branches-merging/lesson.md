# Гілки й злиття

У команді одночасно пишуть тести на логін, кошик і пошук. Якщо всі комітять в одне місце, незавершена робота одного ламає прогін іншим. **Гілки** (branches) розв'язують це: кожна задача живе окремо, а в основну гілку потрапляє лише готове.

## Що таке гілка

Гілка — це просто **рухомий вказівник на коміт**. Основна гілка зазвичай називається `main` (у старих проєктах `master`). Створити гілку означає поставити новий вказівник. Це миттєво, файли не копіюються.

```text
main:              A ── B ── C
                              \
feature/search-tests:          D ── E      ← HEAD (ти тут)
```

**HEAD** показує, де ти зараз: у якій гілці і на якому коміті. Нові коміти додаються в поточну гілку.

## Команди

```bash
git branch                          # список локальних гілок (* — поточна)
git switch -c feature/search-tests  # створити гілку і перейти в неї
git switch main                     # перейти в існуючу гілку
git merge feature/search-tests      # влити вказану гілку в ПОТОЧНУ
git branch -d feature/search-tests  # видалити гілку, яку вже влито
git log --oneline --graph --all     # історія з «деревом» гілок
```

Старий синтаксис, який часто зустрічається в статтях: `git checkout -b <гілка>` = `git switch -c <гілка>`, `git checkout main` = `git switch main`.

> [!WARNING]
> Перед перемиканням гілок закоміть (або відклади через `git stash`) незбережені зміни. Інакше Git або не дасть перемкнутися, або перенесе зміни з собою в іншу гілку, і це заплутує.

## Злиття (merge)

`git merge X` вливає гілку X у **поточну**. Тому спершу перейди туди, **куди** вливаєш:

```bash
git switch main
git merge feature/search-tests
```

Є два варіанти злиття:

- **fast-forward**: у `main` не з'явилося нових комітів, відколи створили гілку. Git просто пересуває вказівник `main` вперед, нового коміту не створюється;
- **merge commit**: обидві гілки мають нові коміти. Git створює спеціальний коміт злиття з двома «батьками».

```text
main:    A ── B ── C ────────── M      ← merge commit
                    \          /
feature:             D ── E ──
```

Якщо обидві гілки змінили **ті самі рядки** одного файлу, Git не знає, яку версію взяти. Виникає **конфлікт** (урок 6).

## Назви гілок

Типова домовленість — префікс за типом задачі + короткий опис:

| Гілка | Для чого |
|---|---|
| `feature/cart-tests` | нові тести / функціональність |
| `fix/flaky-login-test` | виправлення |
| `chore/upgrade-playwright` | технічна робота |
| `test/QA-142-checkout-negative` | з номером задачі з трекера |

Малі літери, слова через дефіс, без пробілів. Злиту гілку видаляють, щоб не накопичувати сміття.

> [!QA]
> Гілки — це ще й ізоляція для тестування. Розробник робить фічу в `feature/new-checkout`, CI проганяє автотести саме на цій гілці, і лише після зеленого прогону й рев'ю гілку вливають у `main`. Тоді `main` завжди лишається «зеленою».

## Типовий цикл задачі

```bash
git switch main                      # 1. з основної гілки
git switch -c fix/login-error-text   # 2. нова гілка під задачу
# … змінюєш файли, запускаєш тести …
git add .                            # 3. зміни в staging
git commit -m "Fix expected error text in login test"
git switch main                      # 4. повертаєшся в main
git merge fix/login-error-text       # 5. вливаєш
git branch -d fix/login-error-text   # 6. прибираєш гілку
```

У команді кроки 4–5 зазвичай роблять не локально, а через **pull request** на GitHub (наступний урок).

## Підсумок

- Гілка — рухомий вказівник на коміт. `main` — основна гілка, HEAD показує, де ти зараз.
- `git switch -c <нова>` створює гілку, `git switch <назва>` перемикає, `git branch` показує список.
- `git merge X` вливає X у **поточну** гілку: спершу перейди в ту, куди вливаєш.
- Fast-forward просто пересуває вказівник, merge commit об'єднує дві лінії історії.
- Назви гілок: `feature/…`, `fix/…`, малі літери через дефіс. Злиті гілки видаляй (`git branch -d`).
