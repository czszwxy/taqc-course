# Етикет код-рев'ю

**Code review** — колега читає твої зміни в pull request до злиття. Мета — не «знайти винного», а зробити код кращим і поділитися знаннями. Для QA Automation рев'ю двостороннє: твої тести рев'юють розробники й старші автоматизатори, а ти рев'юїш їхні тести й зміни.

## Навіщо рев'ю

- ловить помилки раніше, ніж вони потраплять у `main` (і в CI всієї команди);
- тримає код однорідним: однакові підходи, назви, структура;
- поширює знання: більше ніж одна людина розуміє кожну частину;
- для новачка це найшвидший спосіб навчитися.

## На що дивитися в тестовому коді

| Питання | Поганий знак |
|---|---|
| Тест щось **перевіряє**? | немає `expect` — тест «проходить», навіть коли все зламано |
| Очікування розумні? | `waitForTimeout(5000)` — повільно й нестабільно (flaky) |
| Тест незалежний? | покладається на дані чи стан після іншого тесту |
| Немає секретів? | пароль або токен прямо в коді |
| Зрозуміло, що перевіряє? | назва `test1`, магічні числа без пояснень |
| Локатори стабільні? | `page.click('button')`, довгі CSS-ланцюжки, `nth(7)` |
| Працює на будь-якому середовищі? | захардкоджена адреса staging замість `baseURL` |
| Покрито вимогу? | немає негативних кейсів, межових значень |

> [!QA]
> Найнебезпечніший тест — той, що нічого не перевіряє: він завжди зелений і дає хибне відчуття безпеки. Під час рев'ю спершу знайди `expect` і переконайся, що тест **може впасти**. Пригадай модуль 14: тест, що не ловить жодного мутанта, марний.

## Як писати коментарі

**Коментуй код, а не людину.** Пояснюй **чому** і пропонуй **як**.

| Замість | Краще |
|---|---|
| «Це неправильно.» | «Тут `waitForTimeout(3000)`. Тест чекатиме 3 с навіть тоді, коли сторінка готова за 0.5 с, і впаде, якщо API відповість за 3.5 с. Може, краще `await expect(cartBadge).toHaveText('1')`? Воно чекає рівно стільки, скільки треба.» |
| «Хто так пише?» | «Мені не зовсім зрозуміло, навіщо тут другий логін. Це навмисно?» |
| «Перепиши.» | «Пропоную винести логін у helper: він повторюється в 4 тестах.» |

Корисні позначки:

- **nit:** — дрібниця, не блокує злиття (`nit: назва могла б бути 'shows error for wrong password'`);
- **question:** — справжнє питання, а не прихована критика;
- **suggestion:** — пропозиція з прикладом коду (на GitHub є кнопка «Suggest changes»).

Не забувай хвалити те, що зроблено добре («👍 гарне рішення з фікстурою»). Рев'ю — розмова, а не список вироків.

## Рішення рев'юера

- **Approve** — можна зливати (можливо, з дрібними nit-ами);
- **Request changes** — є проблеми, які треба виправити до злиття (немає перевірок, секрет у коді, тест нестабільний);
- **Comment** — питання або загальні думки без рішення.

## Коли рев'юють тебе

- Коментар — про код, не про тебе. Подякуй і розберися.
- Не погоджуєшся? Аргументуй спокійно або запропонуй коротко обговорити голосом.
- Виправлення пуш **новими комітами**, щоб рев'юер бачив, що змінилося, і відповідай на кожен коментар («Done», «Fixed in a1b2c3d», «Left as is because…»).
- Не роби величезних PR: 200 рядків рев'юють уважно, 2000 — «LGTM» не дивлячись.

## Підсумок

- Рев'ю потрібне для якості, однорідності й навчання, а не для пошуку винних.
- У тестах перевіряй: чи є `expect`, чи немає жорстких очікувань, чи тести незалежні, чи немає секретів, чи зрозумілі назви, чи стабільні локатори, чи немає захардкодженого середовища.
- Коментуй код, а не людину: «чому» + «як». Позначки `nit:`, `question:`, `suggestion:`.
- Approve / Request changes / Comment. Секрети й тести без перевірок блокують злиття.
- На рев'ю свого коду відповідай на кожен коментар і пуш виправлення новими комітами.
