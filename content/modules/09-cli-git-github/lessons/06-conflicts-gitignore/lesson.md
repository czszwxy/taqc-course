# Конфлікти злиття і .gitignore

## Звідки береться конфлікт

Git сам зливає зміни, якщо вони в різних файлах або в різних місцях одного файлу. **Конфлікт** виникає, коли дві гілки змінили **ті самі рядки** по-різному. Тоді Git не вгадує, а зупиняється і просить людину вирішити.

```text
CONFLICT (content): Merge conflict in tests/data/users.ts
Automatic merge failed; fix conflicts and then commit the result.
```

`git status` покаже такий файл як **both modified**.

## Маркери конфлікту

У файлі з'являються обидві версії, розділені маркерами:

```text
<<<<<<< HEAD
  admin: { email: 'qa.admin@gadgetly.test' },
=======
  admin: { email: 'admin@gadgetly.test' },
>>>>>>> feature/blocked-user-tests
```

- між `<<<<<<< HEAD` і `=======` — версія **поточної** гілки (куди вливаємо, наприклад `main`);
- між `=======` і `>>>>>>> назва` — версія гілки, **яку вливаємо**.

## Як розв'язати

1. Відкрий файл і знайди всі маркери (пошук за `<<<<<<<`).
2. Для кожного місця вирішіть, яким має бути **правильний результат**: взяти одну версію, другу або **поєднати обидві**.
3. Видали всі три маркери.
4. **Перевір**: код компілюється, тести проходять.
5. `git add <файл>`, щоб позначити конфлікт розв'язаним.
6. `git commit`, щоб завершити злиття.

Передумав зливати? `git merge --abort` поверне все як було до `merge`.

> [!WARNING]
> «Розв'язати» не означає «прибрати маркери». Найчастіша помилка — бездумно натиснути «Accept Current» або «Accept Incoming» і втратити чужу зміну. Часто правильна відповідь — **поєднання** обох. Наприклад, `main` змінив адресу сторінки, а твоя гілка додала параметр, і потрібні обидві зміни.

У VS Code над конфліктом є кнопки **Accept Current Change / Accept Incoming Change / Accept Both Changes / Compare Changes** і окремий Merge Editor. Вони зручні, але рішення все одно приймаєш ти.

> [!QA]
> Після розв'язання конфлікту в тестовому коді **обов'язково запусти тести**. Синтаксично правильний, але логічно неправильний результат злиття — класичне джерело «таємничих» падінь: тест чекає старий текст, у даних лишився видалений користувач.

## Як зменшити кількість конфліктів

- маленькі PR і короткоживучі гілки;
- частіше підтягуй `main` у свою гілку (`git pull` / `git merge main`);
- домовляйтеся, хто що змінює в спільних файлах (конфіги, тестові дані).

**package-lock.json** з конфліктом руками не правлять: візьми версію з `main`, виконай `npm install` (lock перегенерується) і закоміть результат.

## .gitignore

Файл `.gitignore` у корені репозиторію перелічує, що Git має **ігнорувати**: не показувати в `status` і не комітити.

```text
# залежності — відтворюються npm install
node_modules/

# результати прогонів — генеруються кожного разу
test-results/
playwright-report/
*.log

# секрети й локальні налаштування
.env
.env.local

# системне сміття
.DS_Store
Thumbs.db
```

- `папка/` ігнорує папку, `*.log` — усі файли з розширенням `.log`;
- `!` скасовує правило: `!.env.example` (зразок без справжніх значень **комітять**, щоб колеги знали, які змінні потрібні);
- `#` починає коментар.

Що комітимо: вихідний код і тести, `package.json`, `package-lock.json`, конфіги (`playwright.config.ts`, `tsconfig.json`), README. Не комітимо те, що **генерується** (node_modules, звіти), і те, що **секретне** або **особисте** (.env, налаштування IDE).

> [!WARNING]
> `.gitignore` не діє на файли, які **вже** закомічені. Щоб перестати відстежувати такий файл: `git rm --cached .env`, додай його в `.gitignore` і закоміть. Якщо в репозиторій потрапив **секрет** (пароль, токен), він лишається в історії назавжди. Секрет треба вважати скомпрометованим: **змінити** його (rotate) і повідомити команду.

## Підсумок

- Конфлікт — дві гілки змінили ті самі рядки. Git позначає їх `<<<<<<<`, `=======`, `>>>>>>>`.
- Верхня частина — поточна гілка (HEAD), нижня — та, що вливається. Результат може бути однією з них або поєднанням.
- Кроки: виправити файл → прибрати маркери → запустити тести → `git add` → `git commit`. Відмовитися від злиття: `git merge --abort`.
- `.gitignore` виключає згенероване (node_modules, звіти) і секрети (.env). `.env.example` комітять.
- Закомічений секрет треба замінити: з історії він нікуди не зникне.
