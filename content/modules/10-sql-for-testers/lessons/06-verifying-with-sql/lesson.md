# Перевірка результатів тестів через SQL

Ти вже вмієш читати, групувати, поєднувати й змінювати дані. Тепер про те, як це використовується в щоденній роботі тестувальника. SQL — це спосіб побачити, **що насправді сталося** за UI і API.

## Перевірка після дії (grey-box)

Тест «оформити замовлення» в UI закінчується повідомленням «Дякуємо, замовлення №1003 створено». Але повідомлення — лише текст. Перевірка в БД відповідає на важливіші питання:

```sql
-- 1. Замовлення існує, належить правильному користувачу, правильний статус і сума?
SELECT id, user_id, status, total FROM orders WHERE id = 1003;

-- 2. Позиції правильні: товари, кількість, ціна на момент покупки?
SELECT product_id, quantity, unit_price FROM order_items WHERE order_id = 1003;

-- 3. Сума замовлення = сума позицій?
SELECT SUM(quantity * unit_price) FROM order_items WHERE order_id = 1003;

-- 4. Нічого зайвого: створено РІВНО одне замовлення (а не два після подвійного кліку)?
SELECT COUNT(*) FROM orders WHERE user_id = 42 AND created_at >= '2024-10-02';
```

Такий підхід називають **grey-box**: тест іде через інтерфейс, як користувач, а перевіряє ще й «нутрощі».

> [!QA]
> Подвійний клік на «Оформити» → два однакові замовлення. В UI цього не видно, бо показується лише останнє. Видно це тільки в БД (`COUNT(*)` до і після). Це реальний і поширений баг.

## Перевірки цілісності даних

Окремий вид перевірок — пошук «неможливих» даних. Їх запускають після міграцій, імпортів і релізів, а іноді щоночі за розкладом:

| Що шукаємо | Шаблон запиту |
|---|---|
| Сума не збігається з деталями | `JOIN` + `GROUP BY` + `HAVING o.total <> SUM(i.quantity * i.unit_price)` |
| Недопустиме значення (enum) | `WHERE status NOT IN ('created', 'paid', 'shipped', 'delivered', 'cancelled')` |
| Значення поза діапазоном | `WHERE quantity <= 0`, `WHERE price <= 0` |
| «Осиротілий» запис: посилання в нікуди | `LEFT JOIN users u ON u.id = o.user_id WHERE u.id IS NULL` |
| Батько без дітей (замовлення без позицій) | `LEFT JOIN order_items i ON i.order_id = o.id WHERE i.id IS NULL` |
| Дублікати | `GROUP BY LOWER(email) HAVING COUNT(*) > 1` |
| Порожні обов'язкові поля | `WHERE email IS NULL OR email = ''` |
| Залишені тестові дані | `WHERE name LIKE '%test%'` |

> [!TIP]
> Добрий запит для перевірки цілісності повертає **0 рядків, коли все гаразд**. Кожен рядок у результаті — знайдений дефект. Такі запити легко автоматизувати: тест падає, якщо результат не порожній.

## Дублікати і регістр

`UNIQUE` на `email` порівнює текст з урахуванням регістру. Тому `Olena.Kovalenko@…` і `olena.kovalenko@…` для бази різні значення. Для людини й для пошти це одна адреса: двоє акаунтів, плутанина з паролями й замовленнями. Шукаємо так:

```sql
SELECT LOWER(email), COUNT(*)
FROM users
GROUP BY LOWER(email)
HAVING COUNT(*) > 1;
```

`LOWER()` переводить текст у нижній регістр (`UPPER()` — у верхній).

## SQL як доказ у баг-репорті

Баг у даних найкраще доводити запитом і його результатом:

```text
Summary: Order 1013 total (5000) does not match the sum of its items (2999)
Evidence:
  SELECT o.id, o.total, SUM(i.quantity * i.unit_price) AS items_sum
  FROM orders o JOIN order_items i ON i.order_id = o.id
  WHERE o.id = 1013 GROUP BY o.id, o.total;
  → 1013 | 5000 | 2999
```

Розробник копіює запит, бачить те саме і одразу розуміє, де шукати. Вказуй, **на якій базі** (середовище, після якого імпорту чи релізу) це знайдено. Не копіюй зайвих персональних даних клієнтів: потрібні лише id.

## Безпека і доступи

- На production у тестувальника зазвичай доступ **лише на читання**, і то не завжди. Важкі запити до великої бази можуть сповільнити сайт для клієнтів.
- Знайдений дефект даних **не виправляй сам**, а репорть: можливо, ці дані ще потрібні для розслідування.
- В автотестах (модулі про Playwright) до БД звертаються через бібліотеку-клієнт. Логіка перевірок буде та сама, що й у цьому уроці.

## Підсумок

- Перевірка в БД після дії в UI/API (grey-box) ловить те, чого не видно в інтерфейсі: дублікати, неправильні суми, зайві записи.
- Перевірки цілісності: суми, enum-значення, діапазони, осиротілі записи, батьки без дітей, дублікати, тестові дані.
- Хороший запит-перевірка повертає 0 рядків, коли все гаразд.
- Дублікати без урахування регістру шукають через `GROUP BY LOWER(email) HAVING COUNT(*) > 1`.
- SQL-запит з результатом — найкращий доказ у баг-репорті. Дані на production не виправляй сам.
