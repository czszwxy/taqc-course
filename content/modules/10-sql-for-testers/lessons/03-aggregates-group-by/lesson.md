# Агрегати й GROUP BY

Сторінка «Мої замовлення» пише «Усього: 2 замовлення на 20 645 грн». У дашборді адміністратора видно «Доставлено: 5». Звідки взялися ці числа? Їх рахує запит з **агрегатними функціями**. Тестувальник пише такий самий запит сам і порівнює результат з тим, що показує UI.

## Агрегатні функції

Агрегат «згортає» багато рядків в одне значення:

| Функція | Що рахує | Приклад |
|---|---|---|
| `COUNT(*)` | кількість рядків | `SELECT COUNT(*) FROM orders;` → 12 |
| `COUNT(колонка)` | кількість **не NULL** значень | `COUNT(city)` → 9 (у користувача 9 міста немає) |
| `SUM(x)` | суму | `SUM(total)` |
| `AVG(x)` | середнє | `AVG(price)` |
| `MIN(x)`, `MAX(x)` | найменше / найбільше | `MIN(price)`, `MAX(created_at)` |

```sql
SELECT COUNT(*), SUM(total), MAX(total)
FROM orders
WHERE status = 'delivered';     -- WHERE відфільтровує рядки ДО підрахунку
```

> [!WARNING]
> `COUNT(*)` і `COUNT(city)` — різні речі. Перший рахує всі рядки, другий пропускає `NULL`. Якщо UI каже «9 користувачів вказали місто», а ти рахуєш `COUNT(*)`, отримаєш 10 і зарепортиш неіснуючий баг.

## ROUND

`AVG` часто дає дріб: `34665.666…`. `ROUND(x)` округлює до цілого, `ROUND(x, 2)` — до 2 знаків:

```sql
SELECT ROUND(AVG(price)) FROM products WHERE category = 'Laptops';   -- 34666.0
```

> [!QA]
> Округлення — постійне джерело багів: 34665.67 чи 34666? Округлювати вгору чи до найближчого? Округлювати кожну позицію чи загальну суму? Коли числа в UI і в запиті трохи розходяться, спершу з'ясуй, яке правило округлення в **вимогах**.

## GROUP BY — підсумок для кожної групи

`GROUP BY` ділить рядки на групи з однаковим значенням і рахує агрегат **для кожної групи**:

```sql
SELECT status, COUNT(*)
FROM orders
GROUP BY status;
```

| status | COUNT(*) |
|---|---|
| cancelled | 2 |
| created | 1 |
| delivered | 5 |
| paid | 2 |
| shipped | 2 |

Правило: у `SELECT` поряд з агрегатами можна писати лише колонки з `GROUP BY`. Запит `SELECT status, id, COUNT(*) … GROUP BY status` некоректний: яке `id` показати, якщо в групі 5 замовлень? (SQLite мовчки візьме якесь одне, PostgreSQL видасть помилку.)

Сортувати можна й за агрегатом:

```sql
SELECT user_id, SUM(total) AS spent
FROM orders
GROUP BY user_id
ORDER BY spent DESC;
```

## HAVING — фільтр для груп

`WHERE` фільтрує **рядки до** групування, `HAVING` фільтрує **групи після**:

```sql
-- користувачі, у яких більше одного замовлення
SELECT user_id, COUNT(*)
FROM orders
GROUP BY user_id
HAVING COUNT(*) > 1;

-- те саме, але рахуємо лише не скасовані замовлення
SELECT user_id, COUNT(*)
FROM orders
WHERE status <> 'cancelled'      -- спершу відкинули рядки
GROUP BY user_id
HAVING COUNT(*) > 1;             -- потім відкинули групи
```

У `WHERE` агрегат писати не можна: `WHERE COUNT(*) > 1` дасть помилку. Коли рядки фільтруються, кількість ще не порахована.

## Порядок частин запиту (повний)

```text
SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT …
```

> [!TIP]
> Пишучи агрегатний запит, спершу подумай: «що одна група?» (кожен користувач, кожен статус, кожна категорія). Це і є колонка для `GROUP BY`. Далі питання: «що порахувати в кожній групі?» Це агрегат у `SELECT`.

## Агрегати в тестуванні

- **Лічильники в UI**: «Кошик (3)», «Знайдено 14 товарів», «Доставлено: 5». Звір їх з `COUNT`.
- **Суми**: підсумок замовлення має дорівнювати `SUM(quantity * unit_price)` його позицій. Таку перевірку ти напишеш в уроці 6.
- **Дублікати**: `GROUP BY email HAVING COUNT(*) > 1` знаходить повтори.
- **До/після**: кількість рядків до тесту і після. Тест «створити замовлення» має додати рівно 1 рядок в `orders`.

## Підсумок

- `COUNT(*)` рахує рядки, `COUNT(колонка)` — не-NULL значення. Ще є `SUM`, `AVG`, `MIN`, `MAX`, а `ROUND` округлює.
- `GROUP BY` рахує агрегат для кожної групи. У `SELECT` — тільки колонки групування й агрегати.
- `WHERE` фільтрує рядки до групування, `HAVING` — групи після.
- Порядок: `SELECT … FROM … WHERE … GROUP BY … HAVING … ORDER BY … LIMIT`.
- Агрегати — головний інструмент для звірки лічильників і сум, які показує UI.
