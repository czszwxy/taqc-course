# INSERT, UPDATE, DELETE

Щоб протестувати сторінку «Замовлення в статусі paid», потрібне замовлення в статусі `paid`. Щоб перевірити повідомлення «Товар закінчився», потрібен товар з `in_stock = 0`. Готувати такі дані через UI довго, а SQL дає їх за секунди. Але команди, що **змінюють** дані, небезпечні: одна пропущена умова, і зіпсовано всю таблицю.

## INSERT — додати рядки

```sql
INSERT INTO users (id, email, name, city, created_at)
VALUES (11, 'new.tester@gadgetly.test', 'New Tester', 'Lviv', '2024-10-01');
```

- у дужках перелічено колонки, у `VALUES` — значення в **тому самому порядку**;
- колонки, яких немає в переліку, отримають `DEFAULT` (тут `role` стане `'customer'`) або `NULL`;
- кілька рядків за раз: `VALUES (…), (…), (…);`.

> [!QA]
> INSERT сам є тестом обмежень. Вставка другого користувача з тим самим email має впасти з `UNIQUE constraint failed`. Пропуск `name` має дати `NOT NULL constraint failed`. Якщо помилки немає, обмеження немає, і це знахідка.

## UPDATE — змінити рядки

```sql
UPDATE orders
SET status = 'paid'
WHERE id = 1006;
```

Кілька колонок змінюють через кому: `SET status = 'shipped', total = 2299`. Нове значення можна обчислити зі старого: `SET price = price + 500`.

## DELETE — видалити рядки

```sql
DELETE FROM order_items WHERE order_id = 1005;
DELETE FROM orders WHERE id = 1005;
```

Порядок важливий: спершу «діти» (`order_items`), потім «батько» (`orders`). Інакше лишаться позиції, що посилаються на неіснуюче замовлення. А якщо зовнішні ключі ввімкнені, база просто не дасть видалити замовлення.

## Золоте правило: спершу SELECT

> [!WARNING]
> `UPDATE orders SET status = 'paid';` **без WHERE** змінить **усі** замовлення. `DELETE FROM users;` видалить усіх користувачів. База не перепитає «ви впевнені?».

Безпечний порядок дій:

1. Напиши `SELECT` з потрібним `WHERE` і подивись, **які саме рядки** він знаходить і скільки їх.
2. Заміни `SELECT …` на `UPDATE … SET …` чи `DELETE`, а `WHERE` **залиш тим самим**.
3. Перевір кількість змінених рядків. Вона має збігтися з результатом кроку 1.
4. Знову виконай `SELECT` і переконайся, що дані стали такими, як треба.

```sql
SELECT id, status FROM orders WHERE status = 'paid' AND created_at < '2024-09-10';  -- 1 рядок
UPDATE orders SET status = 'shipped' WHERE status = 'paid' AND created_at < '2024-09-10';
SELECT id, status FROM orders ORDER BY id;   -- перевірка
```

> [!TIP]
> У SQL-завданнях кнопка **▶ Run** для зміни даних показує, скільки рядків змінилося, і результат перевірочного запиту. Якщо змінилося 12 рядків, а мав один, ти забув `WHERE`. Добре, що це лише копія бази.

## Транзакції

Транзакція об'єднує кілька команд у «все або нічого»:

```sql
BEGIN;
DELETE FROM order_items WHERE order_id = 1005;
DELETE FROM orders WHERE id = 1005;
-- подивились SELECT-ом, що все правильно
COMMIT;      -- зберегти   (або ROLLBACK; — скасувати все від BEGIN)
```

В автотестах транзакції іноді використовують так: тест працює всередині транзакції, а в кінці робиться `ROLLBACK`, і база повертається в початковий стан.

## Гігієна тестових даних

- **Ніколи** не змінюй дані на production без явного дозволу й процедури. Тестувальнику зазвичай дають доступ лише на читання (read-only).
- На спільному test/staging працюють інші люди. Не змінюй «чужі» записи, створюй свої.
- Позначай тестові дані: `qa+test-123@gadgetly.test`, назва `TEST …`. Так їх легко знайти й прибрати.
- Прибирай за собою (cleanup) або використовуй дані, які тест створює сам. Залишені тестові дані потім «вилазять» у звітах і на вітрині. В уроці 6 ти знайдеш саме такий товар.

## Підсумок

- `INSERT INTO таблиця (колонки) VALUES (…)` — додати. Пропущені колонки отримують `DEFAULT` або `NULL`.
- `UPDATE таблиця SET колонка = значення WHERE …` — змінити, `DELETE FROM таблиця WHERE …` — видалити.
- Без `WHERE` зміна стосується **всіх** рядків. Спершу `SELECT` з тим самим `WHERE`, потім зміна, потім перевірка.
- Видаляй спершу дочірні записи (`order_items`), потім батьківські (`orders`).
- `BEGIN … COMMIT / ROLLBACK` — «все або нічого». Тестові дані позначай і прибирай, production не чіпай.
