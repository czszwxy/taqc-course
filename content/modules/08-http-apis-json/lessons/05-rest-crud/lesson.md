# REST і CRUD

**REST** — найпоширеніший стиль побудови API. Він не є суворим стандартом, але має домовленості, які роблять API передбачуваним. Знаючи їх, ти одразу бачиш, що тестувати, і помічаєш, коли API поводиться «дивно».

## Ресурси й адреси

У REST усе — **ресурси** (товари, замовлення, користувачі). Адреса називає ресурс **іменником у множині**, а дію задає **метод**:

| ✅ REST-стиль | ❌ Не REST |
|---|---|
| `GET /orders` | `GET /getAllOrders` |
| `POST /orders` | `POST /createOrder` |
| `DELETE /orders/1002` | `GET /orders/delete?id=1002` |

- **Колекція**: `/orders` — список.
- **Елемент**: `/orders/1002` — один ресурс.
- Вкладені ресурси: `/orders/1002/items`.

## CRUD ↔ HTTP

| CRUD | Метод | Адреса | Успіх |
|---|---|---|---|
| **C**reate | `POST` | `/orders` | **201** + `Location` |
| **R**ead (список) | `GET` | `/orders` | **200** |
| **R**ead (один) | `GET` | `/orders/{id}` | **200** |
| **U**pdate (повністю) | `PUT` | `/orders/{id}` | **200** (або 204) |
| **U**pdate (частково) | `PATCH` | `/orders/{id}` | **200** (або 204) |
| **D**elete | `DELETE` | `/orders/{id}` | **204** (або 200) |

## Інші домовленості

- **Stateless**: кожен запит самодостатній — несе токен і все потрібне; сервер не «пам'ятає» попередній запит.
- **Пагінація, фільтри, сортування** — через query: `?page=2&limit=10&category=Phones&sort=price`.
- **Версіонування**: `/api/v1/…`, `/api/v2/…` — старі клієнти не ламаються.
- **Помилки** в єдиному форматі: `{ "error": "…" }` з правильним 4xx/5xx.

## Як тестувати CRUD: повний цикл

```text
1. POST   /orders            → 201, Location: /orders/1003, body has id/total
2. GET    /orders/1003       → 200, the same data as in step 1
3. GET    /orders            → 200, the list contains 1003
4. PATCH  /orders/1003       → 200, the field changed, dependent fields recalculated
5. GET    /orders/1003       → the change is really saved
6. DELETE /orders/1003       → 204
7. GET    /orders/1003       → 404, and the list no longer contains it
```

> [!QA]
> Найважливіше правило API-тестування змін: **перевір, що зміна збереглася**, окремим GET-запитом. Відповідь `200` на PATCH ще не означає, що дані змінилися в базі. І перевір **залежні** поля: змінив кількість — чи перерахувалась сума?

> [!TIP]
> Тестові дані, які ти створюєш (замовлення, користувачі), треба **прибирати** після тесту (DELETE або reset). Інакше наступні тести стартуватимуть з «брудного» стану. У Gadgetly API для цього є `POST /api/reset`.

## Підсумок

- Ресурси — іменники в множині; дія — метод.
- Create → POST 201; Read → GET 200; Update → PUT/PATCH 200; Delete → DELETE 204.
- Після зміни — GET, щоб переконатися, що зміна збереглась; перевіряй залежні поля.
- Прибирай тестові дані після себе.
