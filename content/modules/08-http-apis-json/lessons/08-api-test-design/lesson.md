# Дизайн API-тестів

Ти вже вмієш надсилати запити. Тепер головне питання: **що** перевіряти, щоб знайти баги, а не просто переконатися, що «щось повернулося». Техніки тест-дизайну з модуля 03 (EP, BVA, таблиці рішень, переходи станів) працюють і для API — змінюється лише «інтерфейс».

## Що перевіряти у відповіді

| Рівень | Приклади перевірок |
|---|---|
| **Статус** | 201 на створення, 400 на невалідні дані, 401/403 на доступ |
| **Заголовки** | `Content-Type: application/json`, `Location` після 201 |
| **Структура (схема)** | усі поля є, типи правильні (`quantity` — number), немає зайвих (паролів!) |
| **Значення** | `productId` такий, як надіслали; `status: "created"` |
| **Бізнес-правила** | `total = unitPrice × quantity`; знижки; ліміти |
| **Стан системи** | після POST — GET знаходить ресурс; після DELETE — 404 |
| **Формат помилок** | `{ "error": "…" }` з зрозумілим текстом, однаковий скрізь |
| **Нефункціональне** | час відповіді, розмір, поведінка під навантаженням |

## Які запити надсилати

**Позитивні**: типові валідні дані, мінімальні й максимальні допустимі значення.

**Негативні** — кожне поле окремо:

- відсутнє поле; `null`; порожній рядок;
- не той тип: `"2"` замість `2`, `true` замість числа;
- межі: `0`, `1`, `10`, `11` для quantity 1–10 (BVA!);
- неіснуючі посилання: `productId: 99999`;
- невалідний JSON; не той `Content-Type`; порожнє тіло;
- **зайві поля**: `"total": 1`, `"userId": 17` — сервер не повинен їм вірити.

**Доступ** (урок 6): без токена, невалідний токен, **чужий** ресурс, недостатня роль.

**Ідемпотентність і повтори**: повторний DELETE, подвійний POST, PUT з тими самими даними.

**Колекції**: пагінація (сторінки не перекриваються і не губляться елементи), фільтри окремо й разом, сортування, порожній результат.

> [!QA]
> Для пагінації перевір інваріант: якщо пройти **всі** сторінки, кожен елемент має з'явитися **рівно один раз**, а сума елементів — дорівнювати `total`.

## Формат API-тест-кейсу

```text
ID:        API-ORD-07
Title:     POST /orders rejects quantity 0
Pre:       logged in as qa@gadgetly.test (token)
Request:   POST /api/orders  {"productId": 1, "quantity": 0}
Expected:  400, body.error mentions quantity 1–10; GET /api/orders has no new order
```

## Баг-репорт для API

Замість кроків у UI — **запит**: метод, URL, заголовки (без секретів!), тіло. Actual — статус і фрагмент тіла. Expected — що за документацією. Додай `X-Request-Id` і, за можливості, cURL.

## Практика

У завданні 3 — Gadgetly API з **6 навмисними багами**. Документація — у жовтій панелі [API console](/playground/api). Використай свій чекліст із завдання 2.

## Підсумок

- Перевіряй статус, заголовки, схему й типи, значення, бізнес-правила, стан системи, формат помилок.
- Негативні тести для кожного поля: відсутнє, null, не той тип, межі, неіснуючі id, зайві поля.
- Доступ: без токена, чужий ресурс, роль. Ідемпотентність і повтори.
- Пагінація: без перекриттів і пропусків, сума = `total`.
