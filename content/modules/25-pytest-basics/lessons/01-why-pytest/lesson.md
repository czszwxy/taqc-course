# Чому pytest

Досі ти писав **функції**, а приховані тести їх перевіряли. Тепер ролі міняються: код уже написаний, а ти пишеш **тести**. Це і є робота автоматизатора. У Python для цього майже завжди використовують **pytest** — його вимагають у більшості вакансій Python QA Automation.

## Автотест — це функція

```python
# shop.py — код, який тестуємо
def slugify(title):
    return title.strip().lower().replace(" ", "-")


# test_shop.py — тест
from shop import slugify

def test_slugify_replaces_spaces_with_dashes():
    assert slugify("Login Page") == "login-page"
```

Тест — звичайна функція: викликає код і перевіряє результат через `assert`. Якщо умова хибна, `assert` піднімає `AssertionError`, і pytest позначає тест як упалий.

## Чому не unittest

У стандартній бібліотеці є модуль `unittest`, але pytest зручніший:

| | unittest | pytest |
|---|---|---|
| Тест | метод класу-нащадка `TestCase` | звичайна функція (або клас без наслідування) |
| Перевірка | `self.assertEqual(a, b)`, `self.assertTrue(x)`… | звичайний `assert a == b` |
| Повідомлення про падіння | загальне | показує значення обох сторін: `assert 850 == 900` |
| Підготовка даних | `setUp` / `tearDown` | фікстури (наступний модуль) |
| Розширення | мало | сотні плагінів: звіти, паралельний запуск, Playwright |

pytest уміє запускати і старі unittest-тести, тож перехід на нього безболісний.

## Як pytest знаходить тести

Запуск `python -m pytest` шукає тести в поточній папці та підпапках за домовленостями:

| Що | Правило | Приклад |
|---|---|---|
| Файл | `test_*.py` або `*_test.py` | `test_cart.py`, `cart_test.py` |
| Функція | назва починається з `test` | `def test_total_with_discount():` |
| Клас | назва починається з `Test`, **без** `__init__` | `class TestCart:` |
| Метод класу | назва починається з `test` | `def test_add(self):` |

Усе інше (хелпери, `make_user()`, файл `helpers.py`) pytest не запускає як тести — і це добре: допоміжний код живе поруч із тестами.

## Arrange — Act — Assert

Хороший тест читається як три кроки:

```python
def test_slugify_trims_spaces():
    title = "  Cart  "              # Arrange — підготувати дані
    slug = slugify(title)           # Act — виконати дію
    assert slug == "cart"           # Assert — перевірити результат
```

Для коротких тестів кроки можна об'єднати в один рядок, але думати варто саме так.

## Як курс перевіряє твої тести

У задачах модуля ти пишеш файл `tests.py` для коду з `subject.py`. Кнопка **Check**:

1. запускає твої тести на **правильному** коді — вони мають бути зеленими;
2. запускає їх на кількох **зламаних** версіях коду — **мутантах**. Кожен мутант має рівно один баг, і твої тести мають його **зловити** (хоч один тест має впасти).

Мутант, якого не зловив жоден тест, «вижив» — під ним з'явиться підказка, яку поведінку ти не перевірив. Це найчесніша перевірка тестів: тест, який не падає на зламаному коді, нічого не захищає.

> [!QA]
> На своєму комп'ютері (з модуля про налаштування проєкту): `python -m pip install pytest`, файл `test_*.py` поруч із кодом — і `python -m pytest`. Тут, у курсі, працює той самий синтаксис: `assert`, `import pytest`, `pytest.raises`, `pytest.approx`.

## Типові помилки

- Файл `cart_tests.py` або `checks.py` — pytest його не побачить: `collected 0 items`.
- Функція `check_total()` замість `test_total()` — не тест, не запуститься.
- Тест без `assert` — завжди «зелений», навіть якщо код зламаний.
- `class TestCart:` з `__init__` — pytest пропустить клас із попередженням.

## Підсумок

- Тест у pytest — функція `test_*` з `assert`; клас — `Test*` без `__init__`.
- pytest простіший за unittest: звичайний `assert` і зрозумілі повідомлення.
- Файли — `test_*.py` або `*_test.py`; хелпери без префікса не запускаються.
- Структура тесту: Arrange → Act → Assert.
- Тест має сенс, лише якщо він **падає на зламаному коді** — так курс і перевіряє твої тести.
