# Тести, що ловлять баги

Тест, який ніколи не падає, нічого не захищає. У цьому уроці — як писати тести, що впадуть саме тоді, коли поведінка зламалася, і як у цьому переконатися.

## Перевір тест

Перш ніж довіряти новому тесту, побач його **червоним** хоча б раз:

1. Тимчасово зламай код (`>=` → `>`, прибери рядок) — тест має впасти.
2. Або тимчасово зміни очікуване значення — тест має впасти з зрозумілим повідомленням.
3. Поверни все як було.

Якщо тест лишився зеленим, він перевіряє не те, що ти думаєш.

## Покриття коду проти мутацій

**Покриття (coverage)** показує, які рядки коду виконались під час тестів (`pytest-cov`). Але виконати рядок — не те саме, що перевірити результат:

```python
def test_delivery_fee_runs():
    delivery_fee(500, "courier")      # 100 % покриття цього рядка, 0 перевірок
```

**Мутаційне тестування** перевіряє якість тестів: інструмент (для Python — `mutmut`) вносить у код маленькі зміни — мутантів — і запускає тести. Мутант, на якому тести зелені, «вижив» — це прогалина. Саме так курс перевіряє твої задачі в цьому модулі.

## Сильні і слабкі перевірки

| Слабка | Сильна |
|---|---|
| `assert result` | `assert result == 850` |
| `assert len(items) > 0` | `assert items == ["Mouse", "Cable"]` |
| `assert "error" in message.lower()` | `assert message == "Invalid email"` |
| `pytest.raises(Exception)` | `pytest.raises(ValueError, match="Invalid price: 'abc'")` |
| `assert user is not None` | `assert user == User(1, "qa@example.test")` |

Слабка перевірка пройде на багатьох неправильних результатах. Сильна — лише на правильному.

## Розбір: від вимог до тестів

Вимога: «Доставка: вага до 1 кг — 50 грн, понад 1 кг — 80 грн; експрес додає 100 грн». Таблиця рішень:

| Вага | Експрес | Очікування | Тест |
|---|---|---|---|
| 1.0 кг (межа) | ні | 50 | `test_one_kg_is_light_parcel` |
| 1.1 кг | ні | 80 | `test_over_one_kg_is_heavy_parcel` |
| 0.5 кг | так | 150 | `test_express_adds_100_to_light` |
| 2 кг | так | 180 | `test_express_adds_100_to_heavy` |
| −1 кг | ні | `ValueError` | `test_negative_weight_is_rejected` |

Кожен рядок перевіряє окремий ризик: межу ваги, кожну комбінацію умов, некоректні дані. Це ті самі техніки, що й у модулі тест-дизайну, — тепер вони стають кодом.

> [!QA]
> Найкраща звичка автоматизатора — питати «яку помилку розробника зловить цей тест?». Якщо для тесту можна назвати конкретний баг (межа, пропущена умова, неправильне повідомлення), тест корисний. Якщо ні — він лише збільшує час прогону.

## Типові помилки

- Лише «щасливий шлях» — жодного негативного тесту.
- Очікуване значення скопійоване з фактичного виводу програми: якщо там баг, тест його закріпить.
- Перевірка деталей реалізації (назв внутрішніх змінних) замість поведінки — тест ламається при кожному рефакторингу.
- Висока цифра покриття як мета — тести виконують код, але нічого не перевіряють.

## Підсумок

- Новий тест варто побачити червоним — інакше незрозуміло, чи він щось перевіряє.
- Покриття показує виконані рядки; мутаційне тестування — чи тести ловлять зміни.
- Сильна перевірка приймає лише правильний результат.
- Тести будуються з вимог: класи, межі, таблиця рішень, негативні сценарії й повідомлення.
