# Організація тестів

Поки тестів десять, байдуже, де вони лежать. Коли їх сотні, порядок вирішує, чи знайде колега потрібний тест за хвилину і чи будуть тести стабільними.

## Файли й папки

```text
project/
├── shop/
│   ├── cart.py
│   └── delivery.py
├── tests/
│   ├── test_cart.py          ← тести для shop/cart.py
│   ├── test_delivery.py
│   └── api/
│       └── test_orders.py
└── pyproject.toml
```

Правило просте: один модуль коду — один файл тестів з тією самою назвою. У `pyproject.toml` можна вказати, де шукати тести, щоб pytest не обходив увесь проєкт:

```toml
[tool.pytest.ini_options]
testpaths = ["tests"]
```

## Класи для групування

Тести однієї функції чи сутності зручно зібрати в клас:

```python
class TestDeliveryFee:
    def test_pickup_is_free(self):
        assert delivery_fee(500, "pickup") == 0

    def test_courier_is_free_from_10000(self):
        assert delivery_fee(10000, "courier") == 0
```

- назва починається з `Test`, **без** `__init__`;
- кожен тест — метод з `self`;
- у звіті тест виглядає як `test_delivery.py::TestDeliveryFee::test_pickup_is_free`.

## Розбір: кожен тест отримує новий об'єкт

pytest створює **окремий** екземпляр класу для кожного тесту:

| Тест | Об'єкт `self` | Що бачить |
|---|---|---|
| `test_pickup_is_free` | новий `TestDeliveryFee()` №1 | лише свої атрибути |
| `test_courier_is_free_from_10000` | новий `TestDeliveryFee()` №2 | не бачить змін тесту №1 |

Тож `self.something = ...` в одному тесті не протече в інший — клас групує, але не ділить стан. А от атрибути **класу** (оголошені в тілі класу) спільні для всіх — у них не можна класти змінювані дані.

## Хелпери і білдери даних

Повторювану підготовку виносять у функції без префікса `test` — pytest їх не запускає:

```python
def make_user(**overrides):
    user = {"email": "qa@example.test", "role": "customer", "active": True}
    user.update(overrides)
    return user

def test_inactive_user_cannot_log_in():
    assert can_log_in(make_user(active=False)) is False
```

Тест показує лише те, що для нього важливо (`active=False`), а все інше бере зі значень за замовчуванням. Якщо в користувача з'явиться нове обов'язкове поле, правка буде в одному місці.

## Незалежність тестів

Кожен тест має проходити **сам по собі і в будь-якому порядку**. Погано:

```python
CART = Cart()                    # спільний об'єкт для всіх тестів

def test_add():
    CART.add("Mouse", 450)
    assert CART.count() == 1

def test_total():
    assert CART.total() == 450   # працює, лише якщо test_add запустився раніше
```

Добре — кожен тест готує свої дані:

```python
def test_total():
    cart = Cart()
    cart.add("Mouse", 450)
    assert cart.total() == 450
```

> [!QA]
> Залежні тести — головне джерело «нестабільних» прогонів: окремо тест зелений, у повному прогоні червоний, а з `-k` — знову зелений. Плагіни паралельного запуску й випадкового порядку роблять такі залежності помітними одразу. Краще не створювати їх узагалі.

## Типові помилки

- Глобальний змінюваний об'єкт (`CART = Cart()`, `USERS = []`), який тести змінюють.
- Один тест викликає інший тест — це прихована залежність.
- Хелпер з назвою `test_data()` — pytest спробує запустити його як тест.
- Клас тестів з `__init__` — pytest його пропустить.
- Один файл на тисячу рядків «для всього» — шукати тест стає неможливо.

## Підсумок

- `tests/test_<модуль>.py` для кожного модуля коду; `testpaths` у конфігурації.
- Класи `Test*` групують тести; кожен тест отримує новий об'єкт, тож стан не протікає.
- Хелпери й білдери (`make_user(**overrides)`) — без префікса `test`.
- Кожен тест готує свої дані й проходить у будь-якому порядку.
