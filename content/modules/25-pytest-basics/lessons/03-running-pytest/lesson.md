# Запуск pytest і читання результату

Половина роботи автоматизатора — не писати тести, а **розбиратися, чому вони впали**. pytest дає для цього все: потрібно лише вміти запустити саме те, що треба, і прочитати вивід.

## Команди

Усі команди виконуються з **кореня** проєкту в активованому оточенні:

| Команда | Що робить |
|---|---|
| `python -m pytest` | запустити всі тести |
| `python -m pytest -v` | показати кожен тест окремим рядком |
| `python -m pytest -q` | короткий вивід |
| `python -m pytest -x` | зупинитися після першого падіння |
| `python -m pytest -k cart` | лише тести, у назві яких є `cart` |
| `python -m pytest tests/test_cart.py` | один файл |
| `python -m pytest tests/test_cart.py::test_total` | один тест |
| `python -m pytest --lf` | повторити лише ті, що впали минулого разу |
| `python -m pytest -s` | показувати `print` з тестів |

Опції можна поєднувати: `python -m pytest -x -v -k checkout`.

## Анатомія виводу

```text
============================= test session starts =============================
collected 5 items

tests/test_cart.py ..F.s                                                 [100%]

================================== FAILURES ===================================
_______________________________ test_total_with_discount ______________________

    def test_total_with_discount():
        cart = make_cart(discount=100)
>       assert cart.total() == 1050
E       assert 1150 == 1050
E        +  where 1150 = <Cart>.total()

tests/test_cart.py:21: AssertionError
=========================== short test summary info ===========================
FAILED tests/test_cart.py::test_total_with_discount - assert 1150 == 1050
==================== 1 failed, 3 passed, 1 skipped in 0.08s ===================
```

## Розбір: як читати цей вивід

| Рядок | Що він каже |
|---|---|
| `collected 5 items` | pytest знайшов 5 тестів; `collected 0 items` — проблема з назвами файлів чи функцій |
| `..F.s` | по символу на тест: `.` пройшов, `F` впав, `s` пропущений, `E` — помилка підготовки |
| `>` | рядок тесту, на якому стався збій |
| `E   assert 1150 == 1050` | фактичне (1150) проти очікуваного (1050) |
| `tests/test_cart.py:21` | файл і номер рядка |
| `FAILED ... - assert ...` | короткий підсумок — зручно копіювати в тікет |
| останній рядок | загальний рахунок і час |

Тут знижка не віднялася: 1150 = 1050 + 100. Вивід уже підказав гіпотезу.

## F чи E?

- **F (failed)** — упав сам тест: хибний `assert` або виняток у тілі тесту.
- **E (error)** — збій **до** або **після** тесту: у фікстурі (підготовці даних), при імпорті, у прибиранні. Продукт може бути цілком справний — зламалася підготовка.

Коди виходу: `0` — усе пройшло, `1` — є падіння, `5` — не знайдено жодного тесту. CI дивиться саме на код виходу.

## Баг у продукті чи в тесті?

Червоний тест — не завжди баг продукту. Порядок дій:

1. Прочитай `E`-рядки: що отримали, що очікували.
2. Звір **очікуване** значення з вимогами — може, помилився автор тесту.
3. Відтвори вручну (або в консолі Python).
4. Якщо помилився тест — виправ тест. Якщо продукт — заведи баг і залиш тест червоним (або познач як відомий баг).

> [!WARNING]
> Ніколи не «лагодь» тест, підганяючи очікуване значення під фактичне, не перевіривши вимоги. Так баг продукту стає «нормою», а тест — фальшивим захистом.

> [!QA]
> У задачах курсу панель результатів показує те саме: назву тесту, `assert` з фактичним і очікуваним значенням, рядок і підказку. Звичка читати вивід уважно економить години в реальних проєктах.

## Типові помилки

- Запуск не з кореня проєкту — `ModuleNotFoundError` в імпортах.
- `-k` з назвою, якої немає, — `collected 0 items` і код виходу 5, а не «все зелене».
- Ігнорувати `E` і шукати баг у продукті, хоча зламалася фікстура.
- Змінити очікуване значення в тесті, щоб він позеленів, не звіривши з вимогами.

## Підсумок

- `python -m pytest` з кореня; `-v`, `-x`, `-k`, `--lf`, `-s`, `файл::тест` — для вибору й деталей.
- Вивід: `.` / `F` / `E` / `s`, рядок `>`, рядки `E` з фактичним і очікуваним, короткий підсумок.
- F — упав тест; E — збій підготовки або прибирання.
- Червоний тест: спершу звір очікування з вимогами, потім вирішуй — баг продукту чи тесту.
