# Логування

Коли сервер працює десь у хмарі, `print` нікому не допомагає: немає часу події, не видно, з якого модуля повідомлення, не можна вимкнути зайве й увімкнути подробиці, коли щось зламалось. Лог — головне джерело правди про те, що відбувалося в продакшні. Модуль `logging` дає рівні важливості, назви джерел, формат і різні місця призначення — консоль, файл, систему збору логів.

## Рівні

| Рівень | Число | Коли |
|---|---|---|
| `DEBUG` | 10 | подробиці для налагодження: SQL-запити, тіла відповідей |
| `INFO` | 20 | нормальні події: сервіс запустився, замовлення оплачено |
| `WARNING` | 30 | щось незвичне, але робота триває: повільна відповідь, застарілий параметр |
| `ERROR` | 40 | операція не вдалась: оплату не списано |
| `CRITICAL` | 50 | система не може працювати: немає бази даних |

Логер з рівнем `INFO` пропускає `INFO` і вище, а `DEBUG` відкидає. У продакшні зазвичай `INFO`, під час розслідування — тимчасово `DEBUG`.

## Логер на модуль

```python
import logging

logger = logging.getLogger(__name__)      # у файлі app/orders.py → ім'я 'app.orders'


def pay(order_id, amount):
    logger.info("order %s: charging %s UAH", order_id, amount)
```

Імена утворюють **ієрархію**: `app.orders` — дочірній для `app`, а всі — для кореневого логера. Записи «спливають» до батьків (`propagate`), тому налаштувати вивід достатньо один раз на верхньому рівні.

## Налаштування — один раз, у точці входу

```python
# main.py — точка входу застосунку
logging.basicConfig(
    level=logging.INFO,
    format="%(asctime)s %(levelname)s %(name)s: %(message)s",
)
```

```text
2026-03-20 10:15:02,114 INFO app.orders: order 1002: charging 2399 UAH
```

Модулі й бібліотеки лише створюють логер і пишуть у нього, але **не** налаштовують вивід — це рішення застосунку. Фреймворки (uvicorn, Django) мають власну конфігурацію логування, яку розширюють через `logging.config.dictConfig`.

## Розбір: шлях одного запису

`logger.warning("slow request %s", path)` у логері `app.api`:

| Крок | Що відбувається |
|---|---|
| 1 | рівень логера: `WARNING` ≥ рівня `app.api`? Ні — запис відкидається одразу |
| 2 | так — створюється `LogRecord`: рівень, ім'я, шаблон `msg` і аргументи `args`, час |
| 3 | запис передається **обробникам** (handlers) логера: кожен має свій рівень і місце призначення |
| 4 | обробник просить свій **форматер** перетворити запис на текст: `%(levelname)s %(name)s: %(message)s` |
| 5 | текст іде в потік, файл чи мережу |
| 6 | якщо `propagate` увімкнено — запис іде й до обробників батьківського логера |

```python
import sys

handler = logging.StreamHandler(sys.stdout)
handler.setFormatter(logging.Formatter("%(levelname)s %(name)s: %(message)s"))
handler.setLevel(logging.WARNING)
```

Через крок 6 типова помилка — **подвійні рядки**: обробник додали і логеру, і кореневому, а `propagate` лишився `True`. Або функція налаштування викликається двічі й двічі додає обробник.

## «Ліниві» аргументи замість f-рядків

```python
logger.debug("order %s total %s", order_id, total)    # так
logger.debug(f"order {order_id} total {total}")       # гірше
```

З `%s`-аргументами текст збирається лише тоді, коли запис справді виводиться. До того ж шаблон (`record.msg`) однаковий для всіх замовлень — системи збору логів групують за ним однакові події.

## Помилки: logger.exception

```python
try:
    gateway.charge(order)
except PaymentError:
    logger.exception("order %s: payment failed", order.id)
    raise
```

`logger.exception(...)` — це `ERROR` **плюс traceback** поточного винятку; викликають її лише всередині `except`. `logger.error(...)` без `exc_info=True` traceback не додає — і причину потім не знайти.

## Чого не писати в лог

Паролі, токени, ключі API, номери карток, повні персональні дані. Логи читає багато людей і систем, їх довго зберігають. Маскуй дані до запису (урок про регулярні вирази) і логуй ідентифікатори (`user 42`), а не вміст профілю.

## Логи в тестах

У pytest є фікстура `caplog`: вона збирає записи, і тест перевіряє, що, наприклад, при збої оплати записано `ERROR` з номером замовлення. Без pytest те саме роблять власним обробником, що складає записи в список.

## Типові помилки

- `print` у коді сервера замість логера.
- `basicConfig` у модулі бібліотеки — вона «захоплює» налаштування всього застосунку.
- Подвійні рядки: обробник додано двічі або разом із `propagate`.
- `logger.error(...)` у `except` без traceback замість `logger.exception(...)`.
- Секрети й персональні дані в логах.
- `logging.info(...)` (кореневий логер) замість логера модуля — не видно, звідки запис.

## Підсумок

- Рівні: DEBUG < INFO < WARNING < ERROR < CRITICAL; логер пропускає свій рівень і вищі.
- `logger = logging.getLogger(__name__)` у кожному модулі; налаштування виводу — один раз у точці входу.
- Логер → обробники (рівень, місце) → форматер → текст; `propagate` передає запис батькам.
- Аргументи через `%s`, не f-рядком; `logger.exception` в `except` додає traceback.
- Жодних секретів у логах; у тестах — `caplog` або власний обробник.
